The rewrite is still infeasible. Mandatory evidence requires a single shared append/inbox implementation whose mutation breaks both CLI and SDK, while bounds confine work to the SDK and its manifest and the only write/inbox control flow still lives unexported inside cli.mjs run(). Retry-safety and never-overwrite remain unsatisfiable on an API that mints a fresh UUIDv7 path and writes before verify. Port Watch/durable cursors and ACTOR_UNREGISTERED-with-zero-writes are not properties of the existing adapter, so a thin client cannot make them true without a second implementation or a forbidden substrate change. Rule 5, publication approval, and verifier completeness do not remove that contradiction.

## Findings

- Shared-implementation proof contradicts the stated bounds. A mutation that breaks both CLI and SDK append/inbox requires extracting the write and inbox control flow from cli.mjs run() into a shared module both import. Bounds allow only the SDK and its manifest, and they forbid protocol change. Those mandatory requirements cannot be true together in the current repository state.
- The four named exports are not a canonical append/inbox implementation. validateAppendInputs, verifyLog, discoverEventFiles, and EVENT_TYPES do not create events, choose actor directories, enforce reply/retry, or filter an inbox. A client limited to those exports must reimplement the write path, which is the third drifting surface the objective says it must not create, and a shared-module mutation then cannot break both tools.
- Never-overwrite as specified cannot fire. Append invents occurred_at plus a new UUIDv7 and writes with wx to that unique path, so a caller cannot target another actor’s existing file through the public operation. The prescribed refusal is the same unreachable-control defect as a digest mismatch on a digest the API itself computes. wx already makes any colliding path fail for every actor; a test of that flag does not discriminate SDK never-overwrite.
- Retry-safety-by-count is underspecified and incompatible with the current write path. Two append() calls each mint a new id and timestamp, so they are two events by construction and a file count cannot identify a retry. Stabilizing identity needs a caller-supplied id/idempotency key the CLI does not accept. Append writes first and verifyLog afterwards; a second strict_relay reply already leaves a stranded file and an invalid log. Producing exactly one event with zero debris requires validate-then-write and EEXIST-as-success, which is not in the exported substrate and cannot be shared under SDK-only bounds.
- Claim 2 cannot be satisfied by a thin client. Inbox discovery exists in the CLI; Port Watch and durable cursors do not exist in git-adapter and have no spec in the supplied evidence. Implementing them is new product behavior, not a wrapper. Local-only cursors would be a second implementation the shared-mutation proof cannot see. Dropping the qualifier is forbidden by the dispatch’s own ‘qualifiers, not the verbs’ rule.
- ACTOR_UNREGISTERED plus zero writes is not a property of the existing implementation and has no defined subject without enrollment. CLI append mkdirs events/<actor>, writes, then verifies; an unknown actor already leaves files. Git-v0 has no enrolled caller, only actors.yaml. If every caller is unenrolled, every append must refuse and claims 1–4 cannot be demonstrated. If ‘unenrolled’ is silently redefined as ‘missing actors record,’ the check is new pre-write behavior: SDK-only breaks canonicality; putting it in git-adapter exceeds the bounds and the no-enrollment bound.
- Authority framing does not make the dispatch executable. AGENTS.md already splits rule 5, ADR 0038 already authorizes an SDK build and forbids this-slice publish, and verifier completeness only concerns events/ discovery. None of that extracts append/inbox, specifies Port Watch, or defines retry identity. Wiring @engramport/sdk into a private workspace also likely requires root/workspace and git-adapter export edits, which are not ‘SDK and its manifest only.’
