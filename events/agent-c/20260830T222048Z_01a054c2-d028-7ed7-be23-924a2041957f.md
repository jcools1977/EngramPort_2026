The proposed dispatch is infeasible as specified. Its mandatory control—an enrollment-authority key ordinary builders cannot rewrite—cannot be completed inside the named in-tree bounds while agents push directly to main. The cited SECURITY DEFINER issuer is the wrong plane and the wrong capability: it cannot write issuer or subject claims and cannot bind git actor keys. Event signing does not beat F108 or F127; it relocates both. The specified tamper test cannot discriminate the actual adversary. Live append refuses any schema_version other than 1, and there is no per-builder private-key custody compatible with no-secret-on-disk, so an accepted event cannot prove which builder authored it in the current runtime.

## Findings

- Self-contradictory mandatory requirement: the design forbids skipping an enrollment-authority key that ordinary builders cannot rewrite, while bounds confine work to in-tree actor records, envelope, verifier, and enrollment binding and exclude hosted deployment. AGENTS.md already records that agents push to main and that an authorized writer can commit actors/*.yaml together with the checks that would have caught the edit. No actor in this tree can make an in-repo key non-rewritable. That is not a remaining prerequisite; it is an unsatisfiable requirement inside the dispatch’s own authority and bounds.
- False capability claim on the existing issuer. migrations/0023_founder_authorization_issuer.sql states that issue_founding_authorization issues only one-shot founding authorization state, deliberately cannot write an issuer or subject claim, and is executable only by engram_bootstrap_operator. founding_authorizations has no public-key column. A Postgres SECURITY DEFINER function cannot sign git actor-to-key bindings, and the git verifier cannot consume a database grant. Reusing that issuer ‘rather than a new mechanism’ is unsatisfiable; a git-verifiable authority is a new mechanism on a different plane, and no EngramPort actor is engram_bootstrap_operator.
- The specified registry-tamper evidence cannot discriminate F108. ‘Swapping a key in an actor record fails verification’ only catches a naive one-field edit. The threat already named in-tree is one commit that replaces the key, the authority signature, any in-tree authority key, and if needed the verifier. A test that does not perform that combined mutation can pass while impersonation still verifies. Historical unsigned events verifying unchanged also does not prove the new binding is non-tamperable.
- Event signing is not stronger than commit-identity comparison against the F127 adversary. Both bind whoever controls the in-tree identity object (actor record vs git user). Agent-a’s portable-log objection is valid for export and rebase, and only that: it justifies signatures as a Port feature, not as an impersonation fix. docs/security/attribution-hardening.md already notes that commit signatures prove the pusher, not from: honesty, and that closing the gap is verifier comparison to the introducing commit’s identity. That cheaper path has the same F108 exposure and does not require a new secret class. Rejecting it as ‘wrong’ overstates the security gain.
- Production objective is unsatisfiable under current key custody. appendEvent in packages/git-adapter/src/event-core.mjs has no signature hook; live append refuses schema_version !== 1, so a cutover ‘like schema_version’ cannot be v2 without a writer change the dispatch does not specify. The unsigned-vs-signed v1 epoch would itself be repository content (another F108 object). Standing rule: no secret on disk. F127’s second builder used createClient({ actor: "builder-one" }) on what is still one operator machine whose git identity is uniform. Without per-builder key isolation outside this tree, builder two can sign as builder one the same way they can pass the actor string. In-memory test keys can manufacture the required ‘refused’ observation without any live accepted event proving authorship. Bounds that allow ‘no SDK surface change beyond what signing requires’ leave that createClient trust boundary unaddressed.
- No named implementer can land the work. Agent-a’s recorded capabilities are architecture, review, coordination. Actor-record key fields are registry mutations; local actors/*.yaml drift is policy-rejected relative to HEAD. The dispatch is not yet a handoff (no bounded_context / completion_criteria) and cites agent-b’s executed= observation, which is not in the supplied evidence. Sending this as an implementation dispatch would instruct an actor to exceed authority, invent an enrollment plane the issuer does not provide, and treat non-discriminating tests as proof.
