## Blocking findings

**1. Founder authority expiry is never enforced. Security defect, reproduced live.**

`founder_authorities.expires_at` is `NOT NULL`, and nothing reads it. `resolve_founder_authority` selects the row with no predicate on it, and `bootstrap_workspace` checks only `IF NOT FOUND`.

I inserted an authority expiring **one day in the past** and ran the real functions against the live database:

- `resolve_founder_authority` returned it, scopes intact.
- `bootstrap_workspace` **succeeded**, creating tenant, project, principal and owner membership.
- Resulting tenant count: **1**.

An expired founder authority creates a workspace and an owner membership that nothing subsequently revokes. This is exactly the decorative-expiry pattern constraint **C6** exists to forbid, and it sits in the one function whose entire purpose is to be the trusted authority boundary. The column looks like a control and is not one.

**Fix:** enforce expiry in the resolver against the **database clock**, per C6, and separately in `bootstrap_workspace` so it cannot be bypassed by a caller that resolves elsewhere. Add a control asserting an expired authority fails distinctly, with a paired positive control on an unexpired one.

**2. Property 9 has no control, and writing it is less obvious than it looks.**

Nothing demonstrates that removing the datastore guard permits two winners, so "the race is datastore-enforced" is currently asserted rather than proven.

I tried to write it and found something you should know: **the barrier is layered.** I dropped `bootstrap_establishments`'s primary key and both unique constraints, reran the race, and **still got exactly one winner**, because both racers insert the same `p_principal_id` into `principals` and `principals_pkey` fires instead.

That layering is good design, and it means the naive control does not work. The control must either remove the full set of colliding constraints, or target the specific constraint you claim is the barrier and show that the *next* barrier is what caught it. Say which constraint you consider authoritative for this race, because right now the answer is ambiguous.

**3. The loser-residue control's message overclaims what it asserts.**

The runner prints `PASS concurrent loser residue inventory: tenant/project/principal/membership/delegation/approval/session/audit residues are absent for loser graph`, but the assertion behind it checks exactly two things: one `bootstrap_establishments` row and one `project_memberships` row.

The residue really is zero, which I verified across eleven categories, so this is not a false result. It is a control whose name misdescribes what it proves, which is the same defect class I flagged for `application UPDATE denied` in B1 and for the migration-owner control in F16. A later reader will trust the message. Either assert all eight categories or narrow the message to what it checks.
