# Pre-flight: onboarding, the Port Package

**The repository went public today.** Its README says plainly: no npm package, no quickstart, no provisioning path, **"if you are looking for a tool to adopt today, this is not that yet."** This slice is meant to make that caveat obsolete.

`docs/architecture/port-family.md` names Port Package as *"what does a newcomer need to start, and how do they verify it?"* **It has never been built.** F127 recorded why it matters: agent-b enrolled a second builder by writing identity, principal, binding and actor registry **directly into test fixtures, because the repository has no provisioning path.**

---

## PROPOSED DISPATCH (not yet sent)

**Objective: a newcomer can start using EngramPort without reading the source.**

**Scope is deliberately the easy case: starting your own project.** A person clones or forks, registers themselves as an actor, appends a first event, discovers addressed work, and verifies the result. **Joining someone else's existing project is out of scope** and the reason must be stated rather than omitted: joining requires an authority to approve the newcomer, and F127 established that authorship cannot be authenticated here, so "join" would be an unauthenticated self-registration wearing an approval's clothes.

**Deliver:** a documented path a stranger can follow end to end, and whatever minimal tooling that path needs. **It must not touch this repository's own 433-event log**; a newcomer starts a fresh log, not a fork of ours.

**Verification is part of onboarding, not after it.** Port Package's own definition includes "how do they verify it." The newcomer must be able to prove their setup is sound, which `npm run proof:verify` already provides if the path produces a valid log.

**Required evidence.** The path is executed start to finish in a clean directory by something that is not the author's memory: a test that follows the documented steps and ends with a verifying log. **A step that exists only in prose and not in that test is not part of the path.** The repository's own log verifies unchanged.

**Bounds.** Onboarding documentation, minimal scaffolding tooling, and its test. No enrollment for third parties, no npm publish, no site copy change, no protocol or envelope change. `executed=` moves from its observed value, which agent-b states.

## What to check

- **Is "start your own project" actually the valuable case, or is it the easy one agent-a chose to avoid the hard one?** If most real users want to join an existing project, this slice may satisfy a criterion while missing the need.
- **Can a newcomer self-register as an actor without that being the F127 hole under a friendlier name?** In a fresh log they are the only participant, so agent-a believes it is sound. **Attack that**, because it is the assumption the whole scope rests on.
- **Does "must not touch this repository's log" survive contact with a fork?** A user who forks gets our 433 events. Is starting fresh even coherent in a fork, or does the path require something else?
