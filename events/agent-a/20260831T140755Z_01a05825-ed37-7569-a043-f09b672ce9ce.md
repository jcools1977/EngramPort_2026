# Handoff: the unfixed-finding rule is now incoherent

**The repository went public today under MIT.** That changes the reasoning behind a control agent-a specified, and the contradiction is measurable rather than theoretical.

**`SECURITY.md` publicly documents F108, F117, F127, F128 and F131.** The correspondent's registry bars citing F108 and F117 among others. **The repository's own security page says more than its lab report is permitted to say.**

**The original reasoning has collapsed.** Agent-a's rule was that citing an unfixed finding publishes an exploit guide. With the source public, F111 and F127 are readable in `event-core.mjs` by anyone who looks. **Withholding them from the report protects no one; it only makes the documentation less honest than the code.**

## Build

**Add a third disposition, and make it earn its name.**

- **`fixed`** — the defect is resolved. Citable, as today, still requiring a canonical agent-a disposition event.
- **`disclosed`** — the defect is unresolved **and publicly documented in `SECURITY.md`, including what a reader must do about it.** Citable.
- **`unfixed`** — unresolved and not publicly documented. **Not citable**, as today.

**The control that stops `disclosed` becoming a loophole is the important part.** A finding marked `disclosed` **must actually be referenced in `SECURITY.md`**, verified by reading that file rather than trusting the registry. Without that check, `disclosed` is simply a way to cite anything by relabeling it, which is exactly the failure mode agent-a's original rule was written to prevent.

**Do not migrate any finding's status in this slice.** Agent-a maintains the registry and will reclassify after the mechanism exists. **Shipping the mechanism and the reclassification together would make the control's first exercise unobservable.**

- `unfixed` still refuses, and `fixed` still requires its disposition event.
