## The six defects

**A. Extension provisioning is absent — your reported blocker.** `build()` never creates the extensions, so migration `0001` fails with `permission denied to create extension "vector"` under `engram_migrator`. Reproduced.

**The canonical provisioning boundary already exists**: `deploy/init-extensions.sql`, mounted into `/docker-entrypoint-initdb.d/` by `deploy/docker-compose.yml`, which runs as the **image bootstrap superuser** at container init. It only ever runs for the default `engramport` database, which is why a freshly created scratch database has no extensions. Reference that file rather than inlining SQL, so there is one source of truth:

```bash
psql_as postgres "$SDB" < "$root_dir/deploy/init-extensions.sql" >/dev/null || return 1
```

placed immediately after `CREATE DATABASE` and **before** the migration loop. This grants `engram_migrator` nothing, applies no migration as `postgres`, edits no migration, and leaves the live runner's F16 boundary untouched.

**B. `assert()` cannot read the fixture.** It passes `-f "$root_dir/tests/failure/d1-behavioural.sql"`, a **host** path, to a psql running **inside the container**. I confirmed the container cannot see that path. Feed it over stdin, which the host shell resolves:

```bash
assert(){ psql_as engram_maintenance "$SDB" -f - < "$root_dir/tests/failure/d1-behavioural.sql" >/dev/null 2>&1; echo $?; }
```

**C. `assert()` returns no value.** It runs psql and echoes nothing, so `base=$(assert)` captures the empty string and every comparison such as `[ "$base" = 0 ]` is false. **The harness can never report success.** Observed directly once A was fixed: `baseline= applied=t after= restored=`. The `echo $?` above fixes it.

**D. An empty or missing mutation list is reported as success.** With the list emptied, the harness printed `all controls discriminate` and exited **0** having run nothing. Require the count:

```bash
[ "${#MUTATIONS[@]}" -ge 4 ] || { echo "only ${#MUTATIONS[@]} control(s) listed, expected at least 4" >&2; exit 1; }
```

I verified this refuses an empty list with a clear message. A harness that passes vacuously is the same defect class as the notice-only ACL branch.

**E. The G4 loop variable is undeclared.** `FOR ns IN SELECT unnest(ARRAY['shape','installation'])` makes `ns` a row variable, and PostgreSQL rejects it:

```
ERROR:  loop variable of loop over rows must be a record variable or list of scalar variables
```

Isolated both forms side by side: that construct errors, and `FOREACH ns IN ARRAY ARRAY['shape','installation']` with **`ns text` declared** succeeds. Declare `ns text` and use `FOREACH … IN ARRAY`, as the handed-over fixture did.

**F. The seed grants the very scope G3 treats as unheld.** `build()` seeds `custody:mint:credential:3.2:B`, and G3 mints `3.2` expecting `SCOPE_EXCEEDED`. Demonstrated on identical databases differing only in the seed:

| Seed | G3 result |
|---|---|
| yours, `3.2:B` granted | **mints** `epr:credential:01a01a1c-…` |
| handed over, `3.2:B` absent | **`SCOPE_EXCEEDED`** |

So G3 would have failed at baseline for a reason unrelated to the guard. Drop `custody:mint:credential:3.2:B` and keep only the three `3.12` triples: `credential`, `shape` and `installation`. The `shape` and `installation` triples must stay, because without them the scope check masks M8, which is the trap from two rounds ago.
