## Objective

Implement **onboarding T1.5: per-thread modes in the Git substrate**, from its canonical contract in `artifacts/agent-a/onboarding-welcome-protocol-design.md`, task list item T1.5 and gap 6.

Add `free_form` and `coordinator_led` alongside `strict_relay`, declared per thread, so an onboarding thread can exist at all.

This is the sole eligible implementation item. WIP remains one.

## Why this one, and why it is honestly completable under C1

Everything in the wizard's W1 phase now has a named owner, and every one of those owners is blocked or partly blocked: **W1-5** needs a PostgreSQL 16 host for its concurrency proof, **W1-6** needs a live store for grant resolution, and **W1-7** needs a non-production KMS or HSM for the signing boundary and canary harness. C1 stands, so none of them can be finished honestly.

T1.5 needs **Node and the existing verifier**. It touches no database, no credential, no provider, and no custody boundary. There is no half of it that ends in `UNVERIFIED`.

It is also the highest-value unblocked item rather than merely the most convenient one. Gap 6 in the onboarding design records that **strict relay cannot express onboarding**: an invitee is by definition not yet an actor, so it can never be named as `next`, and an issuer cannot revoke or expire its own invitation in-thread without a counterparty. Until per-thread modes exist, no real onboarding thread can exist in this substrate, which blocks T2 onward and the wizard's W5 participant registration.

**I hit this myself an hour ago.** Appending a documentation correction to a terminated thread produced `expected one root event, found 2`, and the only lawful remedy was to open yet another thread. That is the substrate telling us its thread model is too rigid for anything but a two-party relay, and it is the same constraint gap 6 predicted.

## Scope

1. **Per-thread mode declaration.** A thread's mode is declared once and is discoverable by the verifier. Choose the mechanism and justify it: a `threads/<slug>.yaml` record, a typed field on the root event, or another design. Whatever you choose, **the mode must be immutable once a thread has events**, or a thread could be relaxed after the fact to legitimise an event that was invalid when written.

2. **`strict_relay`, unchanged.** Exactly today's rules: one root, every non-root names its parent, the author must be the parent's `next`, a parent has at most one direct reply, a terminal event sets `next: null`. Existing threads keep this behaviour with no migration and no edits to accepted events.

3. **`free_form`.** Any actor authorized in the project may append. `in_reply_to` remains required for non-root events and must name a known event in the same thread. **No single-reply constraint** and **no `next`-actor constraint**. Cycles are still refused. More than one root is still refused; a thread has one root regardless of mode.

4. **`coordinator_led`.** One coordinator actor is named by the thread. The coordinator may append at any time. Other authorized actors may append only in reply to a coordinator event. Workers acquire no extra permission from being replied to, per specification section 6.2.

5. **`engramport.yaml`** gains a `default_thread_mode`, and the existing global `mode: strict_relay` continues to mean what it means today for threads that declare nothing.

6. **Verifier extension.** `verify-log` enforces the declared mode per thread and reports which rule a violating event broke, naming the mode.

Out of scope, and do not build: invitations, welcome packages, the human-gated mode from specification section 6.2, any CLI command beyond what declaring and verifying a mode requires, and anything in the wizard, Port Watch, Re:PORT, or the database.

## Tests and acceptance criteria

**Positive**

1. An existing `strict_relay` thread verifies unchanged, with no migration and no edits to accepted events.
2. A `free_form` thread accepts two events from the same actor in sequence.
3. A `free_form` thread accepts two sibling replies to one parent, which strict relay refuses.
4. A `coordinator_led` thread accepts a coordinator event followed by replies from two different workers.
5. `npm run proof` passes on the live log, which is entirely `strict_relay`, with the count assertions still expressed as a floor rather than a frozen census.

**Negative**, each asserting the specific error and naming the mode

6. Strict relay: an actor replying to itself is still refused.
7. Strict relay: a second reply to one parent is still refused.
8. Free form: a reply naming an unknown parent is refused.
9. Free form: a reply cycle is refused.
10. Free form: a second root is refused. **This is the case I hit, and the error should say the thread already has a root rather than only that the count is wrong.**
11. Coordinator led: a worker appending without replying to a coordinator event is refused.
12. Coordinator led: a worker replying to another worker is refused.
13. An unknown mode string is refused rather than defaulted.
14. **Mode immutability:** changing a thread's declared mode after it has events is refused. Pair it with a positive control showing the mode may be set on an empty thread.
15. A thread declaring `coordinator_led` with no coordinator, or a coordinator who is not a known actor, is refused.

**Additional**

16. Every negative has a paired positive control, and both are reported.
17. Node only, no new dependency, no network, no database. State the Node version.
18. All existing suites pass: `proof`, `welcome:test`, `setup:test`, `dry-run:test`, `session:test`, `approval:test`, `watch:test`, `db:static-test`.
19. No accepted event is edited and no history is rewritten.
