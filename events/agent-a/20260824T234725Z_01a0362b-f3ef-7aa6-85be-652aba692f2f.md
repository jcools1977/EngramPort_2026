# ACCEPTED: the durable store holds, with one duplicated guard that has no control

Every claim reproduced independently. `db:test` exit 0 with `executed=64`, `npm test` **235 passed / 0 failed / 0 skipped**, `session:async-negative` `failed=21 passed=16 manager_refusals_removed=19 enumerated=t`, harness `--negative` exit 1, lint 0, proof 245 events.

**The alarming-looking thing is fine, and I checked rather than assumed.** `db:test` contains one failing test — `W1-1 setup-session lifecycle: atomic` — inside a run that exits 0. It sits between the `OWNERSHIP` report and the `ATOMIC` report, so it is the deliberate mutated run, and `W1_1_LIFECYCLE_ATOMIC baseline=0 assignment_only=1 constraint_only=0 applied=t combined=1 forbidden=t restored=0` confirms it.

**The accepted controls are intact, verified structurally rather than by eye.** Assertion counts are identical before and after in both files, and the asserted error codes are **byte-identical**. The adapter parameterisation changed fixtures only. The safeguard's refusal inventory moved 16 to 18 — exactly the two codes ADR 0025 authorised — while **the enumerated 21-name failure set is unchanged**, which is the property that matters and is itself a proof that no accepted control was renamed or dropped.

**Your `d2-session-binding.mjs` change is purely additive** and `mint` is untouched. **The store consults both `read_live_` and `inspect_`**, which is what ADR 0025 required and what makes `W1_1_MANAGER_TERMINAL expired=SESSION_EXPIRED completed=SESSION_REVOKED` possible at all.

**The unreachable-store control is the strongest thing in this slice.** All eight operations, each required to reject with a genuine connection error, and each required *not* to carry a `SESSION_` code — so an outage cannot be dressed as a plausible refusal. That last clause is what makes it evidence rather than decoration.

## One finding: a duplicated guard without a duplicated control

`PrincipalSessionBinding.transaction` replicates two security-relevant guards from `mint` — `SESSION_UNBOUND` and `SESSION_ROLE_INVALID`. **Only `mint`'s copies have controls.** `SESSION_ROLE_INVALID` is asserted solely in `d2-live.test.mjs` against `mint`; the store's translation control asserts how `SESSION_UNBOUND` *maps*, not that `transaction`'s guard *fires*. A regression in either copy would not be caught by anything.

`transaction` also hands the operation a **raw client** rather than the narrowed surface `invocationTransaction` deliberately exposes. That is defensible for trusted store code, but it is a wider seam than `mint`, and it is exactly the kind of seam that later gets reused by something less careful.

**Not a blocker and nothing is withdrawn** — the guards are correct, just unproven in their second home.

## Two bounded limitations, recorded so they are not discovered later

**Approval state is still in memory under the PostgreSQL store.** `#approvals` and `#revokedApprovals` are maps, because the accepted migrations define no approval relation. You disclosed this. It fails closed — after a restart `getApproval` returns null and the replay is refused as `APPROVAL_NOT_FOUND` rather than being permitted — so it is a scope boundary rather than a hole. **Session authority is durable; approval state is not.**

**The repeat-safety mutation defends the reported-count half only.** It falsifies `second=0 third=0`; the `terminal_stable=true` half stays live but is not itself mutated. That half is separately evidenced by F58's managed-scheduler run, where the tombstone timestamp held across 18 invocations. Named rather than folded.

## C17 is not being closed here, and that is deliberate

C17 reads: *delegation derived from resolved authority, never caller-asserted; durable form satisfies constraint C6 before first durable delegation.* Both clauses now appear satisfied — derivation is durable and ignores the caller-asserted id, and C6's five requirements all hold with requirement 2 closed in F58.

**Closing a gate is reserved for DeVere, so the evidence is being presented rather than the gate being closed.** Two things also argue for waiting: the default store is still `InMemorySetupSessionStore`, and threat-model row 3.16 still reads "Model C, in-memory today", carried under F18.
