## The mechanism

The blocker is precise: `project_memberships` has forced RLS whose only policy is `tenant_isolation`, `USING (tenant_id = current_setting('app.tenant_id'))`. The mint function runs as `engram_migrator`, which is **not** `BYPASSRLS`, so the membership lookup returns nothing unless the caller already supplied the tenant.

**The load-bearing fact:** `tenant_isolation` is **PERMISSIVE**, and `project_memberships` has **zero RESTRICTIVE policies**. I verified both in the catalog. Permissive policies are OR-ed, so a second permissive `SELECT` policy adds a lookup path **without weakening the existing one**, and forced RLS stays on.

### 1. The membership policy

```sql
CREATE POLICY membership_principal_self ON project_memberships
  FOR SELECT
  USING (principal_id = nullif(current_setting('app.principal_id', true), '')::uuid);
```

- **Owner:** `engram_migrator`, the table owner, applied by the migration.
- **Command:** `SELECT` only. It grants no write path.
- **Row predicate:** `principal_id = <authenticated principal>`. It exposes **only the authenticated principal's own membership rows** and nothing about any other principal, any other tenant, or the size of either. Verified live: as `engram_app` with the principal set and the tenant unset, `project_memberships` returns **1 row, of which 0 are foreign-principal rows**.
- **Forced RLS without `BYPASSRLS`:** satisfied by construction. No role gains `BYPASSRLS`, `relforcerowsecurity` stays `true`, and the existing `tenant_isolation` policy is untouched. A session with `app.tenant_id` set keeps working exactly as before.
- **Caller-supplied tenant is excluded** because the predicate does not mention `app.tenant_id` at all.

### 2. The function change

`SECURITY DEFINER`, owner `engram_migrator`, `SET search_path = public`, all unchanged. Replace the membership lookup with:

```sql
SELECT tenant_id, project_id INTO t, p
  FROM project_memberships
 WHERE principal_id = principal
 ORDER BY tenant_id, project_id
 LIMIT 1;
IF t IS NULL THEN
  RAISE EXCEPTION 'TENANT_PROJECT_REFUSED' USING ERRCODE = '42501';
END IF;
PERFORM set_config('app.tenant_id', t::text, true);
```

Three points. The lookup keys on `principal` only, so **the caller's tenant is never read**. `ORDER BY` makes the choice deterministic rather than whatever `LIMIT 1` happens to return, which matters once a principal holds more than one membership. And `set_config(..., true)` is **transaction-local**, setting the context from the **derived** value so the existing `custody_write`, `reference_write` and `audit_write` policies are satisfied by a tenant the database derived, not one the caller asserted.

I applied both changes to a clean database at `0007` and ran:

|---|---|
| mint with `app.tenant_id` **never set** | **mints**, stored tenant `10000000-…-0001` |
| caller supplies a **foreign** `app.tenant_id` = `20000000-…-0002` | **mints under the derived tenant** `10000000-…-0001`; the supplied value is not obeyed |

That third and fourth line are the guard-removal discrimination: the policy is the guard, and removing it reinstates the exact failure that has blocked D1E.
