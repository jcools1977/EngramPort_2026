## Defect 3: the caller-asserted control cannot fail as written

The module never reads `request.principalId`, so there is no guard for the assertion to detect, and the assertion runs against a fake pool. It is a control whose name claims more than its body tests.

It **is** discriminable, and I proved it live. With `[session.principalId]` mutated to `[request.principalId ?? session.principalId]`, `minted_by_principal_id` becomes the caller-asserted principal.

**The choice of the caller-asserted principal decides whether the test means anything.** With a principal holding no authority, the mutated adapter is refused by the database with `42501` and the test passes for the wrong reason: the database refusing, not the adapter binding. I hit exactly that on the first attempt. Use a second principal that **could** legitimately mint, so the differential lands on `minted_by_principal_id` rather than on a refusal.

## Defect 4: items 7 and 8 are mutually masking, and my handoff was wrong to ask for both independently

Measured live, on the committed module:

|---|---|
| remove `DISCARD ALL` only | none |

Transaction-local scoping already prevents the leak, so removing the scrub alone changes nothing; the scrub already scrubs, so widening the scope alone changes nothing. **There is no independent mutation for either control.** Asking for two independent discriminations asked for something the mechanism cannot provide, and that is my error, not yours.

**Required instead:** one joint mutation that removes both, asserting the leak appears; the baseline asserting it does not; and a plain statement in the evidence that the two controls are defence in depth rather than two independent controls. Do not report them as two.

## Defect 5: a failing scrub permanently leaks the connection

```
} finally {
  await client.query("DISCARD ALL");
  client.release();
}
```

If the scrub throws, `release()` never runs and the connection is lost from the pool forever. Proven on a `max: 1` pool with the scrub made invalid: the first call returns `42601`, the second never obtains a connection and fails with `timeout exceeded when trying to connect`, and `pool.end()` then never resolves, so `close()` hangs.

The ordinary error path is sound by contrast: a mint that fails in SQL rolls back, releases, and the next call proceeds. Fix the scrub only: wrap it in its own `try`/`catch` with `release()` in an inner `finally`. The `catch` block's unguarded `await client.query("ROLLBACK")` has the same shape and should also be wrapped, so a failing rollback cannot replace the original error.

## Defect 6: nothing asserts the connection role

Item 3 required connecting as `engram_maintenance`. `connectionString` is caller-supplied and unchecked, so a superuser string would bypass RLS silently and no control would notice. Assert the role on checkout and refuse otherwise with a named code.
