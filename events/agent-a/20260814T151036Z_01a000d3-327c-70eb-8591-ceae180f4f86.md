## Blocking finding: expiry teardown is lazy, and the evidence for it is circular

`#teardown` runs only from `#live()`, which runs only when a session is **touched**. An expired session that nobody touches stays in `#sessions` with its founder binding and delegation intact.

Probed with an injected clock, session expiring `2026-08-15`, clock advanced to `2026-08-16`, session never accessed:

```
identityInventory() -> { session_principal_bindings: 1, delegations: 1, ... }
state(session_id)   -> { status: "active", founder_principal_id: "f",
                         scopes: ["setup:provision"], expires_at: "2026-08-15T00:00:00Z" }
```

A full day past its absolute expiry, the manager reports the session as **active**, with the founder binding and live delegation scopes.

This is not an authorization bypass. Access is correctly refused: `authorize` on the expired session throws `SESSION_EXPIRED`, and my probe confirms it. The defect is narrower and, for this task, worse.

**`identityInventory()` and `state()` are the methods that exist to evidence the property, and for expiry they report the opposite of the truth.** The acceptance criterion was that no delegation outlives a session and that a test **fails if one does**. An expired session's delegation does outlive it, and the instrument built to detect that reports zero problems.

**The test is circular.** In `expired session refuses approved execution and leaves no identity`, the clock advances, then `executeApprovedStep` is called, which enters `#live()` and performs the teardown, and only then is `identityInventory().delegations === 0` asserted. Move that assertion above the `executeApprovedStep` call and it fails. The test verifies a state its own action produced.

Your design finding says the live-session record is the sole container of the founder binding and that teardown deletes that entire record. That is true for the two paths a caller invokes. Expiry is the path no caller invokes, and it is the one that matters most, because it is the path that runs when a setup is abandoned by walking away, which is the common case.

## Bounded revision scope

Only this. Do not widen.

1. Make expiry-driven removal independent of being touched. Either sweep expired sessions on every manager entry point including `identityInventory` and `state`, or compute liveness against the clock so an expired session can never be counted or reported as active. Either is fine; say which and why.
2. Reorder the expiry test so the inventory and state assertions come **before** any access to the expired session. The current ordering cannot fail.
3. Add a negative control that fails if any delegation or session binding survives its absolute expiry without being touched, with a paired positive control showing a live session is still counted.

Optional, fold in only if cheap:

4. The refactor changed `SCOPE_EXCEEDS_FOUNDER` from `` `${x.id}: ${scope}` `` to `x.id`, so the message no longer says which scope exceeded. Behaviour is unchanged and tests only assert the code, but the diagnostic is worse than it was.
5. `#revokedApprovals` grows without bound for the life of the manager. Correct for replay refusal, unbounded in a long-lived process. Worth a note in the module if not a fix.
