## Blocking finding: `engram_app` can execute the SECURITY DEFINER bootstrap

`CREATE FUNCTION` grants `EXECUTE` to `PUBLIC` by default in PostgreSQL, and nothing revokes it. The migration revokes the **tables** and grants `EXECUTE` to `engram_maintenance`, but never revokes the default `PUBLIC` grant on the two functions.

Read from the live catalog, `proacl` is `=X/engram_migrator engram_migrator=X/engram_migrator engram_maintenance=X/engram_migrator`. The leading `=X/` **is** the PUBLIC grant. `has_function_privilege('engram_app', ...)` returns **true** for both functions.

I then used it:

- `engram_app` reading `founder_authorities` directly: **`permission denied for table founder_authorities`**. The table revoke works.
- `engram_app` reading the same rows through `resolve_founder_authority`: **returned `principal_id` and `scopes`**. Information disclosure straight through the revoke.
- `engram_app` calling `bootstrap_workspace`: **succeeded**, creating tenant, project, principal, and an **`owner` membership**.

The table-level `REVOKE` is defeated by the very functions it was meant to protect, because `SECURITY DEFINER` runs as `engram_migrator` and table privileges no longer apply. The least-privileged application role, which B1 deliberately confined to `SELECT` on ten tables and `INSERT` on two with no ownership and no `CREATE`, can mint itself an owner membership through one function call.

This is the exact class of escalation the B1 and W1-2 authority model exists to prevent, and it sits in the function whose whole purpose is to be the trusted authority boundary.

**Fix:** `REVOKE EXECUTE ON FUNCTION resolve_founder_authority(uuid), bootstrap_workspace(uuid, uuid, uuid, text, text) FROM PUBLIC;` before the `GRANT` to `engram_maintenance`. Then add the control property 8 asks for: `engram_app` calling each function is refused, with a paired positive control showing `engram_maintenance` still succeeds. Audit any future `SECURITY DEFINER` function the same way, since the default grant makes this silent.
