## The four defects

**1. `CREATE EXTENSION vector` requires superuser.** The migration runs as `engram_migrator`, which is `NOSUPERUSER` by design under B1. Verified: `permission denied to create extension "vector" / Must be superuser`.

The migration body is otherwise sound and reaches `COMMIT` as superuser, so this is the only defect inside it. **Install extensions as the superuser** in `docker-entrypoint-initdb.d`, alongside `init-roles.sql`, which already runs there with superuser rights. That also matches managed-Postgres reality, where the platform owns extensions rather than an application migration. **Do not grant the migrator superuser**; that reopens B1 and is the wrong fix. Keep `CREATE EXTENSION IF NOT EXISTS` in the migration so it remains a no-op and the migration stays self-describing.

**2. `deploy/seed.sql` violates the schema's own uniqueness constraint.** `principals` carries `UNIQUE NULLS NOT DISTINCT (tenant_id, external_issuer, external_subject)`. The seed inserts two tenant-A principals, `Principal A` and `Disabled A`, both leaving issuer and subject NULL, and under `NULLS NOT DISTINCT` those compare equal and collide. The multi-row `INSERT` is atomic, so zero principals land. `Disabled A` is required by the `missing delegation rejected` control, so give the rows distinct external identities rather than removing one.

**3. The forced-RLS assertion has never been capable of passing.** `tests/isolation/rls.sql` uses `NOT (rowsecurity AND forcerowsecurity)` against `pg_tables`, and **`pg_tables` has no `forcerowsecurity` column**. Forced RLS is `relforcerowsecurity` on `pg_class`. The assertion errors rather than evaluating.

Treat this as the most serious of the four. The entire forced-RLS claim, which B1 and the W1-2 threat model both lean on, rests on a check that has never run. Fix the query and then **prove it can fail**: assert it rejects a table with RLS enabled but not forced.

**4. The migration-owner immutability control gets the wrong error.** `tests/failure/constraints.sql` expects SQLSTATE `55000` "events is append-only" and receives `42501` "permission denied for table events". After B1 narrowed grants, the privilege check fires before the trigger, so a control written to prove *the trigger and not merely a grant* now proves the opposite.

Decide deliberately and say which you chose: either grant the migration owner the privilege needed to reach the trigger, so the control tests what its name claims, or rename the control and add a separate one that genuinely reaches the trigger. **Do not leave a control whose name misdescribes what it proves.** This is the same defect class I flagged for the application-role control during B1 review.
