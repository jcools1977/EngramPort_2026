## The KMS boundary is available and its shape is verified

Recorded as **C7**. I verified this by execution rather than assuming it, and the specifics matter because the first two candidate probes produced false negatives.

**Use a non-production KMS emulator.** `hashicorp/vault:1.17` in dev mode satisfies section 10's "isolated non-production KMS/HSM account or emulator". Verified on the shared host:

- non-exportable `rsa-2048` transit key signs a known input, so the boundary is live;
- export refused with the specific error `private key material is not exportable`;
- **the refusal discriminates**: an `exportable:true` key at the same endpoint returns real PEM private key bytes;
- a policy-scoped token signs its own synthetic key and is **denied** on sign, read and export of a production-named key path, satisfying section 10's requirement that the authorization be structurally unable to reach a real key.

**SoftHSM2 was evaluated and rejected.** It initialises and signs, but `pkcs11-tool --read-object --type privkey` answers `sorry, reading private keys not (yet) supported`. That is a tool limitation, not a token refusal, so export-denied obtained that way proves nothing. Proving B2 on PKCS#11 needs a native binding; Vault transit proves the same property over HTTP with no new dependency. **If you prefer a different boundary, argue for it and prove the same discrimination property before relying on it.**

**Do not substitute an in-memory signer or an ordinary application key.** A signer the application can read defeats B1 by construction, and a harness built on one cannot demonstrate confinement. If the emulator is unreachable in your environment, stop and report it; do not proceed with a substitute.

## The F17 evidence standard, carried forward

This is why W1-6a was sequenced first, and it now applies to everything W1-7 claims.

1. **Negative tests alone do not demonstrate a guard.** Supplying a failing input and asserting refusal restates the negative control. It does not show the guard caused the refusal.
2. **Every claimed security control needs genuine discrimination**: remove or disable that control's specific guard, or inject the specific fault, and demonstrate the previously refused case is then **accepted**, or that the vulnerable variant is **detected**. Then restore.
3. **Where a control cannot be isolated, state it per control with the reason**, and do not count it as demonstrated. Nine of W1-6a's twenty-eight ended here with sound reasons. That is an acceptable outcome; a false claim of isolation is not.
4. **Do not claim a mutation count that was not observed.** Report the number you ran. I will reproduce them independently.
5. **Prove the baseline before any claim built on it.** Both false negatives in my own KMS probing came from asserting a refusal while the underlying thing was broken. A refusal from a dead component is not a refusal.

Section 10 says this in its own words: "each check above must be demonstrated to fail when its control is removed", and "a sink that has never been observed dirty is a sink whose observer is unproven".
