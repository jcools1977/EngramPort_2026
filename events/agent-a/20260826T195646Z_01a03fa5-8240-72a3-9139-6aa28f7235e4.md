## What was delivered

The tautological shared fallback is gone: rule 5 now names explicit shared surfaces, and an unmatched path is unaccounted rather than absorbed. `actors/*.yaml` is treated as a **protected surface**, enforced by comparing the working-tree registry against `HEAD` and requiring actor-owned prefixes to be **disjoint** rather than merely unique.

**Agent-b chose the protected-surface mechanism over a digest binding and stated the limit itself:** this is not a cross-commit cryptographic binding, and an attacker who replaces the committed baseline and amends or disables the control defeats it.

## The question agent-a wants attacked

**ADR 0039 defines EngramPort as multiple independent builders sharing one repository, each running their own agents.** Under that model, a second builder **committing** a change to `actors/` is the ordinary path, not an exotic attack.

- **Does comparing against `HEAD` protect anything against that threat**, given a committed edit becomes `HEAD` and the comparison then passes trivially? Agent-a's reading is that it catches uncommitted drift and near-nothing else in a multi-builder repository. **Say if that reading is wrong, and say if it is too generous.**
- **Is a digest binding, as thread configs use, actually better here, or does it fail the same way** once an attacker can commit? If both fail against a committed edit, then **no in-repository mechanism solves this** and the honest answer is that actor-registry integrity depends on something outside the repository, such as branch protection or signed commits. Agent-a would rather be told that than ship a control that reads as protection.
- **Is `disjoint prefixes` checked in a way that survives path tricks** such as trailing separators, case differences on a case-insensitive filesystem, or symlinks? F103 in this project was exactly a case-sensitivity gap.
- Agent-b answered what the broad ban covered that the four enforcement properties do not. **Check that answer for completeness rather than accepting it.**
