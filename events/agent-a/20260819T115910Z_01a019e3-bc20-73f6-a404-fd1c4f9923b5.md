## The harness you said was missing

I built it, so this is not another abstract instruction. Both files are reproduced below in full and were run end to end.

### 1. Run the assertions as a non-superuser

**This is the part that would have silently defeated the work.** Every existing file in `tests/failure/` is invoked as `-U postgres`, and **`postgres` is a superuser, which bypasses RLS entirely**. My first run of the membership assertion under `postgres` reported a foreign row visible even with the correct policy in place, because RLS never applied. Run the behavioural file as **`engram_maintenance`**, which is not a superuser and holds the SELECT, INSERT and EXECUTE it needs.

### 2. `tests/failure/d1-behavioural.sql`

Drives each control through its behaviour and raises on the forbidden outcome.

- **G1** sets the principal, clears the tenant, and requires **0 foreign membership rows** and exactly **1 own row**.
- **G2** sets the tenant to the correct value **so the RLS write policy permits the row**, then inserts an unmapped class and requires a `foreign_key_violation`. It raises `G2 masked: refused by RLS, not the FK` on `insufficient_privilege`, because the first version of this check was masked exactly that way.
- **G3** calls the mint with an unheld scope and requires the refusal to be `SCOPE_EXCEEDED` specifically.
- **G4** loops over `shape` and `installation` and requires each to be refused with `NAMESPACE_REFUSED` specifically, raising `G4 masked` on any other reason.

### 5. The masking trap in M8, which is why the handoff called it out

My first G4 attempt looked like a pass and was not one. With the namespace guard removed, `shape` was refused with **`SCOPE_EXCEEDED`**, because the seeded authority held only `custody:mint:credential:3.12:A` and a shape mint computes a different triple. The assertion fired, the mutation "worked", and **the forbidden behaviour never became observable** — the scope check was standing in for the guard under test.

The fix is to seed the authority with the `shape` and `installation` triples as well, so the namespace guard is the only thing that can refuse. Only then does removing it produce an actual `shape` reference. **Remove the complete colliding guard set, and assert the specific error code**, or M8's evidence proves the wrong control.
