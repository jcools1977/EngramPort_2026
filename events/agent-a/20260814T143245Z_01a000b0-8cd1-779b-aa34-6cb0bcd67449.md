## Objective

Implement **W1-1: setup session, delegation, and teardown**, taken verbatim from the canonical register in `docs/plan/workspace-setup-wizard-tasks.md`.

This is the sole eligible implementation item. WIP remains one.

Phase W0 is complete: W0-1 compiles a plan, W0-2 dry runs it with no side effects. W1 is where the wizard acquires the authority to actually do things, which makes this the task where ADR 0012's central claim either holds or quietly stops being true.

## The claim this task must make real

ADR 0012 decision 2: **the wizard is a bounded session, never a standing actor.** It authenticates a human founder, acts strictly under that principal's delegation with scopes narrowed to setup and an absolute expiry, holds no authority of its own, retains no credential after the session ends, and has its delegation revoked at completion or abandonment.

If an implementation ends up with any identity that outlives a session, the ADR no longer describes what was built. That is the property to encode structurally, in the way W0-2 made side effects impossible by not importing the capability, rather than by remembering not to.

## Scope

1. **Session lifecycle.** Start, active, completed, abandoned, expired. A session binds to an authenticated founder principal and carries scopes narrowed to setup plus an absolute `expires_at`.
2. **Founder authentication behind an interface.** OIDC is stubbed. Define the interface; do not implement a provider. The stub returns a principal identity and nothing more.
3. **Delegation.** Session scopes are derived from the founder's, never exceeding them, and never outliving the session or the founder. Reuse the ceiling logic from W0-1 rather than writing a second one; if its shape does not fit, say so instead of duplicating it.
4. **Teardown.** Completion or abandonment revokes the delegation and clears any held credential. After teardown the session can authorize nothing.
5. **Approval binding, minimal.** A step executes only under the session that approved it, and only while that session is live. This is the narrow slice of approval needed to prove the session boundary; grouped approval and per-step diffs are **not** in scope here.

Out of scope, and do not build: grouped approval with per-step parameter diffs, the F2 and F7 digest work, the GitHub connector, provisioning, any real execution, the W1-2 threat model which is mine, and anything in Port Watch, Re:PORT, or onboarding. Do not touch `migrations/`.

## Tests and acceptance criteria

**Positive**

1. A session binds to a founder principal with narrowed scopes and an absolute expiry.
2. A step approved and executed within a live session succeeds.
3. Teardown at completion revokes delegation and leaves no credential.

**Negative**, each asserting a specific named error, each with a paired positive control

4. **No standing identity.** A test asserts that no principal, actor, delegation, or credential outlives a session, and fails if one does. This is the headline control and it should be structural: prefer a design where a post-teardown authorization attempt cannot find an identity to use, over one that checks a flag.
5. An expired session cannot execute an approved step.
6. A revoked or torn-down session cannot execute an approved step.
7. A step approved under session A cannot execute under session B.
8. An approval replayed after teardown is refused.
9. A session cannot grant a scope the founder does not hold, and cannot outlive the founder. Reuse W0-1's ceiling; a divergent second implementation is itself a finding.
10. An abandoned session leaves no partial authority: nothing is granted, and nothing is left revocable-but-unrevoked.

**Additional**

11. Deterministic state machine: the same sequence of events yields the same session state, testable without timing. Expiry takes an injected clock rather than reading one, following W0-2's precedent that time is an explicit input or not an input at all.
12. Runs from a clean checkout with one documented command, Node only, no new dependency, no network, no database. State the Node version.
13. All existing suites still pass: `setup:test`, `dry-run:test`, `watch:test`, `welcome:test`, `db:static-test`, `proof`.
14. No secret in any fixture. Stubbed credentials are clearly marked fixture-only.
