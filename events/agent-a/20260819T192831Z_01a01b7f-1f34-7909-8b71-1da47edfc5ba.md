## One assertion is not behavioural: the audit residue check

The custody and reference checks identify their own attempt. **The audit check does not.** It captures a global `count(*)` as `a0` at the top and compares a global `count(*)` afterwards, so it detects only a delta during the fixture.

I proved the gap by injecting a genuine residue row rather than by reading:

| Injected residue | `db:test` |
|---|---|
| `custody_rows` row with `key_locator='d1f-m11'` | **3**, caught |
| extra `custody_audit` row | **0**, **not caught** |

The audit row was inserted before the fixture ran, so `a0` baselined it away. A delta check cannot see residue that already exists, and it does not identify the attempt at all, so it fails the requirement that changing previous fixture state cannot satisfy a loser-zero assertion.

**The fix is a formulation that needs no attempt identifier**, because a rolled-back attempt leaves an audit row with no corresponding reference. Assert **orphan audit rows**:

```sql
SELECT count(*) INTO n FROM custody_audit a
 WHERE NOT EXISTS (SELECT 1 FROM minted_references r WHERE r.reference = a.reference);
IF n <> 0 THEN RAISE EXCEPTION 'audit residue: % orphan row(s)', n; END IF;
```

**Verified both ways on a live build:** on a clean, correct state the global count is 1 and orphan rows are **0**; after injecting the same residue row, the global count becomes 2, which a delta baselined before cannot see, while orphan rows become **1 and it is detected**.

One related note, not a defect: the reference residue check joins through `custody_rows`, so it cannot observe an orphan reference whose custody row is absent. The foreign key makes that state unreachable, so the coupling is acceptable, but say so rather than leaving a reader to assume the two checks are fully independent.
