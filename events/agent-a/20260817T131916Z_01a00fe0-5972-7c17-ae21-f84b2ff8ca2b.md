## Objective

Implement canonical **Re:PORT R2: deterministic evidence assembly and the unchanged-state gate**, from `docs/plan/report-plan.md`. Its canonical scope is unchanged: assemble an evidence set from an authorized source, compute an `as_of_seq`, and decide whether anything changed.

This is the sole eligible implementation item. WIP remains one.

## Why this is the property that matters

R1 established that an unauthorized record aborts the operation. R2 establishes the boundary one layer out: **a party who cannot change authorized state cannot cause a model to run.** That is the same reasoning Port Watch's zero-invocation guarantee rests on, and it is why control 5 below asserts exactly zero rather than a low count.

The dangerous version of this task is one that produces a wake decision that is *usually* right. Every control here is written so a merely-usual implementation fails.

## Scope

1. **Assemble evidence only through the R1 authorized-source interface.** No second retrieval path, no raw candidate arrays. R1's fail-closed returned-record assertion and generated-output exclusion are preserved exactly and must be shown still to hold under R2.

2. **Deterministic ordering and deterministic `as_of_seq`.** Identical authorized state yields an identical evidence set, in identical order, with an identical `as_of_seq`, across runs and processes. State how `as_of_seq` is derived and why that derivation is stable.

3. **The change decision.** A newly authorized event changes **both** the evidence set and `as_of_seq`. An unauthorized event changes **neither**.

4. **Reuse the Port Watch delivery-decision core.** Do not write a second unchanged-state or wake-decision implementation inside Re:PORT. If the existing core does not fit, say so in your reply and propose the smallest change to it rather than forking it. Two implementations of "has anything changed" is the defect this instruction exists to prevent, and it is exactly the shape of duplication the Port family document forbids.

5. **No datastore-level authorization claim.** R2 verifies its supplied source exactly as R1 does. Datastore-level authorization-before-retrieval remains R3 and is blocked by C1. Do not narrow or widen that boundary statement.

### Out of scope, do not build

Generation, prompting, rendering, any view, publication, R3 retrieval, storage, webhooks. No network, database, provider, model, credential, publishing, or external side effect of any kind. Nothing in the wizard, onboarding, or the parked records.

## Controls

**Positive**

1. Identical authorized state yields a byte-identical evidence set and identical `as_of_seq` across repeated runs.
2. The same holds across processes, proving the derivation is a pure function of authorized content rather than of run order or memory identity.
3. A newly authorized event changes the evidence set **and** `as_of_seq`, and the decision is to wake.
4. R1's controls still pass unchanged under R2's assembly path.

**Negative**, each asserting the specific outcome

5. **Unchanged authorized state causes exactly zero generator invocations.** Assert **zero** across many repetitions, using a recording generator stub that counts. A test asserting "few" does not prove this.
6. **Unauthorized-only change causes exactly zero generator invocations**, and changes neither the evidence set nor `as_of_seq`. This is the control that distinguishes R2 from a naive diff over everything the store holds.
7. A source leaking an unauthorized record still aborts the whole operation, with R1's error, rather than being silently excluded from the change decision.
8. A `report.generated` record still cannot enter the evidence set, so a report can never cause the next report.
9. Ordering is stable when the source returns the same records in a different order.
10. `as_of_seq` does not advance on an unauthorized event even when that event's sequence is higher than every authorized one. **This is the sharpest control**: the naive implementation takes the maximum sequence it can see, which leaks the existence of restricted activity through a monotonic counter and triggers generation.

**Discrimination**

11. Every discriminating control must be shown to **fail** against a deliberately naive implementation you write for the purpose: one that diffs over all visible records and takes the maximum sequence. Report which controls fail against it and how. A control never observed failing is not a control.

**Regression**

12. R2 tests plus `report:test`, `proof`, `welcome:test`, `watch:test`, and `lint` all pass.

**Additional**

13. Node only, deterministic fixtures, no new dependency. State the Node version.
14. Every negative has a paired positive control, and both are reported.
15. No secret in any fixture.
