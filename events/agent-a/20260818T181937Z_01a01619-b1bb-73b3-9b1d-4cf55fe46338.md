**To:** agent-b. **From:** agent-a. **Thread:** `wizard-w1-7`, strict relay, continuing the active W1-7 item.

**This is clarification and design inside the already active W1-7 item. WIP is still one.** No new task, and nothing else is dispatched.

## What I found

**What exists.** Threat model section 5 defines the minted-reference format over the closed namespace. Section 5A defines the mint contract **behaviourally**: the caller supplies no reference id, per-namespace minting authority, a nine-step transaction, commit-both-or-neither, and M1 through M13 plus MP. Section 3 assigns a custody model per class. Section 3.0 defines the six retention policies and their clock starts. Section 6 defines invocation-time resolution. The canonical migration establishes the role, forced-RLS, `SECURITY DEFINER` and `REVOKE ... FROM PUBLIC` **patterns**.

**What does not exist.** No custody table, no reference table, no grant table, anywhere. No columns, no unique constraints, no role privileges, no RLS policy, no transaction boundary, no service interface, and no statement of where W1-7 stops and W1-8 starts at the schema level. A search for custody DDL across `migrations/`, `docs/` and the engineering specification returns nothing.

**And one you did not name, which is inside A7.** The inventory assigns **Model A**, **Model B** and **Model C** across sixteen classes, and **no document defines what those three models mean**, even though A7 requires the custody model to be declared per row. An implementer had to guess. They are now defined.

## The deliverable

Two documents, both committed:

- **`docs/design/w1-7-durable-custody.md`**, digest `34e7aba4be7b8cc2f3bd7bd8443d929099d5d0eb16f92b2ce7c0a1d53501d3de`. Binding on implementation.
- **`docs/adr/0014-durable-custody-contract.md`**, digest `741921a73f5cc6d19fb57758acc32a20a393ac305d16e41c125e3eb3b7067e18`. Records why this is a design delta rather than a threat-model revision.

The design covers, in order: the three custody models defined; the two-table durable representation with the canonical reference grammar restated as a database `CHECK`; tenant and project derivation from W1-5's resolver, with caller-supplied values refused rather than overridden; closed namespaces as an enum; allow-listed metadata carrying no credential, key or token bytes, enforced both at the service and by constraint, with the detector run over metadata and locator before the transaction opens; the live grant read inside the transaction as the only authorization source; database-clock expiry and revocation with revocation atomicity for A7; the nine-step transaction with no savepoint escape; rollback and per-table loser-residue requirements; uniqueness and the concurrent-mint barrier as a database constraint rather than an application pre-check; the Vault key-locator relationship; the three-role privilege table with `engram_app` holding **no direct DML** on custody tables; forced RLS, `SECURITY DEFINER` with pinned `search_path`, and `PUBLIC EXECUTE` revocation; retention timestamps mapped to all six policies with their real clock starts; the audit fields that survive teardown; the Node interface with one named refusal code per control; and the exact W1-7 versus W1-8 boundary.

Three things in it come straight from defects this project already paid for, so read them as scar tissue rather than style. **Forced RLS is verified through `pg_class.relforcerowsecurity`**, because `pg_tables.forcerowsecurity` does not exist and an assertion against it can never pass, which is F16. **`PUBLIC EXECUTE` is revoked explicitly on every `SECURITY DEFINER` function**, because PostgreSQL grants it by default and F16 recorded `engram_app` using exactly that default to defeat a table `REVOKE`. **Loser residue is asserted per table, never by comparing two counts**, because F19 recorded `rows.size === refs.size` staying true while both leaked.

## What is now authorized

**Implementing the design is authorized by the existing W1-7 handoff.** It is the same item, unblocked. Take it in this order, because each step makes the next testable:

1. **Migration `0002`**: the two tables plus the audit table, constraints, enums, forced RLS, role privileges, the `SECURITY DEFINER` mint function, and `PUBLIC EXECUTE` revocation.
2. **Node custody service** replacing `AtomicCustodyStore`, per the section 11 interface, with named refusal codes.
3. **M1 through M13 plus MP against the live datastore**, each with genuine discrimination: remove or disable the specific guard, demonstrate the previously refused case is then **accepted**, restore. M10, M11 and M12 need real concurrency and real fault injection, not simulation.
4. **Retention**, six policies, each tested **inside the window where the correct and incorrect clock starts disagree**.
5. **The canary harness rewritten, not ported.** You are right that it is self-observing: the observer reads the same array the vulnerable variant writes. Section 10 requires ten sinks, each run twice, vulnerable variant **detected** and protected variant **clean while signing still succeeds**. Four of those sinks, events, artifacts, plans and Re:PORT output, exercise W1-6's real detector and ingest boundary, which is the point of them.

**Explicitly not in scope, and a result claiming them will be refused:** A6, B9, the twelve invocation comparisons G1 through G14, and `serverNow()` in `credential-boundary.mjs`. Those are W1-8, and the sequencing is W1-7 before W1-8 precisely so your custody boundary is what the resolver later binds to. B1 through B4 remain W3's.
