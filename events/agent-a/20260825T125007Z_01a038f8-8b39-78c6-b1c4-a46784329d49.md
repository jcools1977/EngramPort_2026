# Objective: what "authorize OIDC" concretely costs, as a costed reading

DeVere holds this decision. **Reading only** — no implementation, no provider contacted, no credential, no network. `executed=` stays at **82**. The registry slice on `founder-tenancy-model` **takes precedence** if you are mid-flight there.

## The question

The synthetic verifier is built and mutation-defended. The remaining half of W1-1 criterion 1 is the **authentication fact**: that a real identity provider vouched for the founder. What does authorizing that concretely require, what does each option cost, and **what does each actually discharge?**

## The constraint that shapes every answer

The standing rule has been **synthetic principals, synthetic keys, local containers only — no real provider, founder, credential or production service**, and **no secrets on disk**: supplied at the moment of use, never written to the repository, the scratchpad, or any tracked or untracked file.

**Every option must be costed against that rule, not around it.** If an option requires a client secret to exist somewhere, say exactly where it lives and who holds it.

## A trap worth naming before you start

Supabase is already authorized under ADR 0022 and has an authentication product, so it looks like the cheap answer. **It is not obviously in scope.** ADR 0022 says Supabase's *"only job is the C6 requirement 2 evidence"* and *"nothing else moves there"*. **Using Supabase Auth would exceed that authorization rather than fall under it**, and would need DeVere to widen ADR 0022 explicitly. Cost it as a real option, but cost it honestly, including that widening.

## For each option, return

Options to cost, plus any you think are missing:

- **A. A real hosted IdP** — name the plausible ones and treat them as a class where they behave alike, distinguishing only where cost or risk actually differs.
- **B. Supabase Auth**, with the ADR 0022 widening priced in.
- **C. A self-hosted OIDC provider in the local compose stack** — a genuine issuer with real keys, running locally, contacted over the network but never leaving the machine.
- **D. Defer** — keep the injected authenticator and the trusted-session caveat.

For each:

1. **What must exist that does not exist now**: client registration, redirect URIs, JWKS endpoint, discovery document, a tenant at a provider, a running service.
2. **What secret is required, where it lives, and who supplies it** — measured against "no secrets on disk". An option needing a persistent client secret on cockpit should say so plainly.
3. **What accepted surface changes**, with file and line.
4. **What it proves that the synthetic verifier does not.** This is the crux. The verifier already proves signature, rotation, algorithm confusion, issuer, audience, expiry and nonce against synthetic keys. **Name the specific fact each option adds**, and be skeptical: if an option adds only "a real hostname was contacted", say that.
5. **Whether it discharges the trusted-session caveat on A6, A7 and A8** — and if not, what still would.

## The question underneath

**Is the authentication fact provable at all without a real provider, or is it irreducibly an operational trust statement rather than a testable control?** If the honest answer is that no local option can establish it, say so. That answer would be worth more than a clever workaround, and it would let DeVere decide whether this gets authorized now or stays a documented precondition.

**Do not choose.** Give him costs and consequences.
