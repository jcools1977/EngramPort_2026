## Defect 1: the vulnerable half never touches a sink

All four vulnerable importers are a single `store.push(...)`:

```
events:        vulnerableStore.events.push({tenantId, body: canary})
artifacts:     vulnerableStore.artifacts.push({tenantId, registration:{content: canary}})
plans:         vulnerableStore.plans.push({tenantId, plan: setup(canary)})
report_output: vulnerableStore.report_output.push({tenantId, generated:{summary: canary}})
```

**No production symbol appears in any of them.** The observer then searches that same private array. **Measured**: with **both** `validateAppendInputs` and `detectCredential` broken in a copied tree, the vulnerable half still reports **4/4 dirty**. It is independent of every real path.

This is the defect the original harness had, in reduced form. The stores are now separate, which is a genuine improvement, but the vulnerable variant still observes its own bookkeeping. Section 10 is explicit about why this matters: *"A sink that has never been observed dirty is a sink whose observer is unproven."* The **real** sinks have never been observed dirty. The vulnerable run proves a string search works over an array, not that any observer can see a leak in the event log, an artifact registration, a compiled plan or a Re:PORT generation.

The dispatch asked for "an event body carrying the canary **with the detector disabled**" — meaning the canary travels the real path with the guard off, and the observer finds it where it actually landed. The artifacts case shows the shape clearly: the protected variant writes a real file and passes it through `validateAppendInputs`; the vulnerable variant writes no file at all.

**Required:** each vulnerable variant must route the canary through the **same production path** its protected twin uses, with the detector disabled for that variant only, and the observer must find it **where it actually landed** — the written event file, the artifact on disk, the compiled plan object, the generated Re:PORT output. The isolation requirement is unchanged and already enforced: vulnerable variants stay on the synthetic tenant and synthetic key, and must never reach the non-exportable-key path.

`D3_CANARY_OBSERVER` should then be re-pointed at the real observers, and its `forbidden` condition restated. Report the observed count only.

## Defect 2: an accepted CLI behaviour changed, and the result says it did not

The result states "The CLI factoring preserves its accepted behavior." It does not, at one edge. The old code guarded the loop with `if (options.artifacts)`; the new code passes `options.artifacts?.split(",") ?? []`, and `"".split(",")` is `[""]`, so an empty flag now resolves the repository root as a file path.

**Measured on the same command, same body, both trees:**

| Tree | `engram append … --artifacts ""` |
|---|---|
| before `a870be3` | appends the event normally |
| after `a870be3` | **fails** with `EISDIR: illegal operation on a directory, read` |

The extraction itself is good and the shared validator is the right shape — the detector, the message text and the artifact loop are otherwise identical, and adding `error.code` is an improvement. **Fix:** filter empty entries, `options.artifacts ? options.artifacts.split(",") : []`, and add a regression asserting an empty `--artifacts` still appends.
