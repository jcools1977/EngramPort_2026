## Defect 1: the protected core-dump variant never crashes, so its dump was never produced

The protected variant is `perl -e '$held="synthetic-safe"; exit 0'`. It exits zero. **Measured on a kept run**: `vulnerable-operations/core` holds the 667,648-byte dump; `protected-operations/core` is an **empty directory**. `landingContains` returns false on `ENOENT`, so the sink reports clean because there is nothing to read.

Section 10's protected column says *"Forced crash **during signing** yields a dump with no canary"*, and the section's own preamble gives the reason: *"no core dump means no bytes to inspect."* **This is clean by absence, which is the precise failure section 10 was written to prevent.** The protected variant must crash too, produce a real dump, and be searched.

## Defect 2: five protected halves never receive the canary and never sign

For logs, process arguments, process environment, backups and error surfaces, the protected import calls the worker with **no material at all**. Read from the kept run:

```
operation.log     {"level":"trace","operation":"sign","material":"synthetic-safe", …}
environment.json  {"operation":"sign","environment":null, …}
error.json        {"message":"synthetic-safe","stack":"Error: synthetic-safe …"}
```

So the protected claim is not "the signing operation did not leak the canary" but "we did not hand the worker the canary." **That is tautological**, and it is the shape this project has refused repeatedly.

It compounds with the declared change to accepted `custody-service.mjs`: `clean` was widened from `refused===true` to `refused===true || protected===true`, so a protected import can now self-declare cleanliness. For the first four sinks `clean` still requires a real refusal by the real detector. For these five it requires only the import saying so.

**Also, no signing happens in the observed process.** `syntheticSignature` is a local `sha256` computed by the worker; the live Vault signature is taken separately in the parent. Section 10 says every protected observation happens *during a live signing operation*. **Required:** the protected variants must run the same operation carrying the same canary through the production path, and be clean because the material never reaches that sink — not because it was never supplied.

## Defect 3: the environment observer reads one variable

The worker records `environment: process.env.ENGRAM_CANARY_MATERIAL ?? null`. **Measured**: with the canary placed in `ENGRAM_SOMETHING_ELSE`, the landing records `environment:null` and the observer sees nothing. Section 10 says the observer reads `/proc/<pid>/environ`, meaning the whole environment. On macOS use `ps -E -o command` against the live pid, or have the worker serialise all of `process.env`. The `argv` observer is fine by contrast: it records the whole `process.argv`.
