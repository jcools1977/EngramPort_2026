# Objective: the founder tenancy model, as a reading with costs, not a decision

DeVere holds this decision. He has asked that you and I work it first, so what he receives is evidence and consequences rather than two opinions. **Claim nothing, choose nothing, change no file but your artifact and this reply.**

## The question

May one external identity — one verified `(issuer, subject)` — found more than one tenant? If it may, does it receive **one principal id across tenants**, or **distinct tenant-local principal ids**?

## What I found before writing this, which you should verify or refute

Two facts from `migrations/0001_canonical_core.sql`:

- `bootstrap_establishments.principal_id uuid PRIMARY KEY REFERENCES founder_authorities(principal_id)`, with `tenant_id` and `project_id` each separately `UNIQUE`. **On my reading this makes one-principal-one-tenant structural today**: a second `bootstrap_workspace` call for the same principal hits the primary key and raises `founder bootstrap already established`.
- `principals` carries `UNIQUE NULLS NOT DISTINCT (tenant_id, external_issuer, external_subject)`. **External identity is tenant-scoped**, so the same `(issuer, subject)` may already exist in many tenants as different principal rows with different ids.

**Verify both against source and say plainly if I am wrong.** The whole reading rests on them.

## The error I want you to check hardest, because it is mine

ADR 0026 specifies the binder registry as **"globally unique on `(issuer, subject)`"**. If that stands, one external identity resolves to exactly one principal id, and that principal can found exactly one tenant — so **ADR 0026 silently decided this question while claiming to defer it.** I believe I pre-committed to an answer without noticing.

**Check whether that reading is correct.** If it is, say so; the ADR needs correcting before the binder is built on it, and I would rather you find that than have it discovered after the registry exists.

## What to return

For each of the three options — **(A)** one global principal id founding many tenants, **(B)** distinct tenant-local principal ids per tenant, **(C)** one external identity founds exactly one tenant ever — give:

1. **Exactly what accepted surface must change**, with file and line. Tables, constraints, functions, controls. **Cost stated as evidence, not adjective.** I expect (B) to be nearly free and (A) to collide with an accepted primary key, but I want that measured rather than assumed.
2. **What happens when a founder returns** to create a second workspace: the concrete refusal or the concrete success, named.
3. **The revocation story.** Revoking a founder's authority in one tenant — does it revoke everywhere? Under which option is that answer surprising? This is the one I think matters most and is least visible.
4. **What an attacker gains** at each option if the binder registry is wrong or poisoned, since this registry becomes the root of trust for founder identity.
5. **Any option I have not listed**, including any that avoids the question rather than answering it.

## Explicitly out of scope

No implementation, no migration, no schema, no binder, no OIDC work. `executed=` stays at **82**. Nothing closes, and C17 stays held.

**Do not choose.** If one option is clearly better on evidence, say why and still leave the choice open — the tenancy model is DeVere's call about what EngramPort is, not ours about what is convenient to build.
