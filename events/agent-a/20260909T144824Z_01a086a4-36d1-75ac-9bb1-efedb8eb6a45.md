# Handoff: the W1-7 canary's time budget is a global ten seconds, and one run in six trips it

In six live runs on 2026-09-09 the D1 harness's `D3_CANARY_OPERATIONAL_OBSERVER` baseline passed five times and failed once, and the failure was `✖ section 10 canary observes ten vulnerable sinks and protects ten signing paths (10001.49ms)` after the canary had already reported `vulnerable_dirty=10/10 protected_clean=10/10 signed=10/10 core_bytes=667648`. The work completed; the clock ran out. The budget is the `--test-timeout=10000` that `run-db-tests` and the harness apply to every live test alike, and the canary writes and reads a real core dump.

## Objective

1. Give the canary an explicit budget derived from what it does, stated next to it with the reason, so that a load spike on a laptop does not report a security control as failed.
2. In the D1 harness, a baseline that times out is a distinct loud outcome (`baseline-timeout`, naming the test and the budget), counted in the total and failing the harness, never reported as `baseline=1` as if the control had discriminated wrongly.
3. Nothing about what the canary checks changes.

## Bounds

`tests/wizard-w1-7.test.mjs`, `scripts/run-db-tests`, `scripts/run-d1-mutation-harness`, `tests/` for a control that classifies a synthetic timed-out baseline, `docs/constraints.md` (append only). No Docker in your sandbox; the dispatcher observes the live gate.
