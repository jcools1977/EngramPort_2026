## What is now proven inside PostgreSQL, and what is not

**Proven, given a truthful `app.principal_id`:** tenant and project are derived and a caller-supplied tenant is never obeyed; the custody model is derived from the canonical inventory; scope is contained against held authority; namespaces are closed; the class mapping is enforced by foreign key; references are canonical; authority expiry and revocation are read in-transaction against the database clock; and the application role can neither write custody rows nor execute the mint.

**Not proven, and not provable in the database:** that `app.principal_id` is who they say they are. Probed directly:

- `engram_app` can set `app.principal_id` to another principal and see that principal's membership row, but **cannot execute the mint**: `permission denied for function`.
- **`engram_maintenance` can set `app.principal_id` to any principal and mint as them.** It minted for a second principal, storing that principal's tenant and `minted_by_principal_id`.
- The function takes **no caller principal parameter**, and the grant is looked up **by** the session principal, so there is no second value that could disagree and no cross-check to make.

## The decision: option A, recorded in ADR 0015

**D1's contract begins with a trusted, already-authenticated session principal. D2 owns binding the external authenticated identity to `app.principal_id` and to the privileged database session.**

**Why not B.** A datastore-verifiable session record does not close the gap it appears to close. Whatever role writes that record, `engram_maintenance` already holds full DML on every table in `public` from migration `0001`, so the role that can execute the mint can also forge the session row the mint would check. B moves the same unverifiable assumption one table deeper while presenting as a control, which is precisely the pattern this project keeps refusing.

**Why A is canonical rather than convenient.** Threat model row 3.16 already states the setup-session delegation authority is **Model C, in-memory today**, with gate C17 requiring the durable form to satisfy constraint C6 before the first durable delegation. The specification already treats session authority as application-held and its durable form as gated future work. A agrees with that; B would quietly contradict it.

**Consequences, binding:**

1. **M2 and M3 are accepted only under the explicitly recorded precondition** that the session principal is trusted and already authenticated. Any evidence citing them must state that precondition.
2. **Principal-session binding and its discrimination are assigned to D2**, owned rather than shared.
3. **A7 and A8 do not close until D2 proves the binding.** The custody boundary is sound given a truthful principal; "given a truthful principal" is not yet proven, and that is the specific reason they stay open.
