## Defect 1, blocking: the reference generator cannot satisfy its own CHECK

The function builds the reference from `to_hex(ms)` with no padding. Current epoch milliseconds are a 41-bit value, so `to_hex` returns **11 characters**, `substr(...,1,8)` takes eight and `substr(...,9)` leaves **three**. The second group must be four.

```
built   = epr:credential:1a016287-2ac-7b61-8736-489a98a23732
matches canonical grammar = false
```

So even with authorization satisfied, the insert into `minted_references` would fail its own `CHECK`. **Correction:** `lpad(to_hex(ms),12,'0')` before both `substr` calls. The Node version had `padStart(12,"0")`; the SQL port dropped it.

## Defect 2, blocking: the policies are SELECT-only, so the definer cannot insert

All three policies are `FOR SELECT`. Under forced RLS there is no permissive policy for `INSERT`, and the definer runs as `engram_migrator`, which is **not** `BYPASSRLS`. The live error:

```
new row violates row-level security policy for table "custody_rows"
```

**No mint can ever commit.** Correction: add `FOR INSERT` policies with a `WITH CHECK` that scopes to the derived tenant, so the write is permitted **and** still tenant-bound.

## Defect 3, blocking and a contract violation: tenant derivation is circular

`project_memberships` has forced RLS whose policy compares `tenant_id` to `current_setting('app.tenant_id')`. The definer's membership lookup therefore returns nothing unless **the caller has already set `app.tenant_id`**. With it unset, the mint fails `TENANT_PROJECT_REFUSED` even for a fully authorized principal; with it set, the lookup succeeds.

That inverts the design. §4 requires tenant and project to be **derived from the resolver, never supplied**, and §5A requires the caller to supply neither. As built, the caller must supply the tenant to derive the tenant, which is circular and makes M2 and M3 untestable: a caller who names a foreign tenant is the very thing those controls exist to refuse.

**Correction:** resolve membership by a path that does not depend on the caller's tenant GUC, for example a `SECURITY DEFINER` resolver function that reads membership by `principal_id` alone, and then **set** the tenant context from what it derived rather than trusting what arrived.

**I verified these three are necessary and sufficient.** In a scratch database I added `INSERT` policies and padded the hex, and a fully authorized mint then succeeded, returning `epr:credential:01a01629-50cb-7fac-8888-948534864029` with custody row, reference and audit row all present. Nothing else is broken.

## Defect 4: `metadata` is an unrestricted secret container

Design §3 requires allow-listed keys enforced **both** at the service and by a `CHECK` over `jsonb_object_keys`, precisely so a direct SQL writer cannot smuggle a field past the Node layer. No such constraint exists. Demonstrated live:

```

stored: {"pem": "-----BEGIN PRIVATE KEY-----", "stolen": "hvs.synthetic…"}
```

A Vault token and a PEM header now sit in a custody row. Add the `CHECK` restricting keys to `provider`, `installation_display_id`, `scopes`, `algorithm`, `key_version`, `rotation_generation`, `shape_id`, `notes`.

## Live mint controls: 0 of 14 demonstrated

Stated plainly because schema presence must not be read as evidence. **MP and M1 through M13 have no live demonstration**, since no mint can run. You did not claim otherwise, which is the right call.

Beyond the three blockers, these have no implementation yet and the next revision needs them before the controls are even expressible:

- **M5, revoked grant.** `founder_authorities` has only `principal_id`, `scopes`, `expires_at`. There is **no revocation column**, so a revoked grant cannot be represented, let alone refused. M4's expiry is checkable today; M5 is not.
- **M7, scope containment.** The function tests `'custody:mint' = ANY(scopes)` and nothing more. A requested scope exceeding the grant is neither compared nor refused.
- **M8, per-namespace minting authority.** Any principal holding `custody:mint` may mint **any** namespace, including `shape`. §5A restricts `shape` to the trusted registry path and `installation` to the installation path.
- **M13, class gate.** Not implemented.
- **M11 and M12, fault injection.** No injection points exist, so orphan resistance is unproven. When you add them, assert **per table** that `custody_rows`, `minted_references` and `custody_audit` are each zero. Do not compare two counts to each other; F19 records that equality holding while both leaked.
- **M10, concurrency.** `custody_single_active` is the right barrier and it discriminates, but a genuinely overlapping race has not been run.

Two smaller things while you are in the function. `retention_policy` is hard-coded to `'RET-AUDIT-400'` for every row regardless of class, and §10 maps the policy to the class; `granting_event_id` is declared and never populated. Also, the `EXCEPTION WHEN unique_violation` handler opens an implicit subtransaction: because it re-raises, no partial state survives, so it is structurally sound, but I could not demonstrate that live and am not counting it as proven.
