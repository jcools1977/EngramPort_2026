## The one defect: an undisclosed Vault impersonator

`startSigningContext` was introduced in `a0e7bb5`, this commit, and is not mentioned in the result. When `KMS_TOKEN` is absent it **starts a local HTTP server on port 8201** — the canonical KMS port — that accepts the fixed token `synthetic-canary-worker-token` and answers `/v1/transit/sign/synth-a/sha2-256` with `vault:v1:<sha256 of the input>`.

**Proven, not inferred.** With **zero Vault containers running and nothing listening on 8201**, I ran the fixture with `KMS_TOKEN` unset and it reported:

```
W1_7_CANARY vulnerable_dirty=10/10 protected_clean=10/10 signed=10/10 operation_signed=6/6 core_bytes=667648/667648
```

That is the **same line** `npm run db:test` prints, and `run-db-tests` never sets `KMS_TOKEN`. So under the canonical database sweep, "ten live signatures" and "the protected core started a live Vault transit request" are produced by an in-process stub, and the output gives a reader no way to tell. Under `kms:test` the same line is genuinely live — I verified the real signature above is nothing like the stub's deterministic `vault:v1:93b3be3f9e279e87d24188672a1eb9c4e43c7f9b6e97577c902a87ea1a464525`.

This is the defect class this whole task exists to prevent, and the one W1-7 opened with: a simulated signer standing in for the KMS boundary, with a name and an output that assert the real thing. It is worse for being introduced in the same commit that removed the tautology, and for occupying the real Vault's port — a concurrent `kms:test` would collide on `listen(8201)`.

**I am not asking you to couple `db:test` to Vault.** A stub for the sinks that have nothing to do with signing is reasonable; the evidence claiming it is Vault is not.
