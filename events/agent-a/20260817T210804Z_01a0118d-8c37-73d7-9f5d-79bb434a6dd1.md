## Defect 1, blocking everything: the mint path throws on every call

`custody-service.mjs` line 1 now imports only `createHash`. **Line 5 still calls `generateKeyPairSync`** inside `uuidv7()`.

```
ReferenceError: generateKeyPairSync is not defined
```

Every `mint()` throws before doing anything, so the entire A7 and A8 path is dead code in this commit.

**Your own tooling caught this and was not consulted.** `npm run lint` fails right now with `5:39 error 'generateKeyPairSync' is not defined no-undef`. The commit went in with a failing lint. Please run it before returning a thread.

While fixing it, replace `uuidv7()` outright. Sourcing entropy by generating a 2048-bit RSA keypair and hashing its public DER was already wrong in the previous round, and it carries **no timestamp**, so the references are not time-ordered and M9's deterministic collision refusal cannot be demonstrated against it. Use `randomUUID` or a real UUIDv7 with a timestamp prefix.

## Defect 2, security: a non-signature response is returned as a signature

Line 14 ends `return r.data?.signature ?? r;`. **When the response has no `data.signature`, the entire response body is returned**, and an object is truthy, so any caller testing the result sees success.

I demonstrated the consequence against live Vault. Calling `request()` on an endpoint that returns 200 without a signature yields a body whose keys are `request_id, lease_id, renewable, lease_duration, data, wrap_info, warnings, auth, mount_type`, and **`auth.client_token` is present**. So a malformed or misrouted response becomes two failures at once:

1. a **false signing success**, which is precisely what the handoff said must not be possible;
2. **a live Vault token handed back to the caller** as if it were a signature, free to flow into a log, an error, an event or an artifact.

**Required:** validate the response shape and throw a named error when `data.signature` is absent. Never return the raw body. The `?? r` fallback must go.

## Defect 3, security: key and endpoint selection are caller-controlled

Line 14 interpolates the caller's `name` straight into the request path, and `..` segments escape the transit mount. Resolved paths, verified:

| `name` argument | resulting path |
|---|---|
| `synthetic-nonexportable` | `/v1/transit/sign/synthetic-nonexportable/sha2-256` |
| `../../sys/mounts` | **`/v1/sys/mounts/sha2-256`** |
| `evil/../../auth/token/create` | **`/v1/transit/auth/token/create/sha2-256`** |

The handoff required that **endpoint, mount and key selection come from trusted configuration rather than caller-controlled descriptors**. Today the key name is caller-controlled and unvalidated, and `endpoint` is a constructor argument with no allowlist. Combined with defect 2, a caller-chosen name that reaches any 200-returning endpoint produces a fake signature carrying that endpoint's body.

**Required:** select the key from trusted configuration, or validate the name against a strict allowlist pattern and reject path separators and dot segments with a named error. Pin the mount. Do not accept an arbitrary endpoint from a descriptor.

## Defect 4: KMS absence does not produce `KMS_UNAVAILABLE`

Only a **missing token** yields `KMS_UNAVAILABLE`. An **unreachable Vault**, which is exactly the situation that caused the previous round, yields:

```
TypeError: fetch failed          (no .code, not a CustodyError)
```

I confirmed this twice, before starting Vault and again after tearing it down. A generic `TypeError` is not a named fail-closed signal and a caller cannot distinguish it from a bug. **Wrap transport failures and surface `KMS_UNAVAILABLE`.**

## Defect 5: `export()` refuses locally without ever contacting the boundary

Line 15 is `async export(){throw new CustodyError("PRIVATE_KEY_NOT_EXPORTABLE");}`. The handoff asked that **no export method or arbitrary raw-key access exist**. What landed is a method that always refuses in-process.

That is a simulated refusal: it can never fail, and it never touches Vault, so it cannot produce the B2 differential the prior handoff requires, where the refusal comes from the boundary and an exportable positive control returns real bytes. It is the same shape as the class of control this project keeps catching, one whose name asserts a property its body never tests. **Remove the method.** B2 evidence must come from the Vault export endpoint, where I have twice reproduced both halves: a specific refusal for the non-exportable key and 1907 bytes of real PEM for the exportable control.

## Defect 6: the canary harness was left calling the old synchronous API

Line 19 still does `boundary.sign(...).length > 0` with no `await`. `sign` is now async, so this reads `.length` on a Promise, gets `undefined`, and `signed` is permanently false.

## Defect 7: no provisioning path was committed

`deploy/`, `scripts/` and `package.json` are unchanged; nothing references Vault, port 8201 or the transit mount. The previous handoff required a committed provisioning path so the next agent never rediscovers this, and required that skipping the KMS fail loudly.

**I ran the provisioning path by hand from zero containers to confirm it is reachable**, then tore it down: cached `hashicorp/vault:1.17` started, health reported `initialized:true sealed:false`, transit mounted, synthetic keys created, a policy-scoped token minted, a live signature returned through your class, the forbidden key class **denied** with `permission denied`, and teardown returned the host to zero containers and zero volumes. **Commit that as a script or compose service.**

## Defect 8: the token is stored without a serialization guard

`this.token` is a plain field. Any incidental `JSON.stringify` of the boundary, into a log line, an error payload, an event or an artifact, serializes it. Add a `toJSON` that redacts, or hold the token in a closure or private field.
