# Handoff: F177, the durable cleanup control's `scheduled` observation races the alarm it is measuring

CI run 34597910043 on 4c0d000 (a commit that touched only README, changelog, and one event) went red with one line: `W1_1_OIDC_DURABLE_CLEANUP baseline=0 applied=t after=1 forbidden=f restored=0`. The mutant died, but the log did not carry the line the harness looks for. The run printed `W1_1_OIDC_DURABLE cleanup scheduled=false claimed=204/true alarm=true`; the harness expects `scheduled=true claimed=204/true alarm=true` for that mutant. The next two runs on the same harness content were green, and six local runs of the unmutated control on Node 22 all print `scheduled=true`.

Read `tests/workspace-oidc-durable.test.mjs`, the `cleanup` check. `scheduled` is `scheduled.alarmAt>scheduled.expiresAt && before.alarmAt>before.expiresAt`, where `before` is an inspect on a runtime whose expiry is 60 ms and `alarmAt` is `storage.getAlarm()` at inspect time. If the alarm fires (expiry plus `ALARM_GRACE_MS`) before that inspect runs, which a loaded CI runner with seven Miniflare processes can do, `getAlarm()` is null, `null > n` is false, and `scheduled` reads false. The control's observation depends on the scheduler, so a mutant can die for the wrong reason and the harness reports it, correctly, as a failure to discriminate. The code under test is not implicated.

Record this as F177 in `docs/constraints.md` in the register's form.

## Objective

1. Make the `scheduled` observation independent of when the alarm fires: read `alarmAt` and `expiresAt` in the same durable-object call as the record they describe, and take the `before` observation on a runtime whose expiry cannot elapse before the inspect returns (the first runtime already uses 1000 ms; the 60 ms runtime exists only so the manual `/__oidc/alarm` dispatch finds an expired record). If the alarm has already fired at inspect time, the control must say so as its own distinct outcome (`scheduled=fired-before-inspect`), never `false`.
2. Controls: reproduce the race deterministically on the old control by injecting a delay of `expiry + ALARM_GRACE_MS + margin` before the `before` inspect (a test-only environment variable read by the test, not by the worker) and show it prints `scheduled=false`; the new control under the same delay prints its distinct outcome and still passes or fails on the cleanup assertion alone. Then, on Node 22 (`/opt/homebrew/opt/node@22/bin`), run the unmutated control ten times and the `cleanup` mutant built from `make_w1_1_oidc_durable_variant` ten times; quote every printed line, all ten mutant runs carrying the harness's expected forbidden line. Update the harness's expected string for `cleanup` if the printed shape changes, and keep it exact.
3. Audit the other six durable checks for the same shape (an observation taken through `getAlarm()` on a short-expiry runtime) and fix any that have it, or state that none do with the line that shows it.

## Bounds

`tests/workspace-oidc-durable.test.mjs`, `scripts/run-d1-mutation-harness` (expected strings only), `docs/constraints.md`. No change under `worker/` or `packages/`. Docker is not needed for these controls. Commit as instructed.
