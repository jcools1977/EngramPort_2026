# Pre-flight: the verified builder subject

**F127 measured the problem.** A second builder ran the full path successfully, and also ran `createClient({ actor: "builder-one" })` and appended an event the verifier accepted as builder one's. `impersonation=accepted disposition_read=accepted disposition_write=accepted`. **Repository hosting controls gate push, not authorship.**

## PROPOSED DISPATCH (not yet sent)

**Objective: an accepted event proves which builder authored it.**

**Design: sign the event, not the commit.**

1. **Actor records carry a public key.** F113 recorded that `actors/*.yaml` names a slug, directories and no key.
2. **Events carry a signature over their canonical content**, verified against the claimed actor's key.
3. **The verifier refuses an event whose signature does not verify** under the actor named in `from`.

**Why not commit signing alone.** It binds the pusher, not the author; it breaks under rebase and cherry-pick; and it makes authorship a property of the transport rather than of the log. **`port-family.md` holds that the Port Log is truth, and truth that only survives inside one hosting arrangement is not portable.**

**The hard part, which must not be skipped: the key binding is itself repository content.** If builder two edits `actors/builder-one.yaml` to hold builder two's key, signatures verify and impersonation returns. **That is F108 recurring.** So the actor-to-key binding must be **signed by an enrollment authority** whose key is not itself rewritable by an ordinary builder, using the `SECURITY DEFINER` issuer and bootstrap operator role that already exist rather than a new mechanism.

**Migration.** 412 existing events are unsigned. **Signatures cannot be required retroactively**, so this needs a cutover like `schema_version`: historical events remain valid unsigned, new events after cutover must be signed, and the verifier must refuse an unsigned new event rather than treating the field as optional.

**Required evidence.**

- **Builder two attempts to author as builder one and is refused**, observed rather than read off a guard. This is the exact operation F127 recorded as accepted.
- **Registry tampering is detected**: swapping a key in an actor record fails verification.
- The repository's own 412 events verify unchanged.
- A discriminating mutation per property.

**Bounds.** Actor records, event envelope, verifier, and enrollment binding. No SDK surface change beyond what signing requires, no site copy, no hosted deployment. `executed=` moves from its observed value, which agent-b states.

## What to check

- **Does the authority-signed binding actually escape F108**, or does it just move the tamperable object one level up? If the authority key lives in the repository, agent-a has solved nothing.
