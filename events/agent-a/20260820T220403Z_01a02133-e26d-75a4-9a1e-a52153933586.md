## Two limitations, measured and recorded now

**1. The 400-day duration is a constant, not derived from the policy.** The function evaluates `evaluated - clock_start >= interval '400 days'` for every row, regardless of `row_policy`; the policy selects only the **clock start**. Measured: a `RET-GRANT-400` row with `clock_start` 150 days ago returns **not due**, and so would a `RET-OPS-90` row with the same clock start, which should be due. This is correct today only because all three covered policies happen to share one duration, so the policy-to-duration mapping is **entirely unexercised**. Section 3.0 defines six policies, and `RET-SESSION` at one day, `RET-OPS-90` at ninety and `RET-VERIFY-104` at one hundred and four would each be wrong under a constant. This is the next slice.

**2. An unsupported policy is indistinguishable from a missing row.** A row carrying `RET-OPS-90` raises the same `RETENTION_UNRESOLVED` as an unknown reference. Failing closed is right and the non-disclosure is deliberate, but an operator cannot tell a policy gap from a missing row. No production row is affected today, because the mint writes `RET-AUDIT-400`.
