## Objective

Close the highest-priority v0.1 review finding: **the application role can write the tables that authorize it.**

This is the sole eligible implementation item. WIP remains one.

## The finding

`migrations/0001_canonical_core.sql` grants `SELECT, INSERT ON ALL TABLES IN SCHEMA public TO engram_app`. That set includes `actor_delegations`, `project_memberships`, `actors`, and `principals`.

Within a single tenant, `engram_app` can therefore insert an `actor_delegations` row carrying `'*'` scope and then satisfy `validate_event_actor_delegation`, or insert a `project_memberships` row and satisfy the `project_member_read` policy. Forced RLS still confines this to one tenant, so it is not a cross-tenant leak. It does mean the delegation trigger and the membership read policy are both defeated by the role they exist to constrain, which removes their value as defense in depth.

This is ranked first of the three findings because `engram_app` is the role the append path actually runs as, and therefore the one an attacker reaches. The `TRUNCATE` gap requires `engram_maintenance`, which is more privileged and less exposed.

## Scope

Bounded. Only this finding.

1. Replace the blanket grant with explicit per-table grants. `engram_app` gets `SELECT, INSERT` on `events` and `event_recipients`, and `SELECT` only on the identity and authorization tables it must read to satisfy policies and triggers: `tenants`, `principals`, `projects`, `project_memberships`, `actors`, `actor_delegations`, `agent_sessions`, `threads`.
2. Identity and authorization writes move to a role the append path does not hold. Use `engram_maintenance`, or introduce a dedicated provisioning role if you judge that cleaner; say which you chose and why.
3. Confirm the append transaction of specification section 8.1 still has every read it needs under the reduced grant. If any policy or trigger now fails for lack of a read, that is a finding worth reporting rather than working around with a broader grant.
4. Leave the seed path working. It runs as `postgres` and is unaffected, but check rather than assume.

Out of scope, and do not touch: the `TRUNCATE` guard and the delegation-trigger comment, which stay queued as findings two and three; the append transaction itself; migration 0002; anything in Port Watch, Re:PORT, onboarding, or the wizard.

## Migration discipline

Specification section 21 requires migrations to be immutable, sequential, checksum-verified, and forward-only. `0001_canonical_core` has never been executed anywhere, so amending it in place is defensible and is probably the right call. Amending in place versus adding `0002_role_grants` is your judgment; state which you chose and why in the reply. If you amend, the recorded checksum must change accordingly.

## Tests

Negative controls, each asserting the specific SQLSTATE and message, each with a positive control:

1. `engram_app` inserting into `actor_delegations` is refused; positive control: the maintenance or provisioning role succeeds.
2. `engram_app` inserting into `project_memberships` is refused; same positive control.
3. `engram_app` inserting into `actors` and into `principals` is refused.
4. `engram_app` can still `SELECT` from each of those tables within its tenant, since policies and triggers depend on it.
5. `engram_app` can still `INSERT` a valid event, proving the reduced grant did not break the append path.
6. The existing isolation and immutability suites still pass unchanged.
