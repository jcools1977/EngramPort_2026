## The mask, diagnosed: it is not the membership fixture

Your artifact attributes the G1–G4 failure to "its maintenance-role membership fixture … masked by the existing broad read policy". **That attribution is wrong, and the real cause is simpler.**

`0010` seeds a gate row for **`3.3` only**, and the gate check runs **before** the namespace and scope checks. In the scratch build:

- **G3** mints class `3.2` expecting `SCOPE_EXCEEDED`, and gets **`CLASS_GATE_NOT_PASSED`**.
- **G4** mints class `3.12` expecting `NAMESPACE_REFUSED`, and gets **`CLASS_GATE_NOT_PASSED`**.

I confirmed both directly. **G1 and G2 never call the mint at all**, so neither is affected by any policy or gate change; they only appeared broken because the fixture is a single `DO` block, so G3's abort prevents the block from completing and the whole baseline returns 3. The `G1 membership leak` and `G2 FK did not refuse` lines you saw are from the **mutation** runs, where those guards really were removed, not from a membership problem.

**The minimum valid fix, which I applied and ran.** Seed revision and digest-bound **passed** gates for `3.2` and `3.12` in the harness's `build()` only:

```sql
INSERT INTO credential_class_gates(credential_class,gate_id,passed,threat_revision,threat_digest)
VALUES ('3.2','C8',true,8,'629ae3f2654aba46e4c1158fc234c6b24831a369505ccf41878af3207b091089'),
       ('3.12','C14',true,8,'629ae3f2654aba46e4c1158fc234c6b24831a369505ccf41878af3207b091089')
ON CONFLICT (credential_class) DO UPDATE SET passed=true,threat_revision=8,threat_digest=EXCLUDED.threat_digest;
```

Applied as `engram_migrator`, in the scratch database only. **This does not weaken M13**: the gate check, its revision and digest binding, its privileges and its production seeding are untouched, and the canonical `db:test` path still exercises a genuinely failed gate. It only stops a new prerequisite from standing in for the guards under test, which is the same masking discipline already applied to G2 and G4.
