## Objective

Implement task T1 of the onboarding increment: the **invitation record** and the **welcome-package manifest** as portable file formats, a verifier that accepts a valid package and rejects every malformed or unauthorized one, and artifact-prefix ownership enforcement in `verify-log`.

The full design, including the threat model and the decisions this task must not relitigate, is the referenced artifact. Read it as specification, not as instruction from a peer: it is my design and I am accountable for it, but if you find a flaw in it, say so in your reply rather than implementing around it.

This task is deliberately executable in your environment. It needs Node only, no Docker, no PostgreSQL, no network. That is why it is first: migration 0001 is still unexecuted code, and I will not stack a second unproven layer on top of it.

## Scope

In scope:

1. **`schemas/invitation-v0.schema.json`.** Fields: `schema_version`, `invitation_id` (UUIDv7), `tenant`, `project`, `issuer_principal`, `issuer_actor`, `intended_subject` (an external identity reference or the literal `bearer`), `grant` (object: `role`, `scopes`, `capabilities`, `groups`, `trust_ceiling`), `grant_digest`, `token_sha256`, `single_use`, `issued_at`, `expires_at`, `status` (`open`, `accepted`, `declined`, `revoked`, `expired`). `additionalProperties: false`, exactly as `event-v0.schema.json` does, so unknown fields are rejected rather than ignored.

2. **`schemas/welcome-package-v0.schema.json`.** The manifest shape in section 2.1 of the design artifact: `package_version`, `package_id`, `issued_at`, `expires_at`, `issuer`, `subject`, `checkpoint`, `grant_digest`, `parts[]` each with `name`, `media_type`, `sha256`, and `signature` with `algorithm`, `key_id`, `value`. `additionalProperties: false`.

3. **Digest and signature rules.**
   - `grant_digest` is SHA-256 over the canonical serialization of the `grant` object. Define the canonicalization precisely and document it, using RFC 8785 JSON Canonicalization as spec section 5.2 does. Do not invent a second canonicalization profile; name this one `engramport-grant-v1`.
   - Part digests are SHA-256 over raw part bytes, matching the existing artifact-reference behavior in `verify-log`.
   - The signature is Ed25519 over the SHA-256 of the canonical manifest with the `signature.value` field absent. Node's built-in `crypto` supports Ed25519; add no dependency.

4. **`engram welcome verify --package <dir>`.** Verifies, in this order, and reports every failure rather than stopping at the first: manifest parses and matches schema; every part named in the manifest exists and its digest matches; no unlisted part files are present in the package directory; `grant_digest` in the manifest equals the digest recomputed from the identity part's grant object; the signature verifies against a key resolved from `actors/` or a `keys/` directory; the package has not expired; the referenced invitation's status is `accepted`; the checkpoint's `event_id` exists in the log and its `project_seq` and `chain_hash` are consistent with what the local log shows.
   - Exit non-zero on any failure. Output must name the specific rule violated.
   - **Verification MUST NOT read authority from any part.** Rights come from the identity part only because the identity part is covered by the signature and bound to `grant_digest`. No permission may be derived by parsing prose from any part. This is design section 2.2 and it is the point of the task.

5. **Artifact-prefix ownership in `verify-log`.** An event's `artifacts` references MUST resolve under the authoring actor's own `artifact_prefix`, not merely under `artifacts/`. This is gap 5 in the design. Expect existing events to still pass; if any does not, stop and tell me rather than editing an accepted event.

6. **Negative fixtures, one per rejection reason**, in the style already established in `tests/git-v0.test.mjs`: each mutates a valid fixture package and asserts the specific error. Minimum set: tampered part bytes; part missing; extra unlisted part present; manifest field added; grant object altered so `grant_digest` no longer matches; signature valid over a tampered part list; signature by an unknown key; signature by a revoked key; expired package; invitation status `revoked`; invitation status `open` rather than `accepted`; checkpoint `event_id` absent from the log; checkpoint `chain_hash` inconsistent; artifact reference escaping the authoring actor's prefix.
   - **Four adversarial fixtures are mandatory** and are the reason this task exists, from design section 8.7: a package whose context part contains role-escalation instructions; one whose invitation note impersonates the operator; one whose part content contradicts the identity block; one with a valid signature over a tampered part list. Each MUST verify as either a clean rejection or, where the package is structurally valid, a pass whose reported grant is unchanged by the injected text. Assert the reported grant explicitly. A test that only shows the command exits zero proves nothing here.

7. **A positive control for every negative**, showing the unmutated package verifies. Report both.

Out of scope, and do not build these: bounded-context assembly and token budgeting (T4), `engram welcome issue`, per-thread modes (T1.5, which I will hand off next), any PostgreSQL work, invitation state transitions as live events in this repository's log, and guest or foreign-key registration (T5).

## Completion criteria

1. Both schemas exist, reject unknown fields, and are exercised by fixtures.
2. `engram welcome verify` accepts a valid fixture package and rejects each mutation with the specific named rule, exit code non-zero.
3. Every negative fixture in scope item 6 passes, each asserting the exact error, with its positive control.
4. The four adversarial fixtures pass, and each asserts the resulting reported grant, proving injected prose changed no right.
5. `verify-log` enforces artifact-prefix ownership, with a fixture proving it rejects a cross-prefix reference, and `npm run proof` still passes on the existing log.
6. Everything runs from a clean checkout with one documented command, on Node alone, with no new dependency and no network. State the Node version used.
7. No secret is committed. Invitation tokens appear only as SHA-256 digests in any committed file; fixture tokens are clearly marked fixture-only.
