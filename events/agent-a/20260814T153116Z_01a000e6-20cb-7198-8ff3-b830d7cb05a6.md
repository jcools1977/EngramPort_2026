## Objective

Implement **W1-3: grouped approval, digest scope, and portable plan identity**, now in the canonical register at `docs/plan/workspace-setup-wizard-tasks.md`.

This is the sole eligible implementation item. WIP remains one.

It resolves **C3, F2 and F7 as one unit**, because they are one problem seen from three angles: an approval that cannot say which steps it covers, a digest that cannot say which step it belongs to, and a plan whose identity dies at a process boundary. Fixing any one alone leaves the other two able to defeat it.

## The property this task must establish

**A human approves a specific ordered plan, and nothing else can be executed under that approval.** Not a plan with the same steps in a different order, not one with a step inserted, removed, or swapped, not one whose parameters changed after review, and not a plan that merely looks internally consistent.

ADR 0012 decision 5 chose coarse approval grouping over per-step approval, arguing that thirty approvals train a founder to approve without reading. Constraint C3 records the condition that argument depends on: the grouped approval must bind the ordered `(step_id, action_digest)` list and surface per-step parameter diffs. If this task ships without that, decision 5 traded a real control for a comfortable one.

## Scope

### 1. Widen the action digest

`action_digest` currently covers `parameters` only. Widen it to cover `step_id`, `kind` and `parameters` under RFC 8785 canonicalization.

**Bump the profile name.** Specification section 5.2 versions the covered field list as the hash profile, so a changed field list requires a changed name: `engramport-action-v2`. Do not keep `v1` on a digest that means something different. Nothing external consumes v1 yet, so this is cheap now and expensive later.

### 2. Portable plan identity

A compiled plan carries a `plan_digest` over its ordered `(step_id, kind, action_digest)` sequence plus the profile name, canonicalized the same way. It must be identical across processes, across serialization round-trips, and on any machine.

Provide a loader that takes a serialized plan and returns a usable compiled plan **only after recomputing and verifying its digest**. The `WeakSet` brand stays for in-process construction; the loader is the durable equivalent, and F7 is closed when a plan can be compiled, written to disk, read back, and used.

### 3. The verification model, stated precisely because it is easy to get subtly wrong

**A self-consistent plan is not a verified plan.** Anyone can build a forged plan and compute a correct `plan_digest` over it. Recomputing a plan's own digest and finding it matches proves only that the plan is internally consistent, which is worth nothing on its own.

The trust anchor is the **approval**. Verification means: the presented plan's `plan_digest` equals the `plan_digest` recorded in the approval, and the step being executed matches the `(step_id, action_digest)` entry at its position in the approved sequence. An implementation that checks only self-consistency has implemented nothing, and it will pass a careless test suite. Make the negative control for this explicit.

### 4. Grouped approval

A grouped approval records the `plan_digest` and the ordered `(step_id, action_digest)` list. Approval and execution both verify against it. Integrate with the W1-1 session so an approval remains session-bound and session-expiring; do not weaken anything W1-1 established.

### 5. Per-step parameter differences

Given an approved plan and a presented plan, produce a structured diff: steps added, removed, reordered, and modified, with parameter-level detail for modified steps. Structured data, not prose. This is what makes coarse approval reviewable, so it is a deliverable, not a debugging aid.

### Out of scope

Any real execution, provisioning, GitHub call, database access, W1-2 which is mine, Re:PORT, onboarding, Port Watch, and `migrations/`. Do not touch the v0.1 work.

## Tests and acceptance criteria

**Positive**

1. Digests are deterministic across runs and stable across a serialization round-trip.
2. A plan compiled, serialized, reloaded, and verified against its approval executes normally.
3. A grouped approval over a five-step plan authorizes each of its steps in order.
4. Diffing a plan against itself yields an empty diff.

**Adversarial**, each refused with a specific named error, each with a paired positive control

5. **Reordered** steps: same steps, different order, refused.
6. **Inserted** step.
7. **Removed** step.
8. **Substituted** step: one step replaced by a different one.
9. **Modified** step: a parameter changed after approval.
10. **Forged but self-consistent plan**: a hand-built plan with a correctly recomputed `plan_digest`, presented against a real approval. Refused. This is the headline control for section 3 above.
11. **Cross-plan approval**: an approval for plan A presented with plan B.
12. **Digest-scope control**: two steps with identical `parameters` but different `step_id` or `kind` now have different digests. This is the F2 regression test and it must fail against the old `v1` digest.
13. Serialization round-trip of a **tampered** plan is refused on load.
14. A hand-built step list that never passed `compileSetup` is still refused at approval and at execution.

**Diff controls**

15. Each of the five diff classes is detected and reported with its step id, and a modified step reports which parameters changed.

**Additional**

16. Every negative has a paired positive control, and both are reported.
17. Existing suites all still pass: `setup:test`, `dry-run:test`, `session:test`, `watch:test`, `welcome:test`, `db:static-test`, `proof`. Note that widening the digest changes W0-1 and W0-2 expected values; update those fixtures, and say in your reply exactly which expected digests changed and why.
18. Node only, no new dependency, no network, no database. State the Node version.
19. No secret in any fixture.
