# Council 03: design durable cursors

**DeVere has funded building them.** F115 established that the current ones are not durable in any product sense: no watch state is tracked in git, so a fresh clone starts at zero and two builders on two machines hold divergent cursors for the same `(agent, project)`. **This is a design question, not an implementation handoff.**

**Agent-a's recommendation is sealed at `cf3c441`**, `artifacts/agent-a/council-03-recommendation-sealed.md`, sha256 `f9a86056c2510eeeb3eee27ee9cf5c9c781f4c347d173603ad504fc0baadfa66`. **Do not open it before committing yours**, and state whether you did.

## The question

**Where does a cursor live, such that it is durable across a clone, a machine, and a second builder?**

## The constraint that makes this hard

`docs/architecture/port-family.md`: **"Port Log is truth. Everything else is a projection of it, and no projection may become truth by being useful."** Port Watch is named there as a projection, deletable and rebuildable from the log without loss.

**Every obvious storage location appears to violate either durability or that invariant.** A local file is not durable. A committed file is durable and becomes a second source of truth about what happened, and races between concurrent builders. Cursor events in the log make the bookkeeping durable by making it truth. **Say if you think one of these is acceptable and why the invariant survives it.**

## What the design must also resolve

Agent-c's audit found these; a design that fixes the storage and leaves them is not a fix:

- **`rewind` guards only backward movement.** Any caller may advance the cursor forward, skipping events silently, and the audit event is written only on backward moves.
- **The watch cursor and `listInbox` can disagree in both directions.** `complete()` advances past intervening events that remain unanswered in the inbox; an eligible handoff can wake the watch while never appearing in the inbox.
- **`FileWatchStore` and `key(agent,project)` assume a single writer.** Two processes can both set `active_run` and last-rename wins.
- **`decideWatch` delivers only the first `handoff` carrying `implementation_authority`**, so replies, artifacts and completions are never delivered, while the site says "new work".

## What to return

A recommendation, the reasoning, **what evidence would change your mind**, and **the migration story**: what happens to existing local cursor state, and whether the change is a protocol change under ADR 0028's three classes.

**Also answer the question agent-a thinks is the strongest objection to any derived design:** must delivery ever include events an actor is **not** the `next` for, such as watching a thread for a completion while another actor holds the turn? **If yes, say so plainly**, because it would rule out defining position purely as unanswered addressed work.
