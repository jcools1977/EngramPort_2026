## Objective

Implement task **W0-1: workspace setup plan schema and deterministic compiler**, the first bounded task of the workspace setup wizard increment.

Define `workspace.setup.yaml`, the declarative description of a target workspace, and a compiler that turns it into an ordered, typed, idempotent step list where every consequential step carries an action digest over its exact parameters. No provisioning, no network, no database, no GitHub.

## Why this task is first

Every later wizard phase executes a plan, so the plan format is the spine. It also front-loads the two controls most likely to erode quietly during implementation: digest binding on consequential steps, and the rule that no plan may grant more authority than the founder holds. Both are far easier to enforce in a compiler than to retrofit into nine execution paths.

It is also Node-only. Migration `0001_canonical_core` remains unexecuted in both our environments, and I am not stacking further unproven work on it.

## Scope

1. **`schemas/workspace-setup-v0.schema.json`.** Describes the target workspace: repository reference, database target, participants with proposed role, scopes, capabilities, groups and trust, groups themselves, import scope, and welcome-package defaults. `additionalProperties: false` throughout, matching `event-v0.schema.json`, so unknown fields are rejected rather than ignored.

2. **The compiler.** Input a validated setup document, output an ordered step list. Each step carries: a stable `step_id`, a `kind`, its parameters, a `consequential` boolean, a `depends_on` list, and for consequential steps an `action_digest`.

3. **Canonicalization.** `action_digest` is SHA-256 over the RFC 8785 canonical JSON of the step's parameters, following specification section 5.2. Name the profile `engramport-action-v1`. Do not invent a second canonicalization; if the profile from onboarding T1 (`engramport-grant-v1`) already gives you a canonicalizer, reuse it rather than writing a parallel one.

4. **Determinism.** Identical input yields an identical step list and identical digests across runs. Key order, comments, and insignificant whitespace in the input must not change any digest. Any material parameter change must.

5. **Refusals.** The compiler refuses, with a distinct named error each:
   - cyclic `depends_on`
   - an unsatisfiable dependency
   - a step granting a scope the founder does not hold
   - a grant whose expiry outlives its granting principal
   - a guest grant exceeding the onboarding defaults, which are one project, `untrusted_agent`, at most fourteen days
   - an agent grant exceeding or outliving its owning principal's
   - a requested GitHub permission outside the ADR 0012 enumerated set, which is read authorized content and history, open one pull request on a non-default branch, and receive webhooks. Merge rights and default-branch write must be refused by the compiler, not merely omitted by convention.
   - a participant record asserting its own trust level above `untrusted_agent`, since trust is assigned and never claimed

6. **Negative fixtures with positive controls.** One fixture per refusal above, each asserting the specific error rather than that an error occurred, in the established style of `tests/git-v0.test.mjs`. Each paired with a positive control showing the corrected plan compiles.

7. **Determinism fixtures.** Prove digest stability across runs, prove key reordering and comment changes do not alter digests, and prove a material change does.

Out of scope, and do not build: the dry-run executor (W0-2), session and delegation (W1-1), any provisioning, any GitHub call, any database access, and any live authority check against real membership tables. The founder's held authority is an input to the compiler for this task, not something it looks up.

## Completion criteria

1. Schema exists, rejects unknown fields, and is exercised by fixtures.
2. Compilation is deterministic and proven so by fixtures, including the reorder and comment cases.
3. Every consequential step carries an `action_digest` over `engramport-action-v1`; non-consequential steps are explicitly marked.
4. All nine refusals in scope item 5 are implemented, each with a negative fixture asserting its specific error and a positive control.
5. Dependency ordering is correct and stable; cyclic and unsatisfiable plans are refused rather than reordered.
6. Runs from a clean checkout with one documented command, on Node alone, no new dependency, no network. State the Node version.
7. `npm run proof` still passes, and your onboarding T1 work is unaffected.
8. No secret in any committed file or fixture.
