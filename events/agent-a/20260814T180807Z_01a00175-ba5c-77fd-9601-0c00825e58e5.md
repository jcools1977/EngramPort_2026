## Objective

Implement **W1-4: `engramport-action-v3`, full reviewable-record coverage**, now in the canonical register at `docs/plan/workspace-setup-wizard-tasks.md`.

This is the sole eligible implementation item. WIP remains one.

It closes **F8**, the finding you raised and I confirmed: flipping every step's `consequential` from `true` to `false` leaves every action digest and the `plan_digest` unchanged, and the plan still executes as `authorized`. A founder who approved four consequential steps can have a plan executed that presents zero.

## The property this task must establish

**The surface a founder reviews and the surface an approval covers are the same set, by construction rather than by discipline.**

W1-3 made approval mean something. This makes it mean everything the founder was shown. Your own design finding is the specification for it, and taking your clean-close recommendation rather than documenting the gap is the right call: a rule that says "do not show uncovered fields as approved" survives exactly as long as the person who wrote it is in the room.

## Scope

### 1. `engramport-action-v3`

Binds `step_id`, `kind`, `parameters`, `consequential`, and `depends_on` in its **exact stored order**.

### 2. Deny-by-default coverage, which is the part that stops F8 recurring

Define the profile as **the whole step record minus an explicit, enumerated exclusion list**, not as an allow-list of five fields.

An allow-list reintroduces F8 the first time someone adds a field to the step record and does not think about the digest. A deny-list makes forgetting fail closed: the new field is covered, and excluding it becomes a deliberate act that has to be written down and justified in the profile definition.

Only `action_digest` itself is excluded today. Any future presentation-only exclusion is named there with its reason.

### 3. Profile identification

`engramport-plan-v1` already binds the action profile name inside the plan digest. Keep that: its own covered field list is unchanged, so it does not need a version bump, but it must now name `engramport-action-v3`, so a v2 plan and a v3 plan of otherwise identical steps produce different plan digests.

A serialized plan carrying `engramport-action-v2` must be refused at load with a specific error. Confusing the two profiles must be impossible, not merely unlikely.

### 4. The loader must not normalize

`loadSetupPlan` digests **exactly what the wire carries**. It MUST NOT sort `depends_on`, default `consequential`, coerce types, or normalize any covered field before digesting.

This matters more than it looks. `compileSetup` sorts `depends_on`, so a source-level reordering is a genuine no-op and correctly produces the same digest. But if the **loader** also normalized, a forged wire with reordered dependencies would be laundered into validity by the very check meant to catch it. Normalize at compile, verify verbatim at load.

### 5. Diff must name the field

The structured diff currently reports a step as modified when its `action_digest` differs, and the `parameters` array explains why. Once `consequential` and `depends_on` are covered, a change to either produces a modified step with an **empty** parameters array: a diff that says "something changed" and cannot say what.

Extend the diff to name the field that changed, including `consequential` and `depends_on`, with before and after values. A founder-facing diff that cannot explain a difference is not a control, it is an alarm with no display.

### Out of scope

The review UI itself, W1-2 which is mine, onboarding, Re:PORT, Port Watch, any database or migration work, and every other queued item. Do not touch `migrations/`.

## Tests and acceptance criteria

**Positive**

1. Round-trip: compile, serialize, load, execute against an approval issued before serialization.
2. A source-level `depends_on` reordering compiles to the same digest, because the compiler normalizes. Prove this explicitly so the normalize-at-compile boundary is recorded.
3. Diffing a plan against itself is empty.

**Adversarial**, each **rebuilt with fully self-consistent action and plan digests**, each loading as internally valid, each refused against the genuine session-bound approval with a specific error

4. `consequential` flipped on one step.
5. `consequential` flipped on every step. This is the exact F8 demonstration and it must now fail.
6. A dependency **added** to a step.
7. A dependency **removed** from a step.
8. Dependencies **reordered** within a step, with the compiled step order unchanged. This is the case the loader would destroy if it normalized.
9. All five W1-3 classes still refused: reordered, inserted, removed, substituted, modified steps.

**Profile controls**

10. A wire carrying `engramport-action-v2` is refused at load with a specific error.
11. A v2 plan and a v3 plan built from identical setup input have different `plan_digest` values.

**Diff controls**

12. A `consequential` change is reported by field name with before and after.
13. A `depends_on` change is reported by field name with before and after.
14. A parameter change still reports its path, as W1-3 established.

**Additional**

15. Every negative has a paired positive control, and both are reported.
16. All existing suites pass: `approval:test`, `setup:test`, `dry-run:test`, `session:test`, `watch:test`, `welcome:test`, `db:static-test`, `proof`.
17. **Every changed fixture digest is explained exactly**: which digests changed, and which covered field caused each change. Widening coverage changes every action digest and therefore every plan digest, so state that plainly rather than listing it as incidental.
18. Node only, no new dependency, no network, no database. State the Node version.
19. No secret in any fixture.
