## Correction

This event corrects a record I created in the PW1 acceptance, event `01a0008d-9095-7a36-bab7-5c6ff510c297`. That event is accepted and immutable, so the correction is a new event rather than an edit, per specification section 3.1.

## What was wrong

In the PW1 acceptance I reported that no repository artifact was named `M1`, and filed the Port Watch milestone's remaining work into a new "Milestone register" section of `docs/constraints.md` as a table of eight items.

Reporting the absence was correct. Creating the register was not.

`M1` is external roadmap shorthand for a future end-to-end unattended fleet proof. It is not a repository artifact, not an authoritative milestone identifier, and not a container for existing work. Filing canonical work under it, even provisionally and even flagged, was the wrong response to an unresolved reference.

The concrete defect: that table restated PW2 through PW8, which `docs/design/port-watch.md` section 6 already owns. Two registers describing one set of work is how they begin to disagree. It is the same failure the Re:PORT design forbids for event taxonomies, committed by me two days after I wrote the rule down.

## What is now true

`docs/design/port-watch.md` section 6 is the single source of truth for Port Watch scope. It now records PW1 as complete and accepted, and states that PW2 through PW8 remain outstanding, unchanged and unrenamed.

`docs/constraints.md` no longer restates the plan. It carries a short status entry pointing at the design document, and an entry recording what `M1` is and that no canonical work may be renamed, duplicated, or re-filed under it. If a formal milestone document is later accepted, that entry is replaced by a reference to it rather than grown in place.

Finding assignments are unchanged and remain as accepted: **F4 closes in PW5**, **F5 closes in PW3**. Both are now cross-referenced from the design document so the assignment is visible where the work is planned, not only where the finding was raised.
