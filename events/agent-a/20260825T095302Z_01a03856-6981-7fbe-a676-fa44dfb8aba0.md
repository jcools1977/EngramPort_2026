# ACCEPTED: the synthetic OIDC verifier holds. Your collision disclosure is a finding in its own right

Reproduced independently: `db:test` exit 0 at **`executed=82`**, all ten mutations `baseline=0 applied=t after=1 forbidden=t restored=0`, `npm test` **246 / 0 / 0 skipped**, `session:async-negative` `enumerated=t`, harness `--negative` exit 1, lint 0, proof 255, clean tree.

**ADR 0026's seam is implemented exactly as decided.** The verifier returns a frozen `{iss, sub, aud, exp, nonce}` and **never a `principal_id`** — and the control that proves it is the right one: a signed fixture deliberately carrying a caller-asserted `principal_id` which the clean verifier omits. That tests the decision rather than restating it.

**The ordering is what makes the two dangerous cases real refusals.** I read the source rather than the marker. `alg: none` and non-RS256 are both refused **before any signature dispatch**, so the HS256 construction never reaches a verify call with the RSA public PEM as an HMAC secret. And key status is checked **before** signature verification, so `OIDC_KEY_RETIRED` on a cryptographically valid token signed by a real `kid` is genuinely a lifecycle refusal and not a disguised bad-signature or missing-key result. **That distinction is the whole value of the rotation control**, and you built it the way it had to be built.

Issuer, audience, expiry and nonce are each otherwise-valid RS256 tokens, so no neighbouring check carries another. Expiry uses the injected clock and trusts no caller time. Retention clears in `finally` on both the success and the refusal path, with the observation read from `transientInventory()` rather than asserted.

**Nothing closes.** Criterion 1's cryptographic half is done; the authentication *fact* still needs the binder, which ADR 0026 leaves blocked on DeVere's tenancy decision, and a real identity provider he has not authorised.

## Your disclosure is the finding

**Sixth consecutive slice with a self-reported wrong-reason result**, and this one is worth more than the courtesy. Two `db:test` attempts collided with another live harness on the fixed scratch database name, and you discarded both rather than counting them.

I checked, and **the collision is structural, not bad luck.** `scripts/run-d1-mutation-harness` hard-codes `SDB=engramport_mut`, and `run-db-tests` drives `docker compose` with the default project name, so two concurrent runs share one container and one scratch database. `cleanup` runs `down --volumes`. **One run's teardown destroys the other run's database mid-flight**, which is exactly the failure you saw. The mutation directory is `mktemp -d` and unique; the database is not.

**This matters more than it looks**, for a reason outside this repository. Two agents already run `db:test` against one machine, and DeVere is considering a launchd relay agent that would run it unattended. **A working-tree check cannot catch this** — a concurrent `db:test` never dirties the tree — so the collision would be silent, intermittent, and would produce wrong-reason failures that look like real regressions.

## Dispatched: make the harness refuse to collide

An advisory lock so a second concurrent invocation is **refused with a clear message rather than corrupting the first**. Cover both `run-db-tests` and `run-d1-mutation-harness`, since either can be entered directly.

Required evidence:

1. **A negative control proving a second concurrent invocation is refused** while the first still holds the lock, and that the first run **completes unaffected**. That second half is the part that matters: refusing is easy, surviving is the claim.
2. **Stale-lock recovery**: a lock left by a killed run must not wedge the harness permanently. Prove the recovery path, do not assert it.
3. One discriminating mutation — remove the lock and show two concurrent runs actually interfere — **if that can be done without leaving a wrecked scratch database behind.** If it cannot be made safe, say so and take the structural-limitation exemption rather than shipping a destructive mutation.

`executed=` moves from 82 only on observed execution. If a unique per-run database name is the better fix than a lock, **return that as a reading rather than choosing inside the implementation.**
