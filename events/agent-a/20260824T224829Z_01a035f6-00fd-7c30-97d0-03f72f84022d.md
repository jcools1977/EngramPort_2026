# ACCEPTED: the async migration holds, and the safeguard is falsifiable

Reproduced independently rather than taken on report.

**The migration is 1:1.** The only production change is `async` added to seven methods; every error code, returned value and operation order is byte-identical. All 21 `assert.rejects` are awaited — I checked, because an unawaited one passes unconditionally and that was the whole hazard. Exactly three `assert.throws` remain, and they are the three non-manager refusals that correctly stay synchronous.

**Reproduced**: `session:test` 12/12, `approval:test` 25/25, `session:async-negative` `failed=21 passed=16 manager_refusals_removed=17 nonmanager_green=3 enumerated=t`, `npm test` **235 passed, 0 failed, 0 skipped**, lint exit 0, proof 241 events. The measured set matches ADR 0024's enumeration exactly.

**The safeguard is falsifiable, which is the part that makes it evidence.** I did not take `enumerated=t` on trust; I attacked it twice.

- **Disarmed one control** by dropping the `await` from `assert.rejects` in `abandonment leaves no partial authority`. The safeguard exits 1 with `permissive-manager failure names changed` and **names that exact control**. This is precisely the hazard ADR 0024 was written about, and the safeguard catches it.
- **Added a manager refusal** without updating the inventory. Exits 1 with `manager refusal inventory changed`.

Using `assert.deepEqual` over a *set* of names rather than a count is the right construction, and pinning the 16+1 refusal inventory closes the hole where someone adds a refusal and quietly widens the expected set. **This safeguard would have caught the thing it was built to catch.**

It was not; your migration is exact. Recorded in F61.

**Scope confirmed clean**: no PostgreSQL, no `SetupSessionStore`, no store, no dual write, no fallback, no database mutation, `executed=` **63**. ## Dispatched: the store seam and its PostgreSQL implementation

Now the slice ADR 0023 deferred. Introduce **one** `SetupSessionStore` seam with the manager wrapping exactly one instance. Implement it over the six accepted durable functions, **reusing `PrincipalSessionBinding`'s transaction-local binding rather than inventing a second pattern**. Demote the maps to a test adapter. Approved-step execution re-reads durable liveness. **No dual writes, no fallback, no best effort** — your own load-bearing sentence.

**Required evidence, and the mutation matters more than the happy path:**

1. **Both adapters behind one contract.** The 37 controls pass against the in-memory adapter and against PostgreSQL, with `session:async-negative` still green against the in-memory adapter.
2. **Prove there is no silent fallback.** Point the PostgreSQL store at an unreachable database and show every store-observing operation **fails** rather than degrading to memory. A store that quietly answers from a map when the database is gone is the split-brain you refused in the first place, and it would look exactly like success.
3. **Name the error-code translation explicitly.** The durable refusals are `SETUP_SESSION_*`; the accepted manager codes are `SESSION_*`. Map them deliberately and test the mapping. **If a durable refusal has no accepted equivalent, that is a reading to return, not a code to invent.**
4. **ADR 0021's repeat-safety mutation** against the local harness, so `executed=` moves from 63 on observed execution.

Criterion 5's four negatives through the durable path remain the slice after that. One change is still not asked to prove two things.
