## Objective

Implement migration `0001_canonical_core` plus a reproducible local PostgreSQL 16 + pgvector stack, establishing the canonical identity and event substrate defined in spec section 8, with forced row-level security and database-enforced immutability.

This is the first bounded task of v0.1. It builds the substrate only. The append transaction, chain-hash computation, projections, and HTTP API are deliberately out of scope and will be handed off separately once this substrate is proven.

## Scope

In scope, from spec section 8:

- Extensions `vector` and `pgcrypto`; enums `principal_kind`, `actor_kind`, `trust_level`, `visibility`.
- Tables `tenants`, `principals`, `projects`, `project_memberships`, `actors`, `actor_delegations`, `agent_sessions`, `threads`, `events`, `event_recipients`, with column names, types, keys, unique constraints, and check constraints preserved exactly as specified.
- Indexes `events_project_thread_seq`, `events_project_kind_seq`, `events_search_gin`, `events_labels_gin`, `recipients_lookup`.
- `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY` on every tenant-scoped table, with policies comparing `tenant_id` to `current_setting('app.tenant_id')::uuid`, and project reads additionally requiring membership per spec section 8.2.
- Three distinct database roles: a migration owner, a non-owner application role that cannot bypass RLS, and a separate audited maintenance role. The application role is the only role the test harness uses for event reads and writes.
- `BEFORE UPDATE OR DELETE` triggers on `events` and `event_recipients` that reject the statement, per spec section 5.3.
- `deploy/docker-compose.yml` starting PostgreSQL 16 with pgvector, and a seed script creating two tenants with non-overlapping projects, actors, principals, and events, expressly for isolation tests, per spec section 20.3.
- One command that runs migrations and the test suite against a fresh container.

Out of scope for this task: `event_embeddings`, `artifacts`, projection tables, `outbox`, the HNSW index, the append transaction of section 8.1, chain-hash computation, idempotency resolution logic, OpenAPI, and any application service code.

## Completion criteria

1. Migration applies cleanly to an empty PostgreSQL 16 + pgvector database and is checksum-verified, sequential, and forward-only per spec section 21. Applying it twice is either a no-op or a clear refusal, never a partial mutation.
2. Failure tests exist and pass as negative controls, each asserting the specific error, not merely that an error occurred. Minimum set, mapping to spec section 22.2:
   - Cross-tenant `SELECT` on `events` returns zero rows when `app.tenant_id` is set to the other tenant, exercised through every path in the migration including the GIN-indexed full-text path (item 2).
   - Cross-tenant `INSERT` into `events` naming a foreign `tenant_id` is rejected by the RLS `WITH CHECK` clause (item 2).
   - Guessing a known event UUID from the wrong tenant context returns zero rows rather than a row or a distinguishable error (item 2).
   - `UPDATE` and `DELETE` on a committed event fail as the application role, and also fail as the migration owner, proving the trigger and not merely a grant is the control (item 5).
   - A second insert with the same `(principal_id, project_id, idempotency_key)` and different payload bytes is rejected by the unique constraint (item 1, constraint layer only).
   - An event whose `actor_id` belongs to a disabled principal or lacks a valid `actor_delegations` row is rejected (item 3, to whatever depth is expressible in schema constraints; state clearly in the reply what this task could not enforce at the database layer and must therefore be enforced by the append transaction).
   - `in_reply_to` pointing at a nonexistent event is rejected by the foreign key (item 4).
   - A `content_sha256` or `chain_hash` of incorrect length is rejected by the check constraint.
3. A positive control accompanies each isolation test, showing the same query succeeds under the correct tenant context. A suite that only reports success proves nothing.
4. `RLS` is verified as forced, not merely enabled: a test asserts the application role cannot read across tenants even when it owns no table and no `BYPASSRLS` attribute is set, and a test asserts the application role lacks `BYPASSRLS`.
5. The whole suite runs from a clean checkout with one documented command against a container the compose file starts, with no manual setup step and no secret on disk. No credential is committed; local defaults are clearly marked local-only.
6. Work lands in `migrations/`, `deploy/`, and `tests/isolation/` and `tests/failure/` per the layout in spec section 25, without disturbing the v0 Git proof. `npm run proof` still passes unchanged.
