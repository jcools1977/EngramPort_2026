## Review findings

The SQL is close to spec and the deviations I found are improvements or documented. `project_memberships` referencing `principals(tenant_id, id)` rather than `principals(id)` is stronger than the spec text and prevents cross-tenant membership; keep it and I will amend the spec. Three findings need answers, none blocking this task:

1. **The application role can write the tables that authorize it.** `GRANT SELECT, INSERT ON ALL TABLES IN SCHEMA public TO engram_app` includes `actor_delegations`, `project_memberships`, `actors`, and `principals`. Within a tenant, `engram_app` can insert a delegation carrying `'*'` scope and then satisfy `validate_event_actor_delegation`, or insert a membership row and satisfy `project_member_read`. RLS still confines this to one tenant, so it is not a cross-tenant leak, but it means the delegation trigger and the membership read policy are both defeated by the role they constrain, which removes their value as defense in depth. Identity and authorization tables should be writable only by a role the append path does not hold.

2. **`TRUNCATE` bypasses the immutability triggers.** `reject_canonical_mutation` fires `BEFORE UPDATE OR DELETE FOR EACH ROW`. `TRUNCATE` fires neither and is not covered by the `REVOKE UPDATE, DELETE`. `engram_maintenance` holds enough privilege to reach it. A `BEFORE TRUNCATE ... FOR EACH STATEMENT` trigger closes this, and a negative control should prove it.

3. **The delegation trigger's early return depends on RLS being enforced for the caller.** When `app.tenant_id` is unset, `NEW.tenant_id IS DISTINCT FROM NULL` is true and the trigger returns without validating. For `engram_app` the RLS `WITH CHECK` denies the insert anyway, so the composition is safe today. It is worth a comment stating that the early return is load-bearing on RLS, because a future role with bypass would silently skip delegation validation.

Also note `REVOKE UPDATE, DELETE ON events, event_recipients FROM engram_app` is a no-op, since the preceding grant only conferred `SELECT, INSERT`. Your `application UPDATE denied` control therefore passes on the absent grant rather than on the revoke. Harmless, but the control does not test what its name implies.

## Append-transaction gaps

Your list is accepted as written and will scope the append-transaction handoff. I am adding one item: the append transaction must also enforce that `event_recipients` rows are inserted for every resolved address, since the recipients table carries no constraint tying it to the addressing that produced it.
