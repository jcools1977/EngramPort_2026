# Handoff: F176, the verifier catches checkout drift in one direction only; check at append that the pinned bytes are the bytes git will store

Nick's agent, reading F174's fix, found the direction it does not cover. `verifyArtifactDigest` normalizes the bytes on disk toward LF and compares with the pin. Consider a Windows author whose checkout lacks the attribute: they pin CRLF bytes, `core.autocrlf` commits them as LF, and every other checkout then reads LF, which is not the pin; normalization changes nothing, and the verifier reports a real edit where there was none. The attribute prevents this only where it is present, and the actor who most needs it is the one whose scaffold predates it.

Record this as F176 in `docs/constraints.md` in the register's form, crediting nick-agent's review of 2026-09-10 (summarize; do not copy text from the private repository).

## Objective

1. **At append, refuse a pin that git would rewrite.** For every artifact reference, compare the pinned digest with the digest of the blob git will store for that path (`git hash-object <path>` applies the same conversion `git add` applies, honoring `.gitattributes` and `core.autocrlf`). When they differ, refuse the append with a reason that names the path and says the checkout would store different bytes than were pinned, and that `* -text` in `.gitattributes` fixes it. When git is not available the check is a loud refusal, not a skip.
2. **The verifier reports both directions.** When the disk bytes normalized toward LF match the pin, or the pin's bytes normalized toward LF match the disk bytes' LF form (that is, the pin was CRLF and the checkout is LF), report `CHECKOUT_ALTERED_BYTES` with the same remedy rather than a plain hash mismatch. Keep the byte-exact success path unchanged.
3. **Controls, each observed both ways:** a scaffold with `core.autocrlf=true` and no attribute, a CRLF artifact pinned by its disk bytes: append refused with the new reason; same scaffold with `* -text`: append succeeds and verify is clean. A log whose pinned artifact is CRLF, checked out with `core.autocrlf=input` so the file reads LF: verifier says `CHECKOUT_ALTERED_BYTES`, not `artifact hash mismatch`. A genuinely edited artifact still reports `artifact hash mismatch`. Mutation: remove the new append check and show the first control passes for the wrong reason (append succeeds) and the drift is then reported by the verifier on the other machine's checkout.
4. `docs/git-checkout.md` or wherever F174's user guidance lives gets the sentence that the append itself now refuses a pin the checkout would rewrite.
