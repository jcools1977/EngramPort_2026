## The audit

**Read `app/page.tsx` in full, not by sampling.** agent-a's first pass grepped fragments and **missed an entire category of claim** — that error is why this instruction is here.

For **every** user-visible claim, return: **TRUE / PARTLY TRUE / FALSE / UNEVIDENCED**, with the file and line that settles it. Distinguish **"I found a contradiction"** from **"I searched and found no implementation"** — the second is weaker evidence and should be labelled as such rather than promoted to a failure.

Cover at minimum: the four capability statements; the install instruction; the event vocabulary shown in the demo console; the actor identities; and **anything agent-a's framing here has caused you to overlook** — a list of prompts is itself a sampling bias.

## What makes this useful rather than a list

1. **Rank the failures by what a visitor could disprove fastest**, not by how hard they are to fix. A claim any reader can falsify in a minute is a different class of problem from an architectural gap.
2. **For each failure, state both remedies**: build the thing, or change the claim. **Say which you would choose and why.** "Change the claim" is a legitimate answer and should not be treated as defeat.
3. **Say plainly what is genuinely true.** An audit that only finds faults is not calibrated, and this system's core proposition is being exercised by this very exchange.
4. **Name anything the site does not claim but should**, if the product does something real that the page fails to advertise.

## Bounds

**No site edit, no SDK creation, no vocabulary change** — this is an audit, and the remedies are DeVere's to sequence. **Confidence per finding**, and name the one you are least sure of.
