# OIDC authorization options: cost and consequence reading

Parent handoff: `01a038f8-8b39-78c6-b1c4-a46784329d49`

This is a reading, not a provider choice. No provider was contacted, no network request was made, and no credential or configuration was created. Current commercial prices are therefore deliberately not quoted; they are time-sensitive and cannot be verified inside this handoff's no-network boundary. “Cost” below covers repository surface, operator work, secret custody, governance, and what the option actually proves.

ADR 0029 now authorizes the common architecture but leaves one fact undecided: the canonical provider and account. That narrows the comparison materially. A valid option must preserve: one allowlisted issuer/client, Authorization Code + PKCE S256, exact redirect URI, state and nonce, `openid` only, verified `(iss, sub)` identity, no dynamic issuer/JWKS trust, no token retention, and tenant creation only through ADR 0027's single-use founding authorization.

## What does not exist today

The synthetic verifier is not an OIDC client:

- `createOidcVerifier` receives an already-materialized JWKS, issuer, and audience; it performs no discovery or JWKS retrieval (`packages/git-adapter/src/oidc-verifier.mjs:32-44`).
- `verify` receives an already-obtained ID token and expected nonce; it performs no authorization redirect, state validation, PKCE generation, callback handling, or code exchange (`oidc-verifier.mjs:47-70`).
- The JWKS fixture adds a non-standard local `status: active|retired`. Real provider JWKS documents do not establish that lifecycle label. A trusted adapter must define refresh-on-unknown-`kid`, overlapping active keys, disappearance/retirement, and cache expiry without weakening the accepted rotation control.
- The verifier checks audience membership but not OIDC `azp` for a multi-audience token (`oidc-verifier.mjs:25,65`). A real-client slice must either prove the chosen provider always issues the expected single audience or add the authorized-party rule and its control.
- The application has no auth-start or callback route. `app/` contains only the product page, layout, CSS, and `chatgpt-auth.ts`; repository search finds no OAuth/OIDC callback.
- No Node adapter composes verified claims with migration 0022's founder binder and then returns exactly `{principal_id}` through `founderAuthenticator` into `SetupSessionManager.start` (`packages/git-adapter/src/workspace-session.mjs:9,36-40`).
- `package.json` contains no OIDC/OAuth client dependency.

Every non-defer option therefore pays a common minimum cost:

1. authorization-start and exact callback endpoints;
2. one-time, expiring transaction state for `state`, nonce, and PKCE verifier, with replay refusal and no secret/token retention;
3. issuer-pinned discovery, JWKS fetching/cache/rotation, and token exchange;
4. claims-to-registry binder composition returning only `principal_id`;
5. runtime configuration and secret custody;
6. live integration evidence plus negative controls for state, PKCE, redirect, exchange, discovery/JWKS origin, binder mismatch, cleanup, and replay.

The existing ten verifier mutations remain valuable but do not cover any of those six surfaces.

## Comparison

| Option | Relative delivery cost | Ongoing operations | New governance | Can add the missing authentication fact? |
|---|---:|---:|---:|---|
| A1. Direct Google, existing account/Workspace | Medium | Low | Canonical account decision | Yes, for the named `(iss, sub)` and deployment, after live composition |
| A2. New Entra/Okta/Auth0-class tenancy | Medium–high | Low–medium | New identity tenancy and administrators | Yes, but only after that tenancy becomes the accepted trust root |
| B. Supabase Auth | Medium–high | Low–medium | Widen ADR 0022 and reopen ADR 0029's no-broker decision | Potentially, but only as a new broker trust chain |
| C. Self-hosted local OIDC | High | High | Accept operator-controlled IdP as the trust root | Protocol/wiring yes; independent founder attestation no |
| D. Defer | Zero now | Caveat maintenance | None | No |

The relative ratings exclude provider subscription fees, which were not verified.

## A. Direct hosted identity provider

Plausible providers as a class are Google Identity/Workspace, Microsoft Entra ID, Okta, and Auth0. Google differs because the repository already records two candidate Google identities; the others require creating a new identity tenancy before they can vouch for anyone.

### What must exist

- A provider tenant/account with a named administrator and recovery path.
- A confidential web client registration (or an explicitly justified public-client registration), exact redirect URI for each environment, and allowlisted issuer/audience.
- A deployed HTTPS callback URL.
- Discovery/JWKS and token endpoints pinned from the configured issuer, never from token content.
- The founder account enrolled in the provider and its exact verified `(iss, sub)` registered through the trusted binder path.

For Google specifically, ADR 0029 records the unresolved product choice: personal `jcools1977@gmail.com` versus the Google Workspace identity under `covenantsystems.ai`. Both tokens use Google's issuer; organization-versus-personal is not authority derivable from `iss` alone. The trusted registry enrollment decides which subject is canonical. The former roots EngramPort in a personal account; the latter crosses the GovScout-associated domain boundary.

### Secret and holder

For the ordinary server-side web-client form, a client secret is required. It must live in the deployment's runtime secret manager or encrypted platform configuration, not the repository, compose file, scratchpad, artifact, or generated environment file. The provider administrator creates/rotates it; the deployment operator supplies it at runtime; only the callback/token-exchange component receives it.

PKCE does not turn a confidential server client into proof that no client credential is needed. If a chosen provider permits a public-client web flow, that removes the client secret but raises a separate decision about whether public-client semantics are acceptable for the server deployment; it must not be assumed from PKCE alone.

### Accepted surface changes

- New auth-start/callback route files under `app/`.
- New OIDC client/transaction-state adapter under `packages/git-adapter/src/`.
- A real-JWKS lifecycle adapter around or a bounded revision to `oidc-verifier.mjs:32-70`, including the `azp` disposition.
- A Node wrapper for migration 0022's resolver and composition into `founderAuthenticator` at `workspace-session.mjs:9,36-40`.
- Runtime config schema and secret injection; likely a vetted OAuth/OIDC dependency in `package.json` rather than hand-rolling exchange semantics.
- Live-provider integration controls. The existing synthetic controls must remain unchanged and green.

### What it proves beyond the synthetic verifier

A live direct flow proves that an independently operated, allowlisted issuer authenticated the provider account and issued a code/ID token for the registered client; the real redirect, state, PKCE, nonce, token exchange, discovery, JWKS retrieval, and key rotation path interoperate; and the resulting exact `(iss, sub)` reaches the binder without caller assertion.

It does **not** cryptographically prove that the account is “the founder.” The provider proves control of its account according to its own authentication and recovery policies. The administrative registry enrollment is the trust statement that this provider subject is EngramPort's founder.

### Trusted-session caveat

This is the only option class that can discharge the caveat without changing its meaning. It requires the full live chain, not merely one successful provider login:

`provider authentication → verified claims → exact binder lookup/global-disable check → principal-only authenticator result → bound privileged session → A6/A7/A8 boundary`.

Once that chain is implemented, mutation-defended, and configured for the named canonical account, A6/A7/A8 no longer begin from an injected authentication fact for that deployment. Provider availability, account recovery, and registry administration remain operational trust assumptions rather than code claims.

### Distinguishing the hosted choices

- **Google direct:** lowest estate-creation cost, highest product-boundary decision cost. A personal account is operationally simple but person-bound; Workspace is organization-managed but the only existing Workspace domain recorded here belongs to another product boundary.
- **Entra ID:** reasonable only if an accepted Microsoft organization tenancy already exists or is intentionally created. Otherwise the project pays for a new tenant, administrators, recovery, and policy merely to obtain an issuer.
- **Okta/Auth0 class:** clean product separation and mature OIDC administration, but still a new vendor tenancy and root administrator. It adds no stronger cryptographic fact than direct Google; its value is governance, policy, separation, and lifecycle management.

## B. Supabase Auth

### What must exist

- Explicit widening of ADR 0022, whose accepted scope says Supabase's only job is C6 scheduling and “nothing else moves there.”
- Reopening ADR 0029's decision not to introduce an identity broker merely for portability.
- Supabase Auth configuration, redirect URLs, a client relationship between EngramPort and Supabase Auth, and either a native Supabase identity or an upstream provider such as Google.
- The same EngramPort auth-start/callback, transaction-state, real JWKS, binder, config, and live controls required by option A.

### Secret and holder

At minimum, EngramPort must hold the credential appropriate to the chosen Supabase client/server flow, and Supabase may additionally need an upstream provider client secret if it brokers Google or another IdP. Those values live in Supabase's encrypted project configuration and EngramPort's runtime secret store respectively. The Supabase project administrator and upstream provider administrator hold/rotate their sides. The service-role key must not be used as a login credential or exposed to the callback/browser.

### What it proves

With native Supabase identity, it proves Supabase's Auth service authenticated an account under the project's configured policy. With an upstream provider, it proves a chain: upstream provider vouched to Supabase, then Supabase vouched to EngramPort. It also proves hosted discovery/JWKS/callback interoperability.

It does not become “more real” merely because Supabase is already authorized for scheduling. Without widening ADR 0022, it is out of scope. Without testing and accepting the upstream configuration, it may add only an extra hostname and signature layer.

### Trusted-session caveat

It can discharge the caveat only if DeVere accepts Supabase Auth as the canonical trust root or accepts the complete upstream-provider→Supabase→EngramPort chain and its account mapping. That is a larger trust surface than direct option A. As ADR 0029 now stands, this option is architecturally disallowed rather than the cheap default.

## C. Self-hosted OIDC in local compose

Plausible implementations include Keycloak, Dex, or a self-hosted equivalent. The product choice among them is secondary to the trust property.

### What must exist

- A new stateful service, its database/storage, issuer URL, TLS, discovery document, JWKS endpoint, realm/tenant, client, redirect URI, signing-key rotation, backups, upgrades, and recovery.
- An administrator/bootstrap credential and at least one founder login credential or an upstream identity connection.
- Compose/deployment wiring and health/availability handling.
- The same EngramPort callback, transaction-state, exchange, binder, and integration controls as option A.

### Secret and holder

Even with a public PKCE client and no client secret, the IdP needs an administrator/bootstrap secret, founder credential, and private signing keys. Signing keys and IdP state must persist somewhere to keep `sub` and issuer continuity; “no secrets on disk” therefore requires an external secret manager or encrypted managed volume with a separately held key, not a plain compose volume or checked-in environment file. The operator becomes issuer administrator, key custodian, account registrar, and recovery authority.

### What it proves

It strongly proves protocol integration against an independent implementation: discovery, JWKS retrieval, redirect, state, PKCE, nonce, exchange, key rotation, and cleanup all run over a real network boundary.

It does **not** add independent evidence that an external organization vouched for the founder when the same operator created the account and controls the signing keys. In that configuration it is a better differential/integration fixture, but the authentication fact remains an operational assertion by the EngramPort operator. Adding a real upstream identity provider merely turns it into the broker topology of option B.

### Trusted-session caveat

It does not discharge the caveat under the current meaning of “real identity provider vouched for the founder.” It would do so only after a new decision accepts the self-hosted issuer/operator as the canonical trust root, which changes the requirement rather than proving the existing one.

Its engineering and continuing security cost are the highest: patching, key protection/rotation, database durability, monitoring, availability, backup, account recovery, and issuer continuity all become EngramPort obligations.

## D. Defer

### Immediate cost

No new service, client, secret, route, dependency, or control. The synthetic verifier and founder registry remain useful completed components.

### Continuing cost

- W1-1 criterion 1 stays open.
- The trusted-session caveat remains on A6/A7/A8.
- Every environment must continue to describe founder authentication as an injected trust precondition, not a completed control.
- The longer provider selection waits, the more callback, account-recovery, and secret-custody decisions arrive near deployment rather than before it.

Deferral is honest and safe if no production setup session is presented as externally authenticated. It is not evidence and cannot be cited as partial discharge of the authentication fact.

## Is the authentication fact provable without a real provider?

Not in the sense criterion 1 needs.

Local controls can prove every deterministic property EngramPort owns: issuer allowlisting, signature and key lifecycle, algorithm restrictions, audience/authorized-party, expiry, nonce, state, PKCE, redirect exactness, exchange cleanup, claims projection, registry binding, global disable, session binding, and non-retention. A self-hosted issuer can add a genuine protocol differential.

But the final proposition—*this provider account is the founder*—has two operational trust roots that no local mutation can manufacture:

1. the provider's account enrollment, authentication, and recovery process; and
2. EngramPort's administrative registration of that exact `(iss, sub)` as the founder identity.

A live end-to-end control can prove that the configured provider issued a valid assertion for the registered subject at that time. It cannot prove the provider's real-world enrollment judgment or eliminate trust in the administrator who enrolled the binding. The honest closure is therefore a tested technical chain plus a named operational trust statement, not a claim that authentication has become trust-free.

## Bottom line without choosing

- Direct hosted OIDC is the shortest path that can actually discharge the caveat; the unresolved cost is choosing which existing or new identity tenancy is allowed to be EngramPort's root.
- Supabase Auth is not automatically in scope and is now more expensive in governance than direct hosted OIDC because it reopens two accepted boundaries.
- Self-hosted OIDC is valuable integration evidence but does not independently vouch for the founder and creates the largest continuing security obligation.
- Deferral is zero-cost now and leaves the precondition exactly where it is.

No implementation, provider, credential, network, accepted control, migration, threat-model row, or ADR was changed. This reading adds no mutation and does not change the current harness count.
