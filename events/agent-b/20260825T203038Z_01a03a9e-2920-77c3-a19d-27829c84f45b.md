# W1-1 real Google OIDC provider-composition results

Parent: `01a039d7-1687-77ee-985b-e2dea5358968`

## Implemented boundary

The Worker now composes its accepted Durable Object OIDC transaction client with
Google's discovered provider configuration. The configured issuer stays pinned
to `https://accounts.google.com`; the authorization, token, and JWKS endpoints
come from the discovery document and are accepted only as HTTPS endpoints. A
discovery document with a different issuer is refused.

The JWKS cache replaces rather than accumulates key sets, refreshes on cache
expiry and unknown `kid`, and refuses non-RSA, non-RS256, non-signing, duplicate,
private, or malformed keys. The fetch boundary preserves the global Workerd
`fetch` receiver instead of accidentally binding the cache instance as `this`.
All provider fetches use `redirect: manual`, because Workerd explicitly refuses
the Node-only `redirect: error` value; response status is checked before any body
is accepted.

The token exchange sends the authorization code, PKCE verifier, registered
client, loopback redirect, and process-resident client secret to the discovered
Google token endpoint. It returns only the ID token to the verifier and refuses
a refresh token. The provider verifier independently checks RS256 signature,
issuer, audience, expiry, nonce, and the authorized party. The exported identity
surface is exactly `{iss, sub}`.

The local runner binds only `127.0.0.1:8787`, uses `openid` only, and resolves the
1Password reference through `op run --env-file`. No production deployment,
Cloudflare API call, `wrangler secret put`, second issuer, second client, or
plaintext secret file was used.

## Real Google observation

DeVere completed the loopback authorization with the canonical organization
account in his normal browser. Google discovery, authorization, code exchange,
JWKS retrieval, RS256 verification, nonce verification, and callback all
completed; the callback returned HTTP 200 with this deliberately minimized
verified surface:

```json
{"iss":"https://accounts.google.com","sub":"115177634997399945455","audience_count":1,"azp_present":true,"azp_matches_client":true}
```

The observed single-audience token still carried `azp`, and it matched this
registered client. The independent authorized-party rule therefore remains
load-bearing rather than being omitted on a single-audience assumption.

This is a recorded verified subject value, **not enrollment** and not a claim
that Google's enrollment judgement is independently trustworthy. No ID token,
access token, authorization code, PKCE verifier, client secret, or full claim set
is recorded here.
