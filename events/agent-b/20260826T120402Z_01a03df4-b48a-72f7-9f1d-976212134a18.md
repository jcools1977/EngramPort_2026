# Founder enrollment boundary — costed reading, no decision

Parent handoff: `01a03ded-af8c-7b44-8a9d-a296d09ceea3`

This is a reading only. It chooses no issuer, target, enrollment, or migration
path; performs no database, provider, Supabase, or identity write; and claims no
closure. The verified Google subject remains a recorded value, not an enrolled
identity. `executed=` remains 103.

## What exists, and what does not

Migration 0022 deliberately says that `founding_authorizations` is issuance
state rather than an issuance boundary (`migrations/0022_founder_identity_registry.sql:27-40`).
Its three tables are forced-RLS and writable under the shipped policies only as
`engram_migrator` (`:42-57`); direct access is revoked from PUBLIC,
`engram_app`, and `engram_maintenance` (`:166-171`). The live fixture creates
identity and authorization rows as the database administrator
(`tests/founder-binding-live.test.mjs:34-44`). Consequently the present root is
the table owner/migrator (or any platform superuser/BYPASSRLS equivalent), not a
named EngramPort authorization ceremony.

The stored authorization has an identity, reserved principal and tenant,
expiry, revocation, consumption, and creation times (`migrations/0022_founder_identity_registry.sql:29-40`).
Consumption is locked, checks exact identity, revocation and database-clock
expiry, and succeeds once (`:92-124`). It has no issuer/operator identity,
reason, immutable issuance audit row, delivery rule, or authorization-to-issue
predicate. Its `revoked_at` is useful before consumption, but revoking a
consumed row does not unwind a tenant, principal, binding, session, or grant.
ADR 0027 assigns those later remedies to binding/principal disable and session,
grant, and delegation revocation (`docs/adr/0027-founder-tenancy-model.md:29-35`).

The attacker gain has two levels that should not be collapsed:

- Issue-only access can mint a ceremony for an **already enrolled** identity.
  Exploiting the resulting tenant still requires authentication as that exact
  identity (or compromise/collusion with it).
- The current database-writer root can write both
  `founder_external_identities` and `founding_authorizations`. It can therefore
  register its own verified `(iss, sub)`, reserve a tenant/principal, and gain
  founder control of the resulting tenant once the future atomic bootstrap is
  wired. It still does not thereby obtain an existing tenant; ADR 0027 makes
  each ceremony tenant-local and ordinary sign-in creates nothing
  (`docs/adr/0027-founder-tenancy-model.md:7-13`).

## Question 1 — four costed roots

### A. `SECURITY DEFINER` issuer behind an explicit gate

**Shape and surface.** Add a forward migration defining a narrowly parameterized
issuer function, revoke all direct DML on the authorization table, pin the
function owner/search path, grant `EXECUTE` only to the chosen gate, and append
an issuance audit record. The function should bind an existing identity,
server-generate or validate reserved IDs, enforce a short maximum lifetime, and
record issuer, reason, environment, and revocation. This touches the accepted
ACL/policy surface at migration 0022 lines 49-57 and 166-171 and requires new
live ACL, expiry, concurrency, audit, and guard-removal controls.

**Trust/regress.** The function is a mechanism, not a root. A gate based on an
existing founder is circular for the first founder. A gate based on role
membership, a secret, or an allowlist moves legitimacy to whoever provisions
that role/secret/allowlist. It terminates the regress only when that upstream
deployment authority is named as the bootstrap root and its custody is accepted;
otherwise it merely relocates it.

**Attacker, revocation, audit.** Compromise of `EXECUTE` plus the gate permits
issuance for the identities the function accepts; it need not permit identity
enrollment. Revocation works before consumption. After consumption, remediation
must disable the resulting binding/principal and revoke downstream state. An
append-only audit can attribute the database principal and parameters, but a
database row cannot prove which human legitimately controlled that principal.

**Provability.** Synthetic tests can prove exact ACLs, no direct DML, parameter
binding, one-shot races, expiry, revocation, and audit completeness. They cannot
prove operator identity, role provisioning, credential custody, or human intent.

### B. Dedicated out-of-band operator role with direct write

**Shape and surface.** Provision a distinct operator role and grant it only the
minimum `INSERT` (and, if chosen, revocation) capability. Because forced RLS
currently admits only `engram_migrator`, this is not just an external grant: a
forward migration must add the role to the policy at migration 0022 lines 55-57.
Direct insert also exposes schema details and lacks a single place to cap
lifetimes, generate IDs, or require an audit reason. Granting table `UPDATE` for
revocation additionally permits changes beyond setting `revoked_at` unless a
column grant/trigger boundary is added.

**Trust/regress.** The first authorization is legitimate because a named
deployment operator, authenticated through the managed database control plane,
performs it. That is an explicit operational trust statement. The regress ends
at control-plane account/role provisioning; it is not eliminated. If the role
is shared or its provisioning is unnamed, attribution is weaker than the label
suggests.

**Attacker, revocation, audit.** An insert-only compromise can issue for an
existing identity but cannot enroll a new one unless separately granted identity
write. Current timestamps show when state appeared, not who or why; PostgreSQL
audit/control-plane logs would become part of the proof and retention burden.
Pre-consumption revocation needs a separate narrow capability. Post-consumption
recovery is unchanged.

**Provability.** Catalog tests can prove grants, RLS, and inability to perform
other DML. Real evidence is required for operator account ownership, MFA,
control-plane audit retention, and credential recovery. This option is smaller
in SQL but larger in operational dependence.

### C. Bootstrap-only escape that becomes unreachable

**Shape and surface.** Add an atomic first-founder path guarded by durable empty
state/a one-way latch, then make that path fail permanently after the first
successful ceremony. The latch and authorization consumption must be one
transaction and race-tested. A mere `NOT EXISTS` check is **first caller wins**,
not authorization; it must also require a deployment-held capability or operator
role. ADR 0027 permits later tenants, so this solves only the first ceremony;
subsequent authorizations still require a normal founder/operator issuance
boundary.

**Trust/regress.** The first authorization is legitimate only because a named
deployment custodian holds the bootstrap capability. Empty-database state alone
does not terminate the regress. The escape is structurally unreachable to
ordinary callers after use, but a database owner able to rewrite the latch or
function remains a higher root.

**Attacker, revocation, audit.** A pre-bootstrap capability theft is a race for
first founder and has the largest timing consequence. Binding the capability to
the exact pre-authorized `(iss, sub)`, environment, tenant, principal, and short
expiry narrows the gain. Revocation before use must be possible out of band;
after use the authorization is superseded by binding/principal recovery.

**Provability.** Synthetic controls can prove the two-caller race, irreversible
application reachability, exact binding, and replay refusal. They cannot prove
the bootstrap capability was delivered to the right human or that a database
owner will not reset the latch.

### D. Offline-signed, environment-bound founding envelope

**Shape and surface.** Preinstall a public verification key and accept a signed
envelope binding issuer/subject (or identity id), reserved tenant/principal,
environment, expiry, nonce, and purpose. A narrow function verifies it and
records the envelope digest once. This adds signature verification, key version
and rotation/recovery policy, per-environment replay state, and an audit schema;
it should not add a general online signing service.

**Trust/regress.** This terminates the online chicken-and-egg at an explicitly
offline release/bootstrap signing key. It does not make authorization trust-free:
the key custodian is the root. Unlike a generic secret, the envelope can be
scope-limited and reviewed before use.

**Attacker, revocation, audit.** Stealing one envelope grants only its bound
ceremony; stealing the signer grants arbitrary ceremonies until key revocation.
Short expiry and one-time digest stop replay, while revocation of an unused
envelope requires an online denylist or key revocation. Post-consumption recovery
is unchanged. Synthetic cryptographic and replay controls are available, but
offline custody, signer identity, and ceremony approval require real operational
evidence.

### The non-decision

A and B are not truly exclusive: the smallest controlled operational shape may
be a narrow issuer function (A) executable only by a dedicated bootstrap operator
(B). C can reduce the first-use surface but cannot authorize later tenants. D
makes the upstream root sharply scoped at materially higher key-management cost.
The product/security decision is which human or custody system is allowed to be
that unavoidable root; this reading does not make it.

Whichever root is chosen, the missing threat-model row should state: issuer,
delivery, maximum lifetime, identity/envelope binding, first-use ceremony,
operator attribution, pre-use revocation, post-use recovery, and the precise
attacker gain. Revision 8 remains digest-pinned and untouched; this belongs in a
later accepted revision or decision record.

## Question 2 — target and enrollment cost

### Apply 0021/0022 and enroll on `engramport-dev`

This is at least three actions, not one: apply the canonical `TRUNCATE` guards
from 0021; apply the registry, policies, ACLs, and `SECURITY DEFINER` resolver
from 0022; then make durable real-identity and authorization writes. Migration
0021 is unrelated to enrollment but sequential migration integrity means it
cannot be skipped.

The managed-target application needs more proof than the earlier 0001-0020
fingerprint. The local runner executes migrations as `engram_migrator`
(`scripts/run-db-tests:15-97`), while the prior managed-target comparison
explicitly excluded owners because target ownership differs
(`artifacts/agent-a/c6-scheduling-evidence.md:9-24`). Ownership is
security-relevant for 0022 because its resolver is `SECURITY DEFINER` and its RLS
policies name `current_user='engram_migrator'`. A managed application must
therefore verify/normalize function and table ownership, ACLs, policy behavior,
and checksums, not merely compare function bodies. Applying through a statement
API also repeats the transcription risk the earlier fingerprint found in
practice.

The benefit is a rehearsal on the existing evidence substrate and a durable
binding target available now. Costs are schema drift from the repository's
currently verified target state, a real stable subject in a non-production
database (including platform logs/backups/PITR and deletion policy), and the
temptation to treat an evidence project as production. The existing artifact
explicitly calls `engramport-dev` an evidence substrate, not a production
deployment, and records that its schedule was removed
(`artifacts/agent-a/c6-scheduling-evidence.md:89-96`). Enrollment would not by
itself restore `cron.job` or satisfy the production scheduling obligation.

### Wait for an actual production target

This keeps real identity out of dev and makes the first durable binding occur
where it will be used. It also blocks the enrollment chain until a deployment
target, owner model, migration channel, operator root, scheduler/cadence,
recovery procedure, and data-retention policy exist. Deferring every rehearsal
to production increases first-run and rollback risk; the schema/ACL path should
still be proven synthetically beforehand.

### Third path: split schema rehearsal from real enrollment

Apply and fingerprint 0021/0022 on `engramport-dev` only after separate migration
authorization, exercise 0022 with synthetic identities, and make **no real
`(iss, sub)` write there**. Enroll the verified subject later on the selected
operational target under a separately chosen issuance root. This preserves a
managed PostgreSQL rehearsal while separating a reversible schema proof from the
real-person authorization decision. It does not prove managed-target custody of
the real identity, and it still incurs dev schema drift.

If exact real-enrollment rehearsal is required, a disposable isolated staging
project is another variant, but it does not make the write synthetic: the stable
subject is still durable personal/security metadata and may enter provider
backups or audit logs. Project deletion is not automatically evidence of erasure.

## C17 and the synthetic-only boundary

An external-identity row is **not literally a setup-session delegation**.
C17 names `setup_session_delegations` and gates the first durable delegation
(`docs/security/setup-credential-threat-model.md:528,550`). Relabelling a founder
identity as that object would blur two controls. Therefore enrollment alone is
not the C17 transition.

It is nevertheless the first durable **operational identity** use, not a
synthetic proof fixture. C17 was closed conditionally under a `[TEST-GATED]`
capability reading: production must select the PostgreSQL store and scheduler
before the first operational durable setup session. A real enrollment on dev
does not reopen C17 by definition, but it crosses the operational boundary that
made the conditional reading safe. Before that identity is allowed to create a
durable setup session, the target must meet the store/scheduler obligation; an
empty `cron.job` cannot be hidden by calling enrollment “not a delegation.”

ADR 0033 authorizes real Google discovery, exchange, verification, and subject
capture on one loopback composition. It says the synthetic-only rule remains in
force everywhere else (`docs/adr/0033-provider-composition-authorized.md:6-18`)
and makes enrollment a later condition rather than part of its authorization
(`:30-43`). Persisting the real `(iss, sub)` in any database is therefore a
separate user authorization. The pair is not a bearer secret, but it is a stable
global account identifier and the root input to founder binding; target,
retention, disable/recovery, operator, and purpose must be chosen before writing
it.

## Decisions that remain DeVere's

1. Which root may enroll identities and issue founding authorizations, including
   how the very first ceremony is made legitimate.
2. Whether to authorize migrations 0021/0022 on `engramport-dev`, and whether
   that authorization is schema-only or also permits durable real identity.
3. Whether real enrollment waits for an operational target, uses the split
   rehearsal path, or uses a separately authorized staging target.
4. The operational data-retention/recovery and C17 scheduler obligations for
   the chosen target.
