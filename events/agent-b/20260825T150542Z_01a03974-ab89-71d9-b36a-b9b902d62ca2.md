# OIDC runtime continuity: bounded cost reading

Parent: `01a0396b-9ed8-7ef9-93b7-d8ab64f7492a`

## Disposition

No runtime is chosen. This reading makes no provider, credential, network, DNS,
Cloudflare, route, or implementation change. It closes nothing and leaves
`executed=91` unchanged.

The immediate defect is slightly narrower than the parent wording. The
transaction `Map` is created per `createOidcClient` instance at
`packages/git-adapter/src/oidc-client.mjs:21`, not directly at module scope. If
the composition is created per request, continuity is lost on every callback;
if an instance is cached at module scope, the `Map` is still isolate-local and
continuity is intermittent. Cloudflare explicitly gives no guarantee that two
requests reach the same Worker instance and advises against mutable global
request state. The present store is therefore not a production continuity
boundary under either construction.

## Decision matrix

| Shape | Continuity | PKCE verifier and nonce | Exact one-time consume | Restart / migration | ADR 0031 fit |
|---|---|---|---|---|---|
| A. SQLite-backed Durable Object keyed by `state` | Yes, if persisted before redirect and read through the same named object | Persisted in Cloudflare DO storage for the authorization TTL; recoverable through PITR for up to 30 days | Yes, with an atomic stored claim/delete | Survives isolate eviction and host movement; an already-claimed exchange can still fail closed during interruption | Needs a Worker-specific amendment and a second secret custodian |
| B. Workers KV with TTL | No; a callback in another location may miss a new value for 60 seconds or more | Persisted and cached in Cloudflare KV until expiration/deletion propagation | No atomic read-and-delete; stale reads can replay | Storage survives Worker restart, but consistency faults remain | Same Worker amendment and custody expansion as A |
| C1. One long-running process with the present `Map` | Only while exactly one process remains alive and receives both requests | Plaintext only in that process memory, at most ten minutes | Yes within that one process | In-flight authorizations die on restart; replicas or rolling deploys split state | Direct process-start fit; rotation still requires a restart/reload |
| C2. Long-running process plus PostgreSQL transaction rows | Yes, while the database is available and consume is transactional | Persisted in PostgreSQL, its replicas and backups for the chosen retention period | Yes, transactionally | Survives process restart and scale-out; database failover becomes the dependency | Direct process-start fit; adds database credential-retention obligations |
| D1. Encrypted host-only browser envelope alone | Continuity for an honest browser, independent of Worker affinity | Not persisted server-side; ciphertext lives in the browser cookie for the TTL | No: deleting a cookie does not prevent replay of a copied prior cookie | Survives Worker restart; key rotation can strand in-flight envelopes | Needs a Worker amendment plus a new long-lived envelope key |
| D2. Browser envelope plus a DO replay tombstone | Yes; verifier and nonce remain out of server storage while the DO stores only state digest/status/expiry | Browser ciphertext only; server stores no verifier or nonce | Yes, with an atomic DO tombstone | Survives Worker restart; consumed-before-exchange interruption fails closed | Same amendment and envelope-key obligations as D1 |

The categories are not equivalent. A, B, and C2 create a new server-side
credential-retention boundary for the verifier and nonce. C1 does not persist
them but makes availability depend on one process. D2 is the only costed shape
that combines Worker request independence and server-side one-time enforcement
without storing the verifier or nonce server-side; it does so by adding an
encryption-key lifecycle and more protocol surface. That is a cost distinction,
not a recommendation.

## A. Durable Object keyed by state

### Continuity and retention

`env.OIDC_TRANSACTIONS.getByName(state)` routes start/callback activity for the
same random state to one logical object from any Worker instance. This is
continuity only if the object writes `{state, nonce, codeVerifier, redirectUri,
expiresAt, status}` to its strongly consistent storage before returning the
authorization redirect. Keeping that record only in the object's memory would
repeat the defect: Durable Objects hibernate, restart, and discard in-memory
state.

The persisted record is readable by the object code and by Cloudflare's storage
control plane under the account's access model. It should be claimed or deleted
atomically before token exchange, rejected after expiry on every read, and
cleaned with an alarm or subsequent access. A claim that commits before a
runtime interruption prevents replay but loses that in-flight authorization;
claiming after exchange permits a race. The secure disposition is fail-closed,
so the founder restarts authorization.

Deletion at callback/expiry is not a literal erasure boundary. New Durable
Object namespaces use SQLite storage, whose point-in-time recovery can restore
the object to any point in the previous 30 days. That is materially longer than
the current ten-minute transaction TTL. The threat model must therefore name
Cloudflare, account administrators, PITR, incident restores, and an explicit
rule never to restore this namespace as ordinary application data. Expiry must
remain authoritative even if old storage is restored. `deleteAll()` is also
needed to remove an empty object's retained metadata.

### Accepted surface that would change

- `vite.config.ts:14-34`: declare the DO namespace, class binding, migration,
  and required secret names in the source configuration that generates
  Wrangler output. The ignored `dist/server/wrangler.json` is not the source of
  truth.
- `worker/index.ts:5-15` and `worker/index.ts:28-45`: type the binding, export
  the DO class, and route auth-start/callback to a composition that receives it.
- `packages/git-adapter/src/oidc-client.mjs:21-40`: replace the synchronous
  `Map` with an asynchronous transaction-store interface; preserve
  generate-before-redirect, exact expiry, and consume-before-exchange.
- `packages/git-adapter/src/founder-setup-composition.mjs:27-47`: inject the
  bound transaction store instead of constructing an implicit store.
- Add a DO class and focused Worker/Miniflare controls; do not hand-edit build
  output.

### Required proof and operations

Local Wrangler can prove same-name object routing, stored-state survival across
a locally induced isolate restart, atomic competing callbacks, expiry, cleanup,
and no verifier/nonce in responses or logs. It simulates Cloudflare; it cannot
prove global request distribution, production placement, control-plane access,
PITR retention, platform availability, host migration, or mixed-version
deployment behavior. Production evidence needs a bounded auth-start/callback
smoke, concurrent replay refusal, binding/namespace identity, migration success,
and alerts for DO/storage errors without logging transaction material.

Operations must own namespace migrations, schema compatibility across gradual
deployments, alarms and abandoned-state cleanup, account access, incident
response, and the rule that a storage recovery never resurrects usable state.
Cloudflare handles host patching and logical-object relocation, but that
transfers availability and recovery dependency to Cloudflare. At low volume the
free or included allocations may cover use; current paid Workers have a USD 5
monthly account minimum, then DO request/compute/storage metering. Volume is not
known, so a monthly number would be invented.

## B. Workers KV with short TTL

KV does not meet the control. Cloudflare documents that a newly created value,
including a previous negative lookup, can remain invisible in another global
location for 60 seconds or more. It also lacks an atomic read-and-delete. An
auth-start can therefore redirect successfully and a callback can receive
`OIDC_STATE_REFUSED`; after a successful callback, another location can still
read a stale value. Routing writes through a Durable Object does not repair
KV's read characteristics; routing both reads and writes through the object
makes KV unnecessary for a ten-minute transaction.

KV persists and geographically caches the verifier and nonce. The readers are
every Worker with the namespace binding plus Cloudflare/account control-plane
actors. TTL and deletion bound ordinary availability, not instantaneous
erasure. The current ten-minute TTL is above KV's 60-second expiration minimum,
but that says nothing about exact visibility.

The accepted surface would parallel A at
`vite.config.ts:14-34`, `worker/index.ts:5-15`,
`oidc-client.mjs:21-40`, and `founder-setup-composition.mjs:27-47`, substituting a
KV namespace and adapter. Local Wrangler can prove adapter calls, serialization,
TTL requests, named refusals, and absence from logs. It cannot reproduce or
exclude global cache propagation and cross-location stale reads. A local green
run would not be production consistency evidence.

Cloudflare owns KV patching and replication; the project owns namespace access,
TTL, monitoring, quota, and incident handling. Restarting the Worker does not
lose KV data, but an in-flight authorization can fail solely because the start
and callback observe different cache states. Current paid pricing meters writes
and deletes more heavily than reads after included use, but price does not cure
the semantic refusal. KV is refuted for this transaction, not merely ranked
below another option.

## C. Off-Workers long-running process

### C1: memory only

The present `Map` is valid only behind exactly one long-lived process with both
paths routed to it. It retains verifier and nonce in plaintext memory for at
most `transactionTtlMs` (currently ten minutes), exposes them to that process
and its debugger/core-dump boundary, and leaves no database or backup copy.
Crash or restart destroys them. A second replica, rolling deploy, or load
balancer without perfect affinity makes failures intermittent. Affinity alone
also cannot survive the selected process dying. This is categorically stronger
for non-retention and weaker for continuity/availability.

ADR 0031 fits this shape most directly: the service process can resolve an
`op://` reference at startup, receive the value on standard input or an
inherited environment without a disk file, refuse startup if resolution fails,
and retain plaintext only in process memory. Its rotation clause still hides an
operational fact: changing the 1Password value requires the running process to
reload or restart before it can use the new value. Safe rotation needs provider
overlap, 1Password update, restart/reload, verification, then old-secret
revocation. A rolling restart conflicts with the single-process `Map`, so
in-flight flows must be drained or knowingly abandoned.

Accepted changes would add a real service entry point and service/deployment
definition, change `package.json:9-11` only if the service is owned here, inject
configuration at `founder-setup-composition.mjs:27-47`, and add routing/DNS
configuration outside this repository. `oidc-client.mjs:21-40` can remain
memory-backed. Local controls can prove startup refusal, non-leakage,
expiry/one-time use, graceful drain, and that restart loses transactions. They
cannot prove production affinity, supervisor recovery, TLS/Tunnel/origin
restriction, or uptime.

Operations now owns a host/container runtime, OS and Node patching, TLS or a
Cloudflare Tunnel/origin restriction, process supervision, monitoring,
capacity, restart drains, and recovery. There is no transaction recovery by
design; a founder restarts authorization.

### C2: PostgreSQL-backed process

A transaction table with atomic claim/delete permits replicas and survives
process restart, so this shape actually preserves continuity while PostgreSQL
is available. It also persists the verifier and nonce in database pages,
replicas, logs, snapshots, and backups unless application-level encryption and
retention controls narrow them. Readers include the service database role and
database operators. Ten-minute logical expiry does not imply ten-minute backup
erasure.

Accepted changes add a forward-only migration and database functions/ACLs,
replace `oidc-client.mjs:21-40` with an injected asynchronous store, wire it at
`founder-setup-composition.mjs:27-47`, and add the service entry point. Local
PostgreSQL can prove atomic consume, expiry, cross-process continuity, exact
role access, residue, and restart. It cannot prove production failover, backup
erasure, restore behavior, or operator access. Operations owns database
availability, backup/PITR policy, schema rollout, encryption/key rotation,
connection exhaustion, and recovery. If the process remains a Worker using
PostgreSQL through Hyperdrive, add a Hyperdrive binding and Cloudflare becomes
part of the database credential path; the Worker secret findings below still
apply.

## D. Encrypted browser envelope, with and without a tombstone

An authenticated-encryption envelope in a `Secure; HttpOnly; SameSite=Lax;
Path=/auth` host-only cookie can carry state, nonce, verifier, redirect URI, and
expiry across any Worker isolate without server-side persistence. The callback
must receive that cookie on the same host, decrypt it, compare the query state,
enforce expiry and exact redirect, and delete it. Putting the envelope itself in
the `state` URL is worse: URLs traverse provider, browser-history, proxy, and
logging surfaces even when the payload is ciphertext.

The envelope alone does not preserve the accepted one-time property. A copied
old cookie can be replayed after browser deletion. The provider will normally
refuse reuse of an authorization code, but delegating the local replay control
to provider behavior is not the same control. A DO tombstone containing only a
state digest, expiry, and pending/consumed status restores atomic one-time use
without persisting the verifier or nonce server-side. It must be consumed
before exchange and fail closed on interruption. PITR/restore rules still
matter for the tombstone, though restored records contain no transaction
credential.

This shape adds a long-lived envelope-encryption key, version identifier,
authenticated key rotation, maximum cookie size controls, cookie-origin
controls, and browser compatibility evidence. Rotation needs old and new keys
overlapping for at least the transaction TTL or it strands in-flight flows.
Accepted changes span `vite.config.ts:14-34` and `worker/index.ts:5-45` for
bindings/routing, `oidc-client.mjs:21-40` for an envelope store, composition
injection at `founder-setup-composition.mjs:27-47`, and new cryptographic/cookie
controls. Local Wrangler plus browser tests can prove tamper refusal, expiry,
cookie flags/path, key-version overlap, atomic tombstones, and that neither
verifier nor nonce enters DO/KV/database/logs. They cannot prove production
browser mix, Cloudflare secret custody, global routing, or platform recovery.

## Client-secret delivery on a Worker

All Worker-resident options share the same custody mismatch. A Worker has no
one-time process start at which it can invoke `op`. An authorized deployment
operator or CI identity must resolve the value from 1Password and pipe it
directly to `wrangler secret put` or `wrangler versions secret put`; no `.env`,
`.dev.vars`, `--secrets-file`, shell trace, artifact, or log is acceptable for
this project. The Worker declares the name under `secrets.required`, and upload
refuses if it is absent.

Cloudflare then retains an encrypted secret binding and supplies plaintext to
the Worker environment. That makes Cloudflare an additional custodian. It is an
operational reconciliation with the no-disk rule, but it is not clause-for-
clause compliance with ADR 0031's “held in 1Password,” “process start,” or
“no ... deployment change” rotation language. A Worker choice therefore needs
an explicit ADR amendment or a Worker-specific qualification; implementation
must not silently reinterpret the accepted decision.

Rotation becomes: create overlapping provider credentials if supported,
update 1Password, resolve and pipe the new value into a new Worker version,
deploy/roll out and verify that version, then revoke the old provider value.
`wrangler secret put` deploys a new version immediately;
`wrangler versions secret put` permits a staged version. `secrets.required`
proves configured presence, not that CI resolved the approved 1Password item or
that the value is current. Those need deployment provenance, access control,
redaction, and a synthetic placeholder path for local tests. Cloudflare's
documented local `.dev.vars`/`.env` path is forbidden by ADR 0031; local tests
must inject a synthetic value directly into the harness.

## `https://app.engramport.com/auth/callback`

The subdomain is a useful stable facade, not a continuity mechanism. A
Cloudflare Custom Domain can point every `app.engramport.com` path to a Worker,
or proxied DNS/routes can point it to an external origin. The backing runtime
can then change without changing the exact Google redirect URI. Under A, B, or
D it also separates the authenticated Worker from the apex marketing Worker;
under C it gives the external service a stable public name. It therefore buys
deployment independence under every costed shape, though it is not required to
use a different Worker because path routes can also split traffic.

Costs and cautions:

- Auth-start and callback must use the same host if continuity uses a host-only
  cookie. Starting at the apex and returning only the callback to `app` loses
  the cookie. A `Domain=.engramport.com` cookie would broaden credential scope
  to sibling subdomains and should not be the repair.
- `app` is a broad future application origin. If it later hosts more scripts,
  features, or cookies, its compromise surface grows around the callback. A
  dedicated auth hostname would be narrower but less flexible. This is a
  naming/security tradeoff for DeVere, not a reason to alter the proposed URI
  here.
- The exact URI still couples the provider registration to scheme, host, and
  path. Moving from `/auth/callback`, changing host, or losing the domain still
  requires provider re-registration.
- Ownership includes Custom Domain or proxied-DNS configuration, managed
  certificate state, HSTS/CSP/referrer policy, WAF/rate limits, CSRF and cookie
  boundaries, logs/redaction, monitoring, and removal-order controls that
  prevent a dangling hostname during runtime migration.
- Same-origin assumptions change. The marketing apex must redirect to auth or
  use explicit allowed origins; it must not gain callback-cookie access through
  a broad cookie domain. A production test must exercise the exact registered
  URI, not a `workers.dev` substitute.

For a Worker-as-origin, Cloudflare says a Custom Domain owns all paths on that
host and automatically manages DNS/certificates. For an external origin,
proxied DNS plus a Route/Tunnel is the relevant shape. Local Wrangler cannot
prove either production DNS/certificate/routing arrangement.
