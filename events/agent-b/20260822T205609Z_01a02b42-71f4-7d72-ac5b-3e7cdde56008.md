# Contract finding before implementation: M6 is row-scoped; M3 ambiguity must fail closed

This is the requested pre-implementation finding for the bounded D3 slice. I have changed no file.

## M6 reading: no identity-wide tombstone

Section 5A says `Mint against a revoked custody row / Refused`. The durable contract sharpens that to: a revoked custody row "refuses resolution and refuses to back any further mint." Read with the rest of the same contract, this is row-scoped:

- callers supply no custody row id, reference id, UUID, tenant, project, principal or actor;
- a mint creates a new custody row and then a new binding;
- the old reference remains bound to the revoked row and no longer resolves;
- lawful rotation after revocation creates a different row and reference.

Therefore a revoked row cannot be reused to back another mint under the shipped shape. The observed second mint after revocation is lawful replacement, not an M6 violation. An identity-wide query that rejects whenever historical revoked rows exist would add a permanent tombstone absent from section 5A, contradict rotation semantics, and make compromise recovery impossible for that logical identity.

**Finding:** do not add migration 0015 for an identity-wide revoked-row guard. M6 is structurally satisfied at the row boundary but its negative attempt is unrepresentable because the API accepts no prior-row input. A useful committed fixture can prove the paired lifecycle honestly: revoke old row; old reference remains unresolved and cannot be reused; mint a new row/reference; new reference resolves. That is rotation evidence, not a discriminating M6 mutation, and `executed=` must not increase for it.

If section 5A intended an identity tombstone, it needs an explicit architecture amendment naming the logical-identity key, recovery/re-enablement mechanism, and interaction with rotation before implementation.

## M3 reading: ambiguous membership must refuse

The durable contract is explicit that caller-supplied tenant or project is **refused, not overridden**. It also says tenant/project are derived from the authenticated principal and trusted membership graph. `derive_mint_membership` currently uses `ORDER BY tenant_id, project_id LIMIT 1`; with two same-tenant memberships, that chooses the lowest project UUID without an authorization fact selecting that project.

The correct behavior is fail-closed ambiguity:

- zero eligible memberships: `TENANT_PROJECT_REFUSED`;
- exactly one eligible tenant/project: derive it;
- more than one eligible membership: `TENANT_PROJECT_REFUSED` until a trusted, authenticated project context exists;
- any caller `tenant_id` or `project_id` field remains refused rather than ignored or used to disambiguate.

Choosing the lowest UUID is deterministic but not authorization. A fixture that blesses it would turn storage ordering into authority. If agent-a accepts this reading, M3 warrants a forward-only migration replacing `LIMIT 1` with uniqueness enforcement, plus a same-tenant/two-project fixture and a mutation restoring lowest-UUID selection to make the forbidden mint observable.

## Disposition

No implementation, migration, fixture, mutation, simulator or accepted control changed. A7 and A8 remain open. M10 has not started. W1-8, W3 and AEGIS integration have not started. This finding returns to agent-a for the architecture decision required by the handoff.
