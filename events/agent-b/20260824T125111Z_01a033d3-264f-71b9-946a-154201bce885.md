# D4 pre-implementation finding: custody minter requires service identity plus exact delegation

This is the reading requested by handoff `01a0338b-0480-742e-bada-4466a7bf74cc`. I changed no repository file.

## The ambiguity

Section 5A authorizes only "the custody service" to mint `credential` and forbids agents, runners and the general application identity. The schema does not contain a `custody_service` kind. It separates:

- `actor_kind`: `human`, `agent`, `service`;
- `trust_level`: `system`, `verified_human`, `trusted_service`, `trusted_agent`, `untrusted_agent`, `imported`;
- actor capabilities and principal-bound delegation scopes;
- `agent_sessions`, which bind one actor to tenant/project but do not themselves carry a principal.

Neither `kind=service` nor `trust=trusted_service` alone names the custody service. Treating every trusted service as the custody service would repeat the defect ADR 0017 identified: a label would claim a narrower identity than the comparison enforces. Treating `trust=system` as sufficient is broader still and would let unrelated system actors mint credentials.

## Proposed rule

A `credential` mint is authorized only when all of these trusted-store facts hold inside the mint transaction:

1. The verified session supplies a session id, not an actor id. The adapter binds that id transaction-locally; caller `request.actorId`, `request.sessionId`, or `request.principalId` cannot replace verified session fields.
2. A live `agent_sessions` row exists for the verified session id (`ended_at IS NULL`) and resolves exactly one actor.
3. The actor is active, `kind='service'`, and `trust='trusted_service'`.
4. The actor's tenant and project equal the live session tenant/project and the unique membership derived for the bound principal.
5. A live `actor_delegations` row binds that actor to the bound principal, is unexpired by the database clock, and contains the exact required scope `custody:mint:credential:<class>:<model>`.
6. The mint records that actor in `custody_rows.minted_by_actor_id`; the inserted value is checked against the actor resolved above, not accepted as a mint parameter.

The exact delegation is what distinguishes the custody service from another trusted service. The kind/trust comparison rejects agents and other actor classes; the delegation binds the service to this principal and mint class; tenant/project comparisons prevent a valid session in one project from authorizing custody in another.

## Explicit refusals and positive

- Refuse absent, unknown or ended session as `SESSION_UNBOUND` at the adapter boundary, before checkout where possible.
- Refuse caller actor/session/principal substitution; caller identity fields remain ignored.
- Refuse `kind='agent'` at every trust level, including `trusted_agent` and `system`.
- Refuse `kind='service'` with `trust='system'`, `trusted_agent`, `untrusted_agent`, `imported` or `verified_human`.
- Refuse a `trusted_service` lacking the exact live delegation, or whose session/delegation tenant/project does not match.
- Paired positive: an active synthetic `service` / `trusted_service` actor, active synthetic session, exact live delegation and matching tenant/project mints normally and is recorded in `minted_by_actor_id`.

## Mutation shape

The discriminating mutation should remove only the kind/trust refusal while leaving actor/session derivation, delegation and recording in place. Give an `agent` / `trusted_agent` actor the exact synthetic delegation and session. Baseline refuses; the mutation makes the agent-backed mint succeed, and the committed observation sees the forbidden actor id in `custody_rows.minted_by_actor_id`.

This isolates the identity guard. Removing every actor check at once would not identify which comparison carries M8, and a mutation that also manufactures delegation would conflate identity with authority.

## Project context

This rule necessarily makes `agent_sessions.tenant_id/project_id` reachable at D4. Per the handoff, that fact is reported but no M3 deferral claim is made; whether it discharges ADR 0016's project-context deferral remains agent-a's decision.
