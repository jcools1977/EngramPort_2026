The twelve accepted `session:test` cases are therefore not missing lifecycle behavior. They are conditional evidence for an in-memory manager whose authenticator and authority resolver are trusted inputs. The missing work is establishing that trust and, separately, carrying the delegation durably without weakening the lifecycle.

## What “authenticated founder principal” means today

Today it means: “the arbitrary function wrapped by `founderAuthenticator` returned an object whose only key is a string `principal_id`.” The wrapper proves that a function was deliberately injected; it does not prove how that function authenticated anyone. `start` passes the supplied credential to that callback and correctly refuses extra identity fields, then sends the returned id to another injected callback wrapped by `founderAuthorityResolver`.

Every repository call site is a test fixture. The session fixture accepts the literal `fixture-only-founder-credential` and returns `{principal_id: "founder"}`; the approval fixture uses the same pattern. No production composition instantiates `SetupSessionManager`. There is no OIDC authorization-code exchange, issuer/audience/signature/time verification, PKCE/state/nonce binding, stable subject-to-canonical-principal mapping, or wiring from this manager to W1-5's accepted datastore resolver. “Authenticated” is therefore an interface precondition, not a fact established by current code.

A trustworthy end-to-end session would require:

1. A founder identity adapter that verifies an external OIDC result and maps its verified issuer/subject to the canonical principal id without accepting a caller principal assertion. It must request identity only, retain no refresh token, and destroy exchange transients.
2. Production composition that wires the accepted W1-5 authority resolver, so the founder authority is datastore-derived from that verified principal rather than supplied by an arbitrary application callback.
3. A server-created session result that D2 can bind to the privileged transaction. The present D2 input's `verified: true`, `principalId`, and `sessionId` are still ordinary caller-provided object fields unless an upstream trusted session establishment layer supplies them.
4. The C17 durable form below before any setup-session authority is persisted or shared across processes.

The adapter and its refusal behavior can be designed and tested with synthetic signed OIDC fixtures. Proving the actual configured issuer, client, redirect, account mapping, and exchange against a real identity provider requires external identity-provider authorization and configuration. Under the standing constraint, that step belongs to DeVere. It is a legitimate boundary finding, not an implementation failure.

## C17 position and durable form

C17 is **not satisfied by a durable setup-session delegation today**. Threat-model row 3.16 accurately says Model C, in memory. The manager creates no `agent_sessions` or `actor_delegations` row, and no production call site connects it to PostgreSQL.

The existing schema supplies two useful pieces but not the required record:

- `agent_sessions` (`migrations/0001_canonical_core.sql:46-52`) supplies a session id, tenant/project, actor, start/end timestamps, and lifecycle metadata. It has no founder principal, setup scopes, or authority expiry.
- `actor_delegations` (lines `42-45`) supplies actor, principal, scopes, and expiry. It has no session id, lifecycle status, or revocation/teardown link, and its primary key permits only one row per actor/principal pair. It cannot represent two concurrent setup sessions for the same service actor and founder.

Composing the tables by creating one actor per setup session would make identity cleanup and the “no standing wizard actor” criterion harder, and should not be treated as a schema-free solution. The durable form needs a forward schema decision: either a setup-session delegation relation keyed by `agent_session_id`, or an equivalent session key added to the delegation model, with founder principal, `setup:` scopes, absolute expiry, and terminal state bound to that one session.

Its trusted creation boundary must take only the already-authenticated principal identity plus requested setup bounds, call W1-5's resolver inside the creating transaction, derive rather than accept authority, enforce the founder ceiling and RET-SESSION's 24-hour ceiling against the database clock, and atomically create the session/delegation. Every authorization and introspection query must require the live session, live delegation, matching founder/context, and `expires_at > clock_timestamp()`.

Teardown must atomically end/tombstone the session, remove or irreversibly revoke its delegation and approvals, and leave no credential-bearing state. A server-side job must tombstone expired authority without application traffic. C6 then requires all five durable controls: expiry in every authorization read, scheduled server-side expiry handling, no expired authority reported active, database-clock evaluation, and a planted-expired/paired-live negative control across every read path.

All C17 datastore properties are provable with synthetic principals, actors, sessions, scopes, approvals, clocks, and PostgreSQL rows. They do not require a real credential or provider. What they cannot prove is the external authentication fact that supplied the principal.

## Synthetic-material boundary

- **Criterion 1:** scope restriction, resolver derivation, absolute expiry, credential non-retention, and OIDC verifier logic are synthetically provable. A real configured IdP and real founder account are not; DeVere authorization is required for that final establishment proof.
- **Criterion 2:** synthetically provable for both in-memory and future durable inventories and terminal residue.
- **Criterion 3:** synthetically provable for in-memory and durable paths using injected time and the database clock.
- **Criterion 4:** in-memory cleanup and future durable teardown are synthetically provable. Destruction of real OIDC exchange state at the actual provider boundary is not.
- **Criterion 5:** all four current cases and their future durable counterparts are synthetically provable.
- **C17:** fully provable on synthetic database material once its durable representation exists; it is independent of proving a real IdP exchange.

This means W1-1 can implement and close the lifecycle/durability evidence without a real credential only if its closure remains explicit that external founder authentication is an interface precondition. Removing the trusted-session caveat from A6/A7/A8 requires the separately authorized real identity-provider establishment proof.
