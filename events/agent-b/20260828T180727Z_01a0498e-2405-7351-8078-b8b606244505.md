## Convergence

The recommendations agree on nearly all of the operational shape:

- observation disposition must be durable and reconstructible on a fresh
  clone if the durable-cursor claim remains in force;
- a local cursor is only a disposable cache, never the deciding truth;
- an observation is a notification, not a work obligation, turn, claim,
  approval, or grant of implementation authority;
- disposition must not use `in_reply_to` against the observed event, because
  that would consume strict relay's single direct-reply slot;
- disposition belongs on a separate subscription thread or control stream;
- one record per observation has unacceptable asymptotic growth, so records
  should acknowledge ordered ranges or accepted batches; and
- at-least-once delivery is sufficient, so a crash may cause bounded duplicate
  notification but must not silently lose the uncheckpointed range.

This is enough to reject both a mutable shared projection and local-only state
under the current product promise.

## The remaining split: who writes the durable fact

Agent-a recommends that the subscriber append a batched `acknowledgment` in its
own event directory. The asserted fact is about that actor: it accepted the
covered observation range. This is attractive because actor ownership already
exists, the current event type can carry it, a clone can rebuild from it, and no
new shared multi-writer surface is needed.

Agent-b recommended an access-controlled delivery-control stream whose writer
is EngramPort. That recommendation deliberately narrows the durable claim to
what the product can prove: the configured delivery boundary accepted a batch.
It avoids claiming that a person or model read, understood, or agreed with the
content, and it keeps viewing behavior out of broadly readable project history.

These are not contradictory storage algorithms. They describe two different
acceptance boundaries:

1. **Subscriber assertion:** the actor signs an event saying its boundary
   accepted a range. This is the strongest evidence of subscriber acceptance
   that the existing protocol can represent.
2. **Service assertion:** EngramPort records that its own delivery boundary
   completed a batch. This proves product delivery but not semantic attention.

The returned recommendation uses the subscriber assertion when the subscriber
is capable of writing it. The subscriber owns the fact and appends it in its
own actor-owned subscription thread. A service-generated record may be used
only for a subscription whose declared boundary is itself service-controlled;
it must not impersonate the subscriber or upgrade delivery into human
acknowledgment.

## Privacy and authorization prevent a class-two ruling

Agent-a classifies the change as class two because `acknowledgment` already
exists. Reusing a type avoids a schema addition, but it does not avoid the
product decision. The new behavior exposes durable subscriber viewing history,
defines who may create and read subscription acknowledgments, introduces
caller-visible replay and retry semantics, and decides how selector changes
affect old disposition. ADR 0028 explicitly places privacy, authorization,
retry behavior, and caller-visible workflow changes in class three.

Therefore the protocol cannot move as class two merely because its envelope is
syntactically accepted. DeVere must first decide whether observation
disposition is project-visible actor history or private subscription history.
If project visibility is accepted, the existing actor-owned event directory is
the simplest canonical location. If it is not, an access-controlled canonical
control stream is required. In both cases the mutable latest cursor remains a
projection of append-only accepted records.

## Returned contract recommendation

Subject to DeVere's class-three decision, adopt these semantics:

1. Give every observation subscription a stable id and immutable selector
   revision.
2. After a non-empty ordered batch is accepted, the accepting principal appends
   one cumulative `acknowledgment` on a dedicated subscription thread or
   equivalently governed private control stream.
3. Bind the record to subscription id, selector revision, covered canonical
   source position or range, batch digest and count, and prior checkpoint id.
4. Treat those fields as evidence references, not `in_reply_to` edges. They
   grant no turn and cannot settle work delivery.
5. Rebuild the next position by verifying the checkpoint chain and scanning
   canonical source history after the highest accepted prefix. Local indexes
   may accelerate this but cannot decide correctness.
6. Append only after complete batch acceptance. A crash before append reoffers
   the batch; a crash afterward resumes after it. This gives at-least-once
   delivery with bounded duplicates.
7. Declare maximum batch size or checkpoint interval so growth and duplicate
   bounds are measurable. Never append for an empty poll.
8. On selector change, create a new revision with an explicit baseline or
   replay choice. Never reinterpret an old checkpoint under a new selector.

## Migration

Legacy local cursor state is advisory and must not be imported as accepted
disposition. Register stable subscriptions and selector revisions, rescan
canonical history, and reoffer matching observations unless an authorized
principal appends an explicit baseline acceptance. Expire in-flight legacy
delivery and prefer duplicate notification over silent loss. Stop reading the
legacy cursor after migration, retaining it only as a bounded rollback artifact.
The acceptance test is that a fresh machine derives the same acknowledged
prefix and next batch using canonical records alone.

This council recommends the contract and parks implementation for DeVere. No
source, schema, protocol, site copy, test, mutation, runtime behavior, or
`executed=` count changes.
