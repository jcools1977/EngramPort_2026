# W1-2 adversarial review

## Result

**Not sufficient as the W3 prerequisite. Bounded revision is recommended; W1-2 remains the sole WIP item.** The model identifies real risks and is substantially better than proceeding without one, but it currently overstates several protections as enforced, the capability schema does not establish the discovery/authority boundary it claims, and the fifteen-control gate is internally impossible to satisfy before W3 under the recorded task order.

I would **not** trust the system with a real GitHub App private key even if all fifteen controls passed as presently written. The missing prerequisite is an implemented, independently tested secret-custody/signing boundary: a connector-only identity authorized to ask a KMS/HSM or isolated secret service to sign, with the key-encryption key separately controlled, plaintext key material unavailable to the wizard/agents/runners, and logs/crash/core/backup paths covered. Control 4 proves only ciphertext-at-rest behavior; none proves who can decrypt or use the key, that the wizard cannot, or that plaintext is confined to an isolated signer. This must be demonstrated with a non-production key before a real key is introduced.

## Findings

### P0 — Section 10 cannot be a pre-W3 gate as scheduled

Controls 4–6 require an implemented GitHub App key store, rotation path, and uninstall behavior: those are W3-1 itself, so they cannot exist before W3 begins. Control 11 closes in PW4 according to F11. Control 12 needs W4 welcome-package generation. Control 13 needs Re:PORT, whose R1 work is undispatched. Therefore “W3 MUST NOT begin until every item exists” is unsatisfiable. It risks either permanently blocking W3 or encouraging a paper waiver of the gate.

Close by separating (a) prerequisites before any W3 implementation, (b) W3 acceptance controls using synthetic/non-production credentials, and (c) prerequisites before first real credential. Give every control an owning task and enforceable transition.

### P0 — Sections 4–5/schema: discovery is structurally separate from authority only on paper

No ingest validator, grant store, or invocation resolver consumes `capability-reference-v1`; repository search found only the schema and prose. Passing the schema cannot authorize anything today, but it also cannot prove denial.

The schema accepts `kind: capability_grant` with a `descriptor` payload because `kind` is not coupled to the selected branch. It accepts secrets nested anywhere in `descriptor.input_shape`, and accepts an invocable bearer value in `provider_installation_ref`. A grant's `credential_ref.locator` is unconstrained and may be the secret itself; `manager: env-file-local` also conflicts with claims that only an authorized server-side consumer can resolve it. The exact-name top-level list is not “deny-by-default”; semantic secret detection and recursive content policy are absent.

An implementer can therefore follow the document, receive `provider_installation_ref` from a compromised provider, pass schema validation, and hand that opaque value to the provider SDK as an invocable handle. Discovery has conferred practical authority even though the field is called a reference.

Close by defining and testing a closed descriptor envelope with provider-specific shape schemas referenced by identifier, coupling `kind` to payload, forbidding provider-supplied invocation locators, recursively scanning all strings before ingest, and proving the invocation service derives its credential/installation locator from an independently stored grant—not from descriptor bytes.

### P0 — Section 6 overstates bootstrap founder authority as enforced

`SetupSessionManager.start` authenticates a credential to `principal_id`, then trusts a caller-supplied `founder_authority` object. It checks only that the IDs match and the requested session scopes/expiry are subsets of that supplied object. No current code loads founder authority from a trusted store, creates the first tenant/project/owner membership, or proves the authenticated founder holds the asserted setup scopes. A caller able to invoke `start` can supply arbitrary founder scopes for the authenticated ID.

What is enforced is session narrowing relative to an input assertion, absence of a wizard principal in this in-memory object, and teardown. The root-of-authority chain described by ADR 0012 decision 3 is **required before W3**, not enforced today.

Close with a trusted bootstrap transaction/service that derives founder authority rather than accepting it from the request, atomically creates the first principal/tenant/project/owner relation, and supplies differential denial controls for forged founder authority and partial bootstrap failure.

### P1 — Sections 3 and 8 mislabel partial or nonexistent protections as enforced

- Founder credential non-retention is enforced within `SetupSessionManager`: the authenticator may return only `principal_id`, and the credential is not put in session state. It does not cover OIDC exchange/client state outside that interface.
- Temporary agent credential enforcement is overstated. PW1 passes a plain `{agent, project, scopes}` object to `RecordingRunner`; it has no token value, expiry, minting, authorized-call check, or revocation behavior, and the recording stub intentionally retains it. Only scope separation from supervisor scopes is currently enforced.
- Section 8 says required behavior is enforced by W1-1, but W1-1 has no provisioning credential holder and performs no external provisioning/grant effects. It enforces in-memory delegation/approval teardown and ordered abandonment checks only. Step-scoped destruction, rollback/compensation, and “no unapproved external effect” remain required before the relevant effectful phase.
- C6 is correctly described as future durable behavior. No durable setup/grant authority store exists, so all five C6 requirements remain required before any durable/multi-process authority path, including W3 if W3 persists grants.

Close by narrowing “enforced today” labels to the exact in-memory properties and marking the rest required with owning tasks.

### P1 — Section 3 credential inventory is incomplete

At minimum these sanctioned setup credentials/keys are absent as distinct rows:

1. **GitHub webhook secret**, explicitly required by ADR 0012 and W1-2 acceptance but not inventoried in section 3.2, whose lifecycle text discusses only the App private key and installation tokens.
2. **Key-encryption key / KMS authorization** used to envelope-encrypt the App private key and webhook secret. Without its owner, consumer, rotation, revocation, and separation rules, “encrypted at rest” merely moves the root secret.
3. **Welcome-package signing private key or signing-service authorization**. Setup issues signed welcome packages and the existing verifier/test uses an Ed25519 private key; the signer credential needs a sanctioned custody path.
4. **The newly created database application/runtime credential**, distinct from the founder's provisioning credential. Provisioning must deliver it to the runtime/secret manager without plan, log, artifact, or process-environment leakage.
5. **OIDC protocol transients** (authorization code, PKCE verifier, ID/access/refresh tokens, and any OIDC client secret). Calling the whole flow “Founder OIDC identity” does not assign each transient a permitted consumer or teardown rule.

Close by inventorying these explicitly before their owning phases and stating when a service-held credential is referenced versus when EngramPort itself stores encrypted bytes.

### P1 — Leakage inventory misses durable operational copies

The seven vectors do not explicitly bind CI logs/artifacts and caches, shell history, editor swap/autosave, backups/snapshots, Git object history/reflog after a rejected or amended write, core/crash dumps, and temporary files. Some can be grouped, but grouping must name the control and deletion/retention boundary. In particular, secret scanning before event acceptance does not remove a secret already written to Git's object database or a CI artifact.

Close with a cross-sink lifecycle table covering pre-write scanning, quarantine location, incident response, retention, backup/cache invalidation, and provider rotation. Do not claim quarantine is safe unless the quarantine itself is a secret store with narrower access and deletion semantics.

### P1 — Credential-reference semantics are not safely specified

The model says EngramPort is not a secret manager, yet section 3.2 requires EngramPort to store the App private key envelope-encrypted. The schema also says EngramPort never “stores, transits, or logs” a credential while allowing a server-resolvable `credential_ref`. These are materially different custody models.

Close by distinguishing participant-owned external references, tenant-owned encrypted connector secrets, and operation-scoped fetched tokens. For each, define which service can resolve/use the reference, tenant/project binding, confused-deputy prevention, reference enumeration resistance, revocation atomicity, and audit behavior.

### P2 — Control 15 is not presently measurable for the whole list

The W1-1 lazy-expiry/abandonment controls have useful differential provenance, but most future controls do not define the intentionally vulnerable implementation or mutation that must make the test fail. “Every negative control” also conflicts with controls that are positive confidentiality/lifecycle properties.

Close by giving each gate its counterfactual mutation/fault injection, expected failure, and retained evidence.

### F9 reproduction — reproduced

I passed `database.target = postgres://alice:REAL_SECRET@db.example/engram` to `compileSetup`. Compilation succeeded, `serializeSetupPlan` retained `REAL_SECRET`, and the `database.configure` action digest covered the credential-bearing value. This confirms the secret becomes review-surface and serialized plan data.

### F10 reproduction — reproduced by implementation census

Repository-wide search found requirements for detection but no detector, quarantine implementation, or detector call in the plan compiler, event append path, artifact registration, logs, welcome verification, or Re:PORT code. The F9 probe is also a live negative demonstration that compiler-side detection is absent. I did not plant a secret into the accepted event log because that would create the irreversible incident the model warns against.

### F11 reproduction — bounded by absent implementation

There is no subprocess runner adapter to exploit. PW1's `RecordingRunner` receives an in-process token argument; repository search found no production `spawn`/`exec` adapter or environment construction. Therefore F11 is confirmed as unprevented design scope, but environment leakage cannot yet be reproduced honestly. Its closure assignment to PW4 conflicts with section 10's pre-W3 wording.

### Capability schema probes

Using an actual draft-2020-12 validator against the canonical schema:

- baseline descriptor: accepted
- top-level `token`: rejected
- `input_shape: {token: "SECRET", nested: {private_key: "PEM"}}`: **accepted**
- `provider_installation_ref: "Bearer REAL_SECRET"`: **accepted**
- `kind: capability_grant` with only `descriptor`: **accepted**

Thus the deny-list works only for forbidden exact property names at the immediate descriptor/grant level.

### Existing implementation tests

I independently ran setup (22/22), session (12/12), approval (25/25), welcome-package (19/19), and Port Watch (16/16) tests. These support the bounded current claims above; they do not exercise a capability ingest/resolver, secret detector, provisioning credential holder, GitHub key store, durable C6 path, subprocess environment, welcome generator secret filtering, or Re:PORT.

## Fifteen-gate disposition

| Gate | Disposition now | Required point |
|---|---|---|
| 1 inline plan credential refusal | Not enforced; F9 reproduced | Before any credential-bearing provisioning and before real-key use |
| 2 step-complete provisioning credential destruction | Aspirational; no holder/driver | W2 acceptance, before real provisioning credential |
| 3 zero credentials after session end | Founder non-retention and in-memory teardown enforced; provisioning case unimplemented | Complete for all holders before real credential |
| 4 App key unreadable without KEK | Aspirational | W3 acceptance with synthetic key, before real key |
| 5 rotation invalidates old App key | Aspirational | W3 acceptance with synthetic key, before real key |
| 6 uninstall prevents resurrection | Aspirational | W3 acceptance/integration sandbox, before real key |
| 7 descriptor cannot invoke without grant | Aspirational; no resolver | Before connector invocation exists |
| 8 credential-shaped descriptor rejected | Schema backstop partial and bypassable; no ingest | Before descriptor ingest exists |
| 9 out-of-set advertisement yields no grant/invocation | Compiler permission allowlist exists only for setup plan; connector path absent | Before connector discovery/invocation |
| 10 detection/quarantine in four sinks | Not enforced; F10 | Before any real secret; sink implementations may stage later only if unreachable |
| 11 child environment contains no credential | Aspirational; no subprocess adapter; F11 | Before first credential-bearing subprocess, not necessarily before W3 if W3 cannot spawn |
| 12 guest welcome contains no secret/unauthorized capability | Existing verifier checks signed grant integrity, not secret content or generator authorization | W4 acceptance before first package, unless W3 produces packages |
| 13 Re:PORT excludes planted secret and raises incident | Aspirational; no Re:PORT implementation | R-phase acceptance before first model call, unless W3 can call it |
| 14 abandonment leaves no partial authority | Enforced for in-memory session/delegation/approvals; external effects absent | Re-prove at each effectful/durable implementation |
| 15 all negatives fail without control | Partial only; strongest for W1-1 differential probe | Per owning gate before its real credential/effect |

## Recommendation

Return W1-2 for bounded revision. Preserve its core rules, but correct the enforcement labels, repair or explicitly demote the schema backstop, inventory the missing credentials, split the impossible gate by lifecycle transition, and add the isolated secret-custody/signing prerequisite. Do not begin W3 or introduce a real GitHub App private key on the current wording.
