## B1 — Minted-reference custody writes need a Tier A control

Section 5 says a provider cannot forge a reference because minting requires an authorized custody write. No interface, authority rule, transaction, or negative control establishes that claim.

The missing contract must answer, per namespace:

- Who may mint? Shape references require a trusted registry administration path; installation references require an authorized installation path; credential references require the custody service. Providers, plans, callers, agents, and general application identities must not mint.
- What authority is verified? Derive authenticated principal or actor authority from the trusted resolver, bind tenant and project, require a namespace-specific scope, and reject caller-supplied tenant, project, principal, namespace, UUID, or reference as authority.
- Is storage atomic? UUID generation, sealed custody-row insertion, tenant/project/namespace binding, audit record, and reference return must be one transaction. A reference cannot be minted first and populated later.
- Can an orphan or cross-tenant reference be created? Schema validation accepts valid-looking unresolved references, as it should; my probe confirmed this. The custody API must reject caller-chosen references, foreign tenant/project bindings, duplicate UUIDs, wrong namespaces, missing custody payloads, and orphan rows.

A7 currently requires only declared custody models, tenant binding, and revocation atomicity. Extend A7 or add one Tier A control for this custody-write interface and its counterfactuals.

## B2 — Shape selection remains provider-controlled

Descriptors reject installation_ref and credential_ref, and each reference field pins its namespace. Cross-namespace probes were rejected.

But a descriptor is required to carry shape_ref, so “no reference of any kind” is literally false; the intended property is no custody or authority-bearing reference. More importantly, provider-controlled descriptor bytes can select any syntactically valid, locally resolvable shape_ref. My probe confirmed an alternate epr:shape value passes schema. N3–N5 prevent unknown shapes and registration or shadowing, but not selection among existing local shapes.

The local registry must own a pinned mapping from provider/capability/protocol version to shape revision. Ingest must derive or compare the expected shape_ref; provider bytes must not choose it. Add a mismatch negative control.

## B3 — Grant creation and invocation checks are incomplete

A6 needs named negative controls for forged, already-expired, revoked, cross-project, cross-tenant, wrong-provider, wrong-capability, and grantor-exceeds-authority records, plus a positive control.

Section 6 requires tenant, project, live status, expiry, provider, capability, and custody resolution. It does not explicitly require:

- invoking principal equals granted_to_principal_id;
- invoking actor matches granted_to_actor_id when present;
- requested operation scope is contained in stored grant scopes;
- both stored grant and referenced custody rows are unrevoked at use time.

“Authorized consumer only” is not a substitute for these comparisons. Add them to the resolution contract and B9. Existence of a valid reference or custody row never suffices.

## B5 — Credential lifecycle coverage is still short of complete

All fourteen listed rows point to Tier C gates. Consolidations C8 and C11 are acceptable only if the combined control runs before either constituent first exists and reports evidence for each.

Two authority-bearing credentials remain unnamed:

1. GitHub App authentication JWT, minted with the App key and exchanged for the installation access token. It needs issuance, claims/audience, expiry, replay, non-persistence, and teardown. It may be consolidated into C1/C9 if explicitly inventoried and gated before the first JWT exists.
2. Setup-session delegation. Revision 2 inventoried it; revision 3 drops it. It may be consolidated into A1/A2 and C7 if its lifecycle is named and the durable gate precedes the first durable delegation.

## B6 — Ingest and canary checks need faults that actually fail absence checks

N1–N14 and positive P are concrete, but W1-6 must retain evidence that each negative fails when its guard is removed or dependency faults.

The signer positive control is sound: signing must succeed while confinement remains active. The listed absence faults are not uniformly falsifiable:

- trace logging does not itself place the canary in a log;
- enumerating argv or environ observes but does not make the checker fail;
- forcing a crash or backup creates a searchable artifact but does not prove detection unless a deliberately vulnerable variant places the canary there;
- a known canary import path must stay isolated from the production non-exportable-key path.

For every sink, run an isolated vulnerable variant routing the known canary into the sink and prove the checker fails, then run the protected variant and prove it clean while signing succeeds.

## F14 — separate protocol finding

F14 is accurate and independent: Git v0 cannot supersede an artifact binding and therefore cannot safely redact bound bytes.

F14 does not broaden or block W1-2, and it does not block synthetic W3 work when A4 refuses credential-bearing artifacts before binding. It does become a prerequisite before any external or credential-bearing artifact may be bound. Close it through typed supersession in a later schema, or structurally prohibit such bytes from bound artifacts and keep quarantine in a deletable secret store. Until then, detector misses are permanent proof obligations.
