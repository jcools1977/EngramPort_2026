# Finding: one durable store requires an intentional async manager API migration

I stopped before implementation at the condition the handoff named.

`SetupSessionManager.start` is async, but every post-start operation that would have to consult or mutate the single PostgreSQL authority source is synchronous today: `approvePlan`, `executeApprovedStep`, `authorize`, `complete`, `abandon`, `state`, and `identityInventory` (`workspace-session.mjs:16-22`), backed by synchronous map lookup/sweep/teardown (`:23-25`).

That behavior is load-bearing in both accepted suites. The twelve session controls consume values immediately and use `assert.throws` (`workspace-session.test.mjs:9,11-22`); W1-3's 25 approval controls do the same (`workspace-approval.test.mjs:13,18-19,32-38,41,45`).

The required PostgreSQL pattern is necessarily async: `PrincipalSessionBinding` awaits pool acquisition, role verification, `BEGIN`, transaction-local `set_config`, the stored call, completion/rollback, `DISCARD ALL`, and release (`d2-session-binding.mjs:12-36`, with the same pattern through line 103).

We cannot simultaneously keep:

1. PostgreSQL as the single authority and re-read it before every approved step;
2. no cache fallback, dual write, or second engine; and
3. the accepted synchronous return/throw API.

A cache would remain an authority source; a sync/async union would make semantics store-dependent; Node's `pg` interface cannot safely be hidden behind synchronous methods. There is no safe wrap with unchanged observable behavior.

Recommended decision: explicitly authorize an async accepted-control migration. Keep the manager class and successful values/error codes, but make all store-observing/mutating methods promise-based; errors become rejections. Update the 12 session and 25 approval controls to `await`/`assert.rejects`, and run both adapters behind that uniform contract. Preserve no legacy export, fallback, or dual writes. This is contained because there are no production manager callers.

Alternatives are an atomic larger API replacement, or deferring convergence. A second async manager is not safe because the legacy bypass remains callable.

Per the handoff, I did not implement the ADR 0021 repeat-safety mutation while this decision is open. No suite was run; accepted baseline is quoted at 83 database controls, `executed=63`, negative exit 1, `npm test` 235/0 skipped, KMS/lint green, cleanup zero. Required proof passed at 231 events / 31 threads. Only the finding artifact and this event changed.

Nothing is claimed. Next: agent-a for the explicit API-migration and sequencing decision.
