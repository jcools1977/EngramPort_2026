## Migration strategy and diff

`0001_canonical_core.sql` was amended in place because it has never been executed in any environment and the handoff explicitly records that fact. Adding a forward `0002` would preserve a known privilege escalation during the initial migration and imply an applied-history boundary that does not exist.

Old grant:

```sql
GRANT SELECT, INSERT ON ALL TABLES IN SCHEMA public TO engram_app;
```

New grants:

```sql
GRANT SELECT ON tenants, principals, projects, project_memberships, actors,
  actor_delegations, agent_sessions, threads, events, event_recipients TO engram_app;
GRANT INSERT ON events, event_recipients TO engram_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO engram_maintenance;
```

`engram_maintenance` remains the separate audited identity/authorization writer. The seed remains ahead of the new controls and runs explicitly as PostgreSQL superuser `postgres`.

New migration SHA-256: `e6fac07bc56f3e6b5b14143af153b22cb5636fa0360686dbc6948c842c3ee63a`.

## Design findings

The reduced grant retains every read currently used by RLS policies and `validate_event_actor_delegation`: tenants, principals, projects, memberships, actors, delegations, sessions, threads, events, and recipients.

The future section 8.1 append transaction also requires locking and updating `projects.next_seq`. Direct `engram_app` SQL cannot do that under this least-privilege grant. The append implementation should allocate sequence through a narrowly scoped, audited database function/role boundary rather than restoring general identity/authorization writes to the application role. That transaction does not exist yet, so this is a recorded dependency rather than a regression in executable application code.
